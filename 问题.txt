【问题1】刷新后浏览器状态不一致（严重）
时间：12:16（触发后约 8 秒刷新）
现象：
- 浏览器1（触发浏览器）：显示"研究进行中"、"点击查看实时进度"
- 浏览器2（刷新后）：显示"研究已完成"、"点击查看详细报告和文件"、"继续研究"按钮
- 浏览器2 URL 自动恢复 session_id=53c340a0-8e36-4e94-8531-27b51346ff13 ✅
- 浏览器2 模式显示"⚡ 代理"（非"深度研究"模式）✗
分析：
- 浏览器2 刷新后从后端加载会话状态，但后端返回的状态是"研究已完成"
- 浏览器1 仍在流式输出中，显示"研究进行中"
- 状态不一致：可能后端的 stream_completed 事件已发布，但浏览器1未收到/未处理
- 或者刷新后加载的 ChatSession 状态与实时状态不同步
后续观察：点击"确认执行"后，浏览器2 通过实时同步纠正为"研究进行中"，状态恢复一致
结论：刷新瞬间状态不一致，但实时同步会自动纠正

【问题2】深度研究详情未实时同步工具调用状态（严重）
时间：12:21（点击第一个"确认执行"后约 5 秒）
现象：
- 浏览器1（聊天模块）：工具调用 (2)，第一个 shell_exec 已完成，第二个 shell_exec 等待中/待审批
- 浏览器2（聊天模块）：工具调用 (2)，与浏览器1一致 ✅
- 浏览器3（深度研究详情）：工具调用 (1)，第一个 shell_exec 仍显示"等待中/待审批" ✗
  - 进度 27%
  - 未显示第二个工具调用
  - 审批状态未更新（仍为待审批，应已变为已确认）
分析：
- 深度研究详情页面的工具调用状态没有实时更新
- 可能原因：
  1. 深度研究详情使用轮询而非 WebSocket 实时同步
  2. task 频道的 tool_call_completed 事件未触发详情页面更新
  3. researchStore.updateTaskFromEvent 未正确处理工具调用状态
- 这是跨模块实时同步的核心问题：聊天模块的审批状态变更未同步到深度研究详情

【问题3】跨浏览器工具调用数量严重不一致（严重）
时间：12:24（点击第二个"确认执行"后约 8 秒）
现象：
- 浏览器1（触发浏览器）：工具调用 (3)，第三个 shell_exec（ollama ps）等待中/待审批
- 浏览器2（刷新过的）：工具调用 (7)，第三个 shell_exec（ollama ps）已超时，第四个 shell_exec（python -c）已超时
  - 显示"队列 7"，远超浏览器1的3个
分析：
- 浏览器2 显示的工具调用数量（7）远多于浏览器1（3）
- 浏览器2 显示第三个工具"已超时"，但浏览器1显示"等待中/待审批"
- 可能原因：
  1. 浏览器2 收到了历史回放事件（replayFromSeq），包含了旧的工具调用
  2. 浏览器2 的 toolCallsMap 累积了重复的工具调用（去重失败）
  3. 后端事件序列号不连续，导致浏览器2 看到了不同时间点的快照
  4. 浏览器1 的 WebSocket 事件丢失（未收到 tool_call_completed）
- 这是实时同步的核心问题：不同浏览器看到不同数量的工具调用

【问题4】工具调用显示"已超时"但浏览器1仍显示"等待中"
时间：12:24
现象：
- 浏览器2：第三个 shell_exec（ollama ps）显示"已超时"
- 浏览器1：第三个 shell_exec（ollama ps）显示"等待中/待审批"
分析：
- 工具调用实际已超时（后端 60 秒超时），但浏览器1 未收到 tool_call_timeout 事件
- 浏览器2 收到了超时事件，状态正确
- 浏览器1 的 WebSocket 事件可能丢失或延迟

【问题5】深度研究详情完全未同步工具调用状态（确认问题2，严重）
时间：12:26（测试进行约 10 分钟后）
现象：
- 浏览器1/2/4（聊天模块）：工具调用 (7)，多个工具已完成/已超时
- 浏览器3（深度研究详情）：工具调用 (1)，第一个 shell_exec（ollama list）仍"等待中/待审批"，进度 90%
分析：
- 深度研究详情页面完全没有实时同步工具调用状态
- 聊天模块的工具调用状态变更（已完成/已超时）未同步到深度研究详情
- 可能原因：
  1. 深度研究详情页面使用轮询（"轮询中"），而非 WebSocket 实时同步
  2. SSE 连接只接收 stream_reasoning 事件，不接收 tool_call_* 事件
  3. researchStore.taskInfo.toolCalls 与 sessionStore.toolCallsMap 是分离的，未同步
  4. handleStreamCompleted 委托更新 taskInfo 只更新 taskInfo 本身，未更新 toolCalls
- 这是"聊天模块深度研究模式 ↔ 深度研究详情"实时同步的核心问题

【问题6】浏览器1事件滞后（严重）
时间：12:24-12:26
现象：
- 12:24 时浏览器1显示工具调用 (3)，第三个"等待中/待审批"
- 12:26 时浏览器1跳到工具调用 (7)，第三/四个"已超时"
- 浏览器2/4 在 12:24 时已经显示工具调用 (7)
分析：
- 浏览器1（触发浏览器）的事件接收滞后于浏览器2/4
- 可能原因：
  1. 浏览器1 的 SSE 流占用主线程，WebSocket 事件处理被阻塞
  2. 浏览器1 的 _processSessionEventOrdered 间隙等待逻辑导致延迟
  3. 浏览器1 的事件队列积压，处理速度跟不上事件到达速度
- 触发浏览器反而比非触发浏览器更慢，这是反直觉的

【问题7】深度研究详情审批后聊天模块审批状态未更新（严重）
时间：12:28
现象：
- 在浏览器3（深度研究详情）点击"确认执行"后：
  - 浏览器3：第一个 shell_exec 审批状态变为"已确认"，审批按钮消失
  - 浏览器1（聊天模块）：仍显示 2 个审批按钮（确认执行、拒绝），审批状态未更新
  - 工具调用 (7)，但仍有待审批的工具
分析：
- 深度研究详情的审批操作未同步到聊天模块
- 可能原因：
  1. 深度研究详情使用独立的审批 API，未通过 session 频道发布 approval_approved 事件
  2. 深度研究详情的审批只更新了 task 频道，未更新 session 频道
  3. 审批事件的双频道发布在深度研究详情审批路径上未生效
- 这是跨模块实时同步的核心问题：深度研究详情的审批操作未同步到聊天模块

【问题8】深度研究详情工具调用列表不更新（严重）
时间：12:28
现象：
- 浏览器3（深度研究详情）点击"确认执行"后，工具调用列表仍只显示 (1)
- 实际聊天模块显示工具调用 (7)，多个工具已完成/已超时
- 深度研究详情的"工具调用"区域不随实时事件更新
分析：
- 深度研究详情页面的工具调用列表是静态的（基于首次加载的快照）
- 没有订阅 WebSocket 的 tool_call_* 事件来实时更新工具调用列表
- 只通过轮询更新任务状态（进度百分比），不更新工具调用详情

【问题9】Agent 陷入工具调用重试循环，工具调用数激增到 17（严重）
时间：12:30
现象：
- 浏览器1 工具调用数从 7 激增到 17
- 多个工具调用显示"已超时"
- Agent 不断重试 ollama ps、python -c、write_file 等工具
分析：
- ollama ps 命令超时（可能 ollama 服务未运行或响应慢）
- Agent 超时后未正确处理，继续重试相同或类似的工具
- 工具调用数量无上限增长，可能导致前端性能问题
- 这与实时同步有关：工具超时事件未正确通知 Agent 调整策略

发现的问题（按严重程度排序）：

【严重】问题5/8：深度研究详情完全未同步工具调用状态
- 浏览器3（深度研究详情）始终显示工具调用 (1)
- 聊天模块显示工具调用 (17)
- 深度研究详情的工具调用列表是静态的，不随实时事件更新
- 这是"聊天模块深度研究模式 ↔ 深度研究详情"实时同步的核心问题

【严重】问题7：深度研究详情审批后聊天模块审批状态未更新
- 在浏览器3点击"确认执行"后，浏览器1 仍显示审批按钮
- 深度研究详情的审批操作未同步到聊天模块
- 审批事件的双频道发布在深度研究详情审批路径上未生效

【严重】问题3/6：跨浏览器工具调用数量不一致（中间状态）
- 浏览器1（触发浏览器）事件滞后于浏览器2/4
- 12:24 时浏览器1显示 (3)，浏览器2/4 显示 (7)
- 12:26 时浏览器1追上到 (7)
- 触发浏览器反而比非触发浏览器更慢

【严重】问题9：Agent 陷入工具调用重试循环
- 工具调用数从 7 激增到 17
- ollama ps 超时后 Agent 不断重试
- 工具调用数量无上限增长

【中等】问题1：刷新后浏览器状态不一致
- 浏览器2 刷新后显示"研究已完成"，但实际"研究进行中"
- 后续通过实时同步自动纠正

【中等】问题4：工具调用显示"已超时"但浏览器1仍显示"等待中"
- 工具超时事件未及时到达浏览器1

========================================
问题根因初步分析
========================================

1. 深度研究详情的实时同步缺失（问题5/7/8）
   - 深度研究详情页面使用轮询，未订阅 WebSocket 的 tool_call_* 事件
   - 深度研究详情的审批 API 未通过 session 频道发布 approval_approved 事件
   - researchStore.taskInfo.toolCalls 与 sessionStore.toolCallsMap 是分离的

2. 触发浏览器事件滞后（问题3/6）
   - SSE 流占用主线程，WebSocket 事件处理被阻塞
   - 或 _processSessionEventOrdered 间隙等待逻辑导致延迟

3. Agent 重试循环（问题9）
   - 工具超时后 Agent 未正确调整策略
   - 可能与实时同步的 timeout 事件处理有关
