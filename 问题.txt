# 测试问题记录（spec: unify-tool-call-display-parallel-subagents）

## 场景：chat 代理模式「并行派发 2 子代理 + wait_for_subagent 批量等待」实测（4 浏览器）

### 问题 1（核心）：父代理总结正文渲染位置错乱 —— 总结段插入在子代理 1 与子代理 2 之间
- 现象：父 agent 最终总结（"两个子代理均已执行完毕，以下是汇总结果：📋 任务汇总..."）被切段渲染为：
  1. "两个子代理均已执行完毕，以下是汇总结果："（38 字符）渲染在子代理 1 卡之前
  2. 其余总结（"📋 任务汇总 ✅ 子代理 1... ✅ 子代理 2... 综合结论"）渲染在子代理 1 卡与子代理 2 卡之间
  3. wait_for_subagent 卡反而在最后
- 期望：总结应在所有工具卡（含 wait_for_subagent）之后
- 根因（前端内存数据实证）：
  - message.content 被持久化/更新为**最终总结段**（1158 字符），流式段1（"好的，我将并行派发..."）不在 content 中
  - mainToolCalls position 基准不一致：spawn1 pos=38（流式早期值），**spawn2 pos=undefined、wait_for pos=undefined**（position 注入缺失）
  - splitContentByToolPositions：有 position 的 spawn1 切在 content[0:38]，无 position 的 spawn2/wait_for 追加**末尾**，收尾内容段（剩余总结）排在其前 → 总结段夹在卡1 与卡2 之间
- 关键数据：msg id=3472 tool_calls = [spawn(38), spawn(undefined), wait_for(undefined), shell_exec×8(sub=None)]，content_len=1158

### 问题 2：刷新后子代理工具卡脱离子代理卡（渲染为独立主代理工具卡）
- 现象：刷新浏览器后，8 个 shell_exec 工具卡（子代理内部）渲染为消息流中的独立 ToolCallCard，不在子代理卡展开面板内
- 根因：DB 持久化的 tool_calls 中 8 个 shell_exec 的 **subagent_thread_id 全部为 None**（sub=None）→ 前端 buildSubagentsFromMessage 按 subagentThreadId 归集失败 → 落入 mainToolCalls 渲染为主代理工具卡
- 疑点：subagent_tool_entries 聚合时含 subagent_thread_id（tool_call_aggregation.py aggregate_tool_entry），持久化合并（stream_persistence.py L451-456 追加）链路中图层字段丢失

### 问题 3：刷新后执行中的自动通过工具卡（dir /x）完全丢失
- 现象：dir /x（自动通过、执行中）在刷新后不渲染；python -c（高危待审批）从 Approval 表还原存在
- 根因：wait_for_subagent 挂起时 _persist_chat_tool_calls 只落库挂起前条目；挂起后子代理内部执行的**自动通过**工具卡（无审批记录、无持久化）无数据源可还原；仅需审批卡（有 Approval 记录）经 enrich_tool_calls_with_approvals 还原

### 问题 4：子代理 1 卡状态未更新（任务完成后仍显示"执行中"）
- 现象：任务全部完成（子代理 2 已完成、wait_for 已完成）后，子代理 1 卡仍显示"执行中"
- 疑点：子代理 1（dir-lister）经多次审批 + 自动通过命令，SubAgentInstance.status 或前端推导状态未收敛为已完成；子代理 2（单轮审批）正常

## 2026-08-17 复测结论（服务重启加载新代码前，12:42 测试会话 d3321217 / msg 3486）

### 问题 5 根因确认（两层）
- **根因 A（主因，DB 实证 msg 3486）**：`stream_persistence._merge_tool_calls_incremental` 的 **name 降级匹配**
  - existing 已含首个子代理的 shell_exec（ollama-list）后，后续子代理（ollama-ps / env-version）的同名
    shell_exec 条目（id 不同）被 `existing_by_name["shell_exec"]` 匹配 → 演进合并（吞掉新条目）而非追加
    → 聚合条目（带 subagent_thread_id/agent_name/depth）无法落库（persist count 不变、changed=False）
  - 日志证据：ollama-list PENDING 后 persist count 4→5（聚合成功）；ollama-ps / env-version PENDING 后
    count 5→5（被 name 匹配吞掉）；随后 `sync_approval_state_to_chat_message: 已重建缺失 tool_call 项`
  - ollama-ps 最终有图层字段：审批重建（无图层字段）→ 后续主链路 persist 按 **id** 匹配演进补全
    （_evolve_tool_call 图层字段补全分支）；env-version 审批后无后续 persist → 保持无图层字段
- **根因 B（兜底缺失，代码实证）**：`approval_service.sync_approval_state_to_chat_message` 重建缺失
  tool_call 项时只写 id/name/args/parameters/approval + seq/position，**未写 subagent_thread_id /
  agent_name / depth**（审批 extra 已透传这些字段，create_approvals_for_interrupts 写入）
- 前端表现（复现确认）：中途刷新浏览器页面4 后，env-version 两个 shell_exec 卡插在主正文中间
  （"三个"段之后），显示 agent_path "main → env-version-runner → env-version-runner" 但脱离子代理卡

### 问题 5 修复（已实施，待重启验证）
1. `stream_persistence._merge_tool_calls_incremental`：name 降级匹配仅限 new 条目**无 id** 的旧数据
   兼容场景；new 有 id 时仅按 id 精确匹配 → 同名工具不再误合并，聚合条目正常追加落库
2. `approval_service.sync_approval_state_to_chat_message` 重建分支：从 approval.extra 读取
   subagent_thread_id / agent_name / depth / parent_tool_call_id / agent_path 补齐重建条目图层字段

### 问题 6 根因确认与修复
- 根因（日志 + DB 实证）：子代理审批超时信令 resume_value='_timeout'（字符串，非批量决策 dict），
  旧代码 `_resume_subagent_from_signal` 无 collect 回退 → decisions 为空 → "缺少批量决策，跳过恢复"
  → 子代理永远挂起（interrupted_pending_user_input），wait_for_subagent 永不结束
- DB 实证（session 9c74c6b1）：子代理审批 extra 均正确落库 graph_interrupt_id（291ccd...等）与
  subagent_thread_id（subagent_88eac...等），state=timeout → collect_batch_decisions 可收集
  {tool_call_id: TIMEOUT_DECISION} → 修复链路成立
- 修复（session_manager._resume_subagent_from_signal，已加载）：resume_value 非 dict 且携带
  graph_interrupt_id 时回退 collect_batch_decisions 收集批次决策，全部决断后 finalize +
  runtime.resume 恢复子代理（Agent 收到超时 ToolMessage 调整策略继续）
