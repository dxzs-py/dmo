## 2026-08-11 深度研究 write_file 审批期间显示重复/在最前（观察记录）
### 现象
任务执行到 write_file（写研究计划）审批时：
- 页面顶部"审批面板"区显示 1 个 write_file（含确认/拒绝按钮）
- 下方"工具调用记录"区同时显示 1 个 write_file 卡片
- 用户感知为"write_file 在最前面和最后都出现了"
- 点击"确认执行"后：顶部审批面板消失，工具调用记录仅剩 1 个 write_file，顺序恢复为 write_todos → ls → write_file（正常）

### 分析
审批面板区（ResearchTaskDetail.vue L84-102）与工具调用记录区（L105-121）各自渲染 ToolCallCard：
- 审批面板渲染 approvalStore.pendingApprovals（taskId 过滤后）
- 工具调用记录渲染 researchStore.toolCalls（含 approval 字段的 write_file）
同一工具在两个区域各显示一次 → 视觉上"重复 + 在最前"。
审批通过后 pendingApprovals 移除该条目 → 审批面板消失 → 恢复单个。

### 待确认
- 是否符合预期 UX（审批中的工具是否需要同时在两个区域显示）？
- 工具调用记录区 write_file 排序是否始终正确（当前观察：write_todos → ls → write_file，正常）

### 用户结论
write_file 在最前/重复 = 两处独立渲染：① 工具调用记录区展示 1 个；② 工具调用记录上方（ResearchTaskDetail 的审批面板区）额外展示 1 个，点击"确认执行"后消失。判定为旧版本/冗余代码组件导致，待清理。

## 2026-08-11 深度研究 read_file 审批通过后卡片卡"执行中"（复现）
### 现象
任务 research_d2e2f1866e1e：read_file（读取 /plans/research_plan.md，controlled 级）审批通过后：
- 前端工具卡片状态停留在"执行中"，无输出结果，永不更新
- 任务本身继续推进（20:44:09 出现新的 write_file 审批），read_file 结果被使用但前端无感知
- 与任务 research_446650f66639 现象一致（复现）

### 后端日志证据（django.log + 日志2.txt）
1. 20:42:43 发布 approval_pending（interrupt_id=call_00_vo9L2bW4iQ0qkhor4qkT9813, graph_interrupt_id=236d79...）+ tool_call_waiting
2. 20:43:25 用户确认 → approval_processing + tool_call_running → ApprovalGateway 恢复（approved=True）
3. 20:43:25 恢复执行 → middleware 第二次拦截"需要审批 read_file"（新 graph_interrupt_id=79985419）→ "用户已确认"（516）→ "审批完成: 保留 2 个"（565）
4. **此后无 read_file 的 tool_call_completed 事件**（ToolCallLifecycle 无任何"上下文不存在/非法转换/同批次指纹跳过"日志，说明 transition(COMPLETED) 未被调用）
5. 对比 write_file（任务开头审批）：恢复执行后正常发布 tool_call_completed（带 graph_interrupt_id）

### 根因（待最终确认）
- read_file 审批恢复执行（恢复线程重新初始化 ContextManagerMiddleware）后，ToolNode 执行 read_file → ToolMessage 产出 → adapter.py messages 模式 extract_tool_events_from_message 提取 COMPLETED → _publish_tool_event → transition_async。
- 疑点：seen_tool_call_ids（恢复模式预热，count=8）中 read_file 的 tool_call_id 已存在 → extractor 分支 1（AIMessage）跳过，但分支 2（ToolMessage）**只对 PENDING 用 seen 去重**，COMPLETED 应正常发射。
- 需进一步确认：恢复模式下 messages 模式的 astream 是否产出 read_file 的 ToolMessage；或 ToolNodePatch 的 skipped_call_ids（已有 ToolMessage 跳过执行）导致 read_file 未执行。
