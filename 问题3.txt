## 2026-08-11 深度研究 write_file 审批期间显示重复/在最前（观察记录）
### 现象
任务执行到 write_file（写研究计划）审批时：
- 页面顶部"审批面板"区显示 1 个 write_file（含确认/拒绝按钮）
- 下方"工具调用记录"区同时显示 1 个 write_file 卡片
- 用户感知为"write_file 在最前面和最后都出现了"
- 点击"确认执行"后：顶部审批面板消失，工具调用记录仅剩 1 个 write_file，顺序恢复为 write_todos → ls → write_file（正常）

### 分析
审批面板区（ResearchTaskDetail.vue L84-102）与工具调用记录区（L105-121）各自渲染 ToolCallCard：
- 审批面板渲染 approvalStore.pendingApprovals（taskId 过滤后）
- 工具调用记录渲染 researchStore.toolCalls（含 approval 字段的 write_file）
同一工具在两个区域各显示一次 → 视觉上"重复 + 在最前"。
审批通过后 pendingApprovals 移除该条目 → 审批面板消失 → 恢复单个。

### 待确认
- 是否符合预期 UX（审批中的工具是否需要同时在两个区域显示）？
- 工具调用记录区 write_file 排序是否始终正确（当前观察：write_todos → ls → write_file，正常）

### 用户结论
write_file 在最前/重复 = 两处独立渲染：① 工具调用记录区展示 1 个；② 工具调用记录上方（ResearchTaskDetail 的审批面板区）额外展示 1 个，点击"确认执行"后消失。判定为旧版本/冗余代码组件导致，待清理。

## 2026-08-12 审批超时后任务永久停止（第四次反馈）
### 现象
research_bbb46677d112 的 read_file 审批（call_00_zAJAKhYVQbVbJxdVjyGe9055）超时后整个任务停止，浏览器长时间无响应。
### 后端日志证据（日志2.txt L1654-1682）
1. L1655-1656 cleanup 扫描到 1 条超时审批（2376）→ timeout_approval 完整执行（L1662 Redis 持久化 state=timeout）
2. L1672 `超时递减pending计数: remaining=2`（该任务仅 1 条 pending → 计数偏差）
3. L1674 gateway 路由 deep_research 恢复（approved=False）→ 派发 research.resume
4. **L1678 `[Resume] 同批次尚有未决断审批，退出: resolved=0` → Task research.resume succeeded: {'status': 'waiting', 'reason': 'batch_not_all_resolved'} → 永久卡死**
### DB/Redis 实证
- DB：2376 `state=processing`（timeout_approval 只把 DB 置 PROCESSING，_persist_and_broadcast 不更新 DB）
- Redis：`approval:processed:call_00_zAJAKhYVQbVbJxdVjyGe9055` = `timeout` → **DB/Redis 状态不一致**
- 模拟实验：2376 置 pending+过期 → timeout_approval → DB=processing；pending 态下 `_collect_batch_decisions` 返回 `({}, False)`（resolved=0，与日志吻合）
### 根因链（5 个缺陷叠加）
1. research_resume_task 批次判定 `_collect_batch_decisions` 读到 pending → `batch_not_all_resolved` 直接退出，无自愈/重试 → 永久卡死
2. DB/Redis 状态不一致：DB 停留 PROCESSING（被误判为"已批准"），Redis 是 timeout
3. 并行恢复无 thread 粒度锁：1da9d0d4（155.9s）+ ab3725c7（58.7s）并行恢复同一 thread（checkpoint 竞争 + 重复审批）
4. timeout_approval 成功路由后不释放 task 锁（TTL 1800s 残留）→ 后续超时恢复被跳过
5. remaining==0 短路：计数归零直接 return 不触发恢复 → 单审批超时卡死
### 修复（已实施）
- approval_service.timeout_approval：加 dispatch_resume 参数；DB 终态化为 TIMEOUT；移除 remaining==0 短路；移除 task 锁（并行防护移交 research_resume_task thread 锁）
- deep_research.research_resume_task：max_retries 1→10；入口 thread 粒度锁（research:resume:task_lock:{thread_id}）；批次未决断先自愈（过期 pending → timeout_approval(dispatch_resume=False) 终态化）→ 重新收集 → 仍未决断 retry(countdown=5)；外层 except Retry: raise
- 验证：pending+过期 → timeout_approval(dispatch_resume=False) → DB=timeout → `_collect_batch_decisions` 返回 resolved=1（TIMEOUT 视为已决断=False，恢复命令可构建）
### 附加修复（计划 3.1-3.7 补全）
- 3.1 extractor：chunk args 类型归一化（dict/list → json.dumps），防拼接 TypeError；聚合验证通过（分片拼回 {"todos": ["a", 1]}）
- 3.2 策略补全：write_todos（原 todo_write）+ ls/glob/grep/web_search/web_fetch SAFE 策略 → middleware 注册验证通过（POLICY_OK）
- 3.3 middleware：无策略工具注册 ctx（完整参数，不发布 RUNNING）
- 3.4 adapter._publish_tool_event：parameters 空时从 ctx 兜底（权威参数源）
- 3.5 middleware 审批幂等：已审批/已完成 tc_id 跳过拦截（恢复后不重复审批）；tool_node_patch 经复核不收紧（正常 ToolMessage 跳过 = 防重复执行，收紧有重复执行风险）
