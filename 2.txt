## 问题描述

## 根因
risk_level 字段只存在于 approval_* 事件 payload 中（通过 _build_approval_extra_fields
注入顶层），不在 tool_call_* 事件 payload 中。

- 触发浏览器：通过 approval_pending 事件获取 risk_level → 正确显示"需审批"
- 非触发浏览器：依赖同一 approval_pending 事件路径，但该事件可能因 seq 跳号、
  INTERRUPTED 状态跳过、全量同步覆盖而丢失，导致 riskLevel 缺失
- 旧代码 dangerLevel 回退 'low' → 'safe'，导致误显示"安全"

## 修复方案（根本修复）

### 阶段 1：risk_level 注入 tool_call_* 事件 payload
后端：
1. tool_call_lifecycle.py ToolCallContext 添加 risk_level 字段
2. tool_call_lifecycle.py register 方法补全 risk_level（仅补全空字段）
3. tool_call_lifecycle.py transition/transition_async 透传 risk_level 到 publish_tool_call
4. tool_call_lifecycle.py 新增 _normalize_risk_level 函数
5. realtime_sync.py publish_tool_call 添加 risk_level 参数，payload 注入 risk_level

=================================================================

一、问题描述
后端日志：
WARNING [ChatApprovalResume] 校验失败: interrupt_id=call_00_kjWNzAyhnaaCdmW7OXZc5881
不属于会话 582da1d9-bdaa-4547-b056-ce514e9106cf 的 Agent，可能属于深度研究或其他 Agent

二、根因分析
1. chat agent 通过 task 工具 spawn 子 agent（如 web-researcher）
2. 子 agent 执行到需审批的工具时，ApprovalMiddleware 通过 interrupt() 冒泡到父 graph
3. chat stream loop（loop.py）捕获 interrupt，调用 request_approval_async(source="chat")
   → source="chat" 是正确的：子 agent 属于 chat session，不应改为 deep_research
4. approval_gateway 根据 source="chat" 正确路由到 ChatApprovalResume
5. ChatApprovalResume 调用 aget_state(thread_config) 校验 interrupt 归属
6. **根因**：子 agent 的 checkpoint 存储在与主 agent 不同的 checkpoint_ns（namespace）下，
   aget_state 默认只查主 namespace，找不到子 agent 的 interrupt
7. 校验失败 → 返回错误

三、修复方案（非补丁式根因修复）

修复 1：approval_parser.py（_build_approval_entry 函数）
- 透传子 agent 嵌套层级字段：parent_tool_call_id / depth / agent_name / agent_path
- ApprovalMiddleware 在审批请求中已注入这些字段（depth>0=子 agent），
  但 approval_parser 未透传到 approval_data，导致 Approval.extra 缺失这些字段
- approval_service._merge_passthrough_fields 已注册 EXTRA_PASSTHROUGH_FIELDS
  包含这些字段，只需 approval_data 顶层携带即可自动透传
- 影响文件：Django_xm/common/approval_parser.py

修复 2：views_chat.py（_stream_chat_resume_generator 函数）
- 读取 approval_extra.depth，若 depth > 0（子 agent interrupt），
  跳过主 agent checkpoint namespace 的 aget_state 归属校验
- 子 agent 与主 agent 共享 thread_id，LangGraph 通过 Command(resume=...)
  的 interrupt_id 自动路由到正确 checkpoint_ns，无需手动查 namespace
- 主 agent interrupt（depth=0 或无 depth 字段）保留原有校验逻辑
- 影响文件：Django_xm/apps/chat/views_chat.py

四、设计说明
为何不将 loop.py 中的 source 改为动态提取？
- 子 agent 的执行上下文与主 chat agent 共享同一个 checkpointer 和 thread_id
- 子 agent 的 interrupt 从 graph 冒泡到 chat stream loop，本质上是 chat session 的审批
- approval_gateway 按 source 路由：source="chat" → ChatApprovalResume（正确）
- 若改为 source="deep_research" → DeepResearchApprovalResume → Celery 任务恢复（错误！）
- Celery 恢复走完全不同的路径（独立的 agent 实例、独立的 checkpointer thread_id）
- 正确的修复是让 ChatApprovalResume 识别子 agent interrupt，而非改 source

### 【根因 P3-R1】致命：前端 handleSessionEvent 只读 payload.sessionId，后端 session_id 在事件顶层 → 所有 WebSocket 事件被静默丢弃
- 文件：frontend/langchain-vue/src/stores/sync/handleSessionEvent.js L85 / L102-105
- 证据链：
  1. 后端 _publish_to_session_async（realtime_events.py L192-197）构造 event：
     {type, timestamp, payload, session_id, seq}——session_id 在事件顶层（与 payload 平级），payload 内部无 session_id
  2. 后端 publish_tool_call / publish_approval 的 payload 均无 session_id（realtime_sync.py L167-174 / L296-304）
  3. 前端 handleRealtimeEvent（sync.js L399）用 `payload.sessionId || event.sessionId` 正确路由到 handleSessionEvent
  4. 但 handleSessionEvent L85 `const sessionId = event.payload?.sessionId`（无 event.sessionId fallback）
     → 解析为 undefined → `if (!sessionId) return` 静默丢弃（无任何日志）
  5. applySessionEvent 的 _getSessionId（L102-105）同样只读 payload.sessionId
- 黑盒验证（b1 页面注入模拟 tool_call_completed 事件，session_id 在顶层）：
  handleRealtimeEvent 无异常返回，但 toolCallsMap 未新增条目 → 事件确实被丢弃
- 影响：
  - 所有 WebSocket 实时事件（tool_call_*/approval_*/message_updated/stream_*）在任何浏览器均不处理
  - 触发浏览器靠 SSE 流正常；非触发浏览器只靠 SnapshotSync 快照恢复（content/approval 可恢复，
    但 tool_calls 的 status/result 快照缺失（P3-31）→ 工具状态无法恢复）
  - 解释 P3-30/P3-33（非触发浏览器工具完成状态不同步）、replay 后 count=0（重载后无事件处理日志）
  - 实时同步核心层缺陷，影响聊天/深度研究/学习工作流/聊天深度研究模式所有模块
- 修复方案：handleSessionEvent L85 与 _getSessionId 改为 `event.payload?.sessionId || event.sessionId`
