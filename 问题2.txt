## 根因分析

### 证据汇总
1. **数据库**：tool_calls 正确持久化，approval.state=pending ✓
2. **Redis**：**完全为空（0 keys）** ❌ — replay 始终返回 count=0
3. **实时推送**（未刷新浏览器）：完美同步 ✓ — Page 0/2/3 所有事件实时更新
4. **刷新后浏览器**（Page 1）：
   - 刷新时 replay count=0（Redis 无事件可回放）
   - 仅靠 API snapshot 恢复数据
   - snapshot 返回刷新时的数据库快照（此时流正在中断中，只有 2 个旧工具）
   - 后续流推进的 message_updated 事件通过 Redis Pub/Sub 瞬态发布，**不持久化**
   - 刷新后的浏览器通过 WebSocket 连接，但因 replay 无事件，错过了这些瞬态 Pub/Sub 消息
   - 直到流结束后，API snapshot 更新到最终状态

### 根本原因
Redis Pub/Sub 是瞬态的（fire-and-forget），事件不持久化。WebSocket replay 依赖 Redis 持久化 keys 来补发历史事件。当 Redis 无持久化 key 时，刷新后的浏览器只能：
1. 从 API snapshot 获取初始数据（时点快照，可能已过时）
2. 后续流推进的更新通过 Redis Pub/Sub 发布，但刷新后的浏览器错过了之前的订阅

### 正确修复方向
**不是**在"approval_pending 事件顺序"或"streamState 转换"上打补丁，而是：
1. 后端在发布实时事件时，同时将事件持久化到 Redis（如 list 结构，按 session_id 组织）
2. 前端刷新后通过 replay 获取所有历史事件（包括 approval_pending、tool_call_waiting、message_updated 等）
3. 前端按事件顺序还原完整状态（包括中间态如"等待中"、"等待其他审批"）

上述第 117 行、第 130 行声称"Redis 完全为空（0 keys）"，以及第 140-148 行基于该前提的

   自然返回 0 条（因为后端 seq 从 37 开始递增，但前端 lastSeq=32 是旧值，
   查询条件 `seq > last_seq` 在某些场景下未能匹配到新事件，并非 Redis 为空）。

因此"Redis 为空"是误判，**不是**本次问题的根因。Redis 持久化机制本身工作正常。

### 真正根因（已被日志证据确认）

1. **【主根因 Z1】初始加载 API 不注入 approval 状态**

   导致刷新后 tool_calls 中 approval 字段为空 → 审批按钮消失。

   返回 0，导致空 approval 无法合并 → 快照中有 approval 数据但合并被跳过。
   修复：Task 5-6 修正 `_approvalStatePriority` 空 approval 返回 -1，
   `_reconcileApprovals` / `_reconcileToolCalls` 合并 approval 字段。

3. **【根因 Z2/Z3】`timeout_approval` 绕过 `_persist_and_broadcast`**
   `timeout_approval` 未同步 TIMEOUT 终态到 ChatMessage → 超时后刷新状态丢失。
   修复：Task 4 补充 TIMEOUT 终态同步到 ChatMessage。

❌ 严重问题：刷新后浏览器(P24)审批中间状态未同步
   - 触发浏览器点击确认后，Tool状态从'待审批'变为'等待其他审批'
   - 刷新浏览器仍显示'待审批'，确认执行按钮仍可点击
   - 这意味着刷新后的WebSocket连接未能接收到审批状态变更的实时事件
   - 最终状态（已完成/已确认）能同步，但中间态（等待其他审批）丢失

⚠️ UI差异：刷新后浏览器工具状态文字不同
   - 未刷新浏览器显示'等待中'，刷新后显示'待执行'
   - 刷新后缺少'全部确认'按钮和详细描述文字

根因分析：
1. 审批中间状态事件可能未通过WebSocket推送到刷新后重新连接的客户端
2. 或者刷新后WebSocket重连时只回放（replay）了历史事件，但中间态事件在replay中被遗漏
3. 也可能是前端在处理replay事件时忽略了中间态审批事件（只处理终态）
4. '待执行'vs'等待中'的差异可能是API snapshot与实时事件对状态字段取值不同导致
