# 04 内存管理与淘汰策略

> Redis 全内存存储，依赖 jemalloc 分配器、8 种淘汰策略、近似 LRU/LFU 算法与碎片整理保证内存可控，理解 used_memory vs used_memory_rss 是排查内存问题的关键。

## 零基础前置认知

**这篇在讲什么**：Redis 的所有数据都住在内存里，所以**内存管理 = 花最少的空间 + 放得下就淘汰谁**。本篇讲四件事：**内存账本怎么看**（used_memory vs RSS、碎片率）、**满了之后淘汰谁**（8 种策略、近似 LRU/LFU 哪个适合你）、**碎片怎么清**（activedefrag）、**怎么自查**（MEMORY 命令族）。读完你能配出一个 `maxmemory + 淘汰策略` 组合，并解释"为什么 RSS 比 used_memory 大两倍"这类线上疑问。*生产 maxmemory/碎片整理配置在篇末与 99 附录可查，本篇以原理和命令为主。*

> 辅助类比：把内存管理想成"宿舍储物柜管理"——**jemalloc** 是"按物品尺寸分格子的储物架"（8B/16B/32B 一格，放 10B 的占 16B 格，剩 6B 空隙=碎片）；**used_memory** 是"你实际用了多少格子"、**RSS** 是"宿管统计给你划了多少区域"（含空格子/碎片）；**淘汰策略**是"柜子满了，谁先被清走"——LRU 看"谁最久没碰"、LFU 看"谁被碰得最少"，都是"抽样看一眼"而非"翻遍全柜"（近似）；**碎片整理**是"管理员挑个空隙把东西挪紧"（不打断你使用）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| jemalloc | Redis 默认内存分配器（按大小分级分配） | 替代 glibc malloc，碎片率低约 30%；tcmalloc 为备选 |
| used_memory / used_memory_rss | Redis 分配器视角 / 操作系统视角的内存 | 差值即碎片；RSS<used 通常意味着发生 SWAP（严重） |
| 碎片率（mem_fragmentation_ratio） | used_memory_rss / used_memory | 1.0-1.5 正常，>1.5 建议整理，>2.0 严重 |
| 淘汰策略（eviction policy） | maxmemory 满后选择删除哪些 key 的规则 | `noeviction` 拒绝写入；`*-lru/*-lfu/*-random/ttl` 逐出 |
| 近似 LRU | 随机采样 N 个 key 淘汰最久未用的（非全量） | `maxmemory-samples`（默认 5）控制采样，越大越接近理论 LRU |
| LFU | 按访问频率淘汰（24bit 拆分衰减时间+计数） | 比 LRU 更能反映"热点稳定"；`lfu-log-factor/decay-time` 调灵敏 |
| activedefrag | 4.0+ 主动碎片整理（后台渐进式挪动内存） | 由碎片率阈值（10/100）与 CPU 占比（1/25）驱动 |
| 对象共享 | 0-9999 整数复用预缓存对象 | 计数型 String 节省内存；共享对象不记录独立访问时间 |

> 区分/注意：**"内存碎片" ≠ "内存泄漏"**——碎片是"空格子"（总占用高但能回收复用），泄漏是"格子永远不还"；`INFO memory` 能同时看到两者迹象（碎片率高走 activedefrag，泄漏高走 MEMORY DOCTOR 排查）。**近似 LRU/LFU 都要采样**，采样数是墙（samples=5 约八成接近理论 LRU），别追求"绝对精确"——Redis 单线程，代价是 CPU。**淘汰策略只对 `maxmemory>0` 生效**：不设 maxmemory 则不淘汰（进程内存涨到被 OS OOM killer 干掉），生产必须设限。

## 一、内存分配器

### 1.1 分配器选择

Redis 默认使用 jemalloc，相比 glibc malloc 减少内存碎片率约 30%。

| 分配器 | 特点 | 适用 |
|--------|------|------|
| jemalloc | 默认，碎片率最低 | 生产环境 |
| tcmalloc | Google 实现，性能稳定 | 备选 |
| glibc malloc | 系统默认，碎片较高 | 不推荐 |

jemalloc 按大小分级分配：

```
Small (< 8KB)：8B / 16B / 32B / 48B / 64B / 80B / 96B / ... / 4KB
Large (8KB - 4MB)：按页对齐
Huge (> 4MB)：按大页对齐

请求 10B 实际分配 16B → 产生 6B 内部碎片
```

### 1.2 RedisObject 内存开销

```
RedisObject 结构（共 16 字节）：
┌─────────────────────────────────────────────────────────┐
│ type(4bit) │ encoding(4bit) │ lru(24bit) │ refcount(4B) │ ptr(8B) │
└─────────────────────────────────────────────────────────┘

内存开销示例：
SET name "张三"
实际内存 = RedisObject(16B) + SDS头部(3B) + "张三"(6B UTF-8) = 25B
加上 key 的 RedisObject + SDS = 约 50B+
```

## 二、内存关键指标

### 2.1 指标说明

| 指标 | 含义 | 关注点 |
|------|------|--------|
| `used_memory` | Redis 分配器分配的内存总量 | 实际数据占用 |
| `used_memory_rss` | 操作系统分配给 Redis 的内存 | 包含碎片 |
| `used_memory_peak` | 内存使用峰值 | 容量规划依据 |
| `mem_fragmentation_ratio` | used_memory_rss / used_memory | >1.5 碎片严重 |
| `maxmemory` | 最大内存限制 | 超出后触发淘汰策略 |
| `mem_allocator` | 内存分配器 | jemalloc / tcmalloc / libc |


### 2.3 碎片率判断

```
碎片率判断标准：
< 1.0    ：Redis 使用了超过操作系统分配的内存（SWAP，严重问题）
1.0-1.5  ：正常范围
1.5-2.0  ：碎片较多，建议开启自动整理
> 2.0    ：碎片严重，需要立即处理
```

## 三、内存淘汰策略

### 3.1 8 种淘汰策略

Redis 内存达到 `maxmemory` 限制时触发淘汰，共 8 种策略：

| 策略 | 范围 | 算法 | 适用场景 |
|------|------|------|----------|
| `noeviction` | 不淘汰 | — | 数据不能丢失，写入报错 |
| `allkeys-lru` | 所有 key | LRU | 通用缓存 |
| `allkeys-lfu` | 所有 key | LFU | 热点数据缓存 |
| `allkeys-random` | 所有 key | 随机 | 无访问热点 |
| `volatile-lru` | 设过期 key | LRU | 混合使用（部分持久化） |
| `volatile-lfu` | 设过期 key | LFU | 混合使用 |
| `volatile-random` | 设过期 key | 随机 | 混合使用 |
| `volatile-ttl` | 设过期 key | TTL 最短 | 业务有明确 TTL |

### 3.2 配置命令

```bash
# 设置最大内存
CONFIG SET maxmemory 2gb

# 设置内存淘汰策略
CONFIG SET maxmemory-policy allkeys-lru

# 查看内存淘汰策略
CONFIG GET maxmemory-policy

# 设置 LRU/LFU 采样数（默认 5，越大越精确但 CPU 开销大）
CONFIG SET maxmemory-samples 10

# 查看淘汰统计
INFO stats | grep evicted
```

### 3.3 选型决策

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| 纯缓存 | `allkeys-lru` 或 `allkeys-lfu` | 全部可淘汰，热点明显 |
| 缓存 + 持久化数据 | `volatile-lru` | 仅淘汰有过期时间的 key |
| 数据不能丢失 | `noeviction` | 写入报错需应用降级 |
| 热点变化快 | `allkeys-lru` | 最近访问更有参考价值 |
| 热点稳定 | `allkeys-lfu` | 频率更能反映热点 |
| 业务有明确 TTL | `volatile-ttl` | 按剩余生存时间淘汰 |

## 四、LRU 实现原理（近似 LRU）

### 4.1 近似 LRU 算法

Redis 的 LRU 并非严格 LRU，而是**近似 LRU**——随机采样 N 个 Key，淘汰其中最久未使用的。

```
LRU 淘汰流程：
┌─────────────────────────────────────────────────┐
│ 1. 内存达到 maxmemory 阈值                      │
│ 2. 随机采样 N 个 Key（maxmemory-samples，默认 5）│
│ 3. 淘汰其中最久未访问的 Key                     │
│ 4. 重复直到内存低于阈值                         │
└─────────────────────────────────────────────────┘

采样数与精确度关系：
samples=5  → 接近理论 LRU 的 80% 精确度
samples=10 → 接近理论 LRU 的 90% 精确度
samples=20 → 接近理论 LRU 的 95% 精确度（CPU 开销增大）
```

### 4.2 LRU 时钟

每个 RedisObject 的 24bit lru 字段存储最后一次访问时间戳（精度秒，按 `LRU_CLOCK_RESOLUTION` 通常 1 秒）：

```bash
# 查看 key 的空闲时间（秒）
OBJECT IDLETIME key

# 查看 key 的访问频率（LFU 模式下）
OBJECT FREQ key
```

## 五、LFU 实现原理（Redis 4.0+）

### 5.1 LFU 计数器机制

LFU 基于访问频率淘汰，比 LRU 更适合访问模式变化的场景。

```
LFU 计数器机制：
每个 Key 的 RedisObject 中有 24bit 用于 LFU：
┌──────────────┬───────────────────────┐
│ 高 16bit：衰减时间 │ 低 8bit：访问计数器  │
└──────────────┴───────────────────────┘

访问计数器增长（对数增长：计数越大，再增长越难）：
- 计数器最大 255
- 每访问一次，以"依赖当前计数的概率" +1：计数低时接近必加，计数高时概率大幅下降
- `lfu-log-factor`（默认 10）控制"涨到高计数有多难"——因子越大，普通 key 越难刷到高计数，避免短时热点虚高
- 因此区分"长周期高频"（计数高）与"短期突发"（计数上不去）

计数器衰减：
- 每 lfu-decay-time 分钟（默认 1 分钟）访问计数减 1
- 防止历史高频 Key 永远不被淘汰（给新热点让位）
```

### 5.2 LFU 配置

```bash
# 查看 LFU 配置
CONFIG GET lfu-log-factor
CONFIG GET lfu-decay-time

# 调整 LFU 参数
CONFIG SET lfu-log-factor 10
CONFIG SET lfu-decay-time 1

# 设置 LFU 淘汰策略
CONFIG SET maxmemory-policy allkeys-lfu
```

### 5.3 LFU 计数器增长曲线

| 当前计数 | lfu-log-factor=10 时增长概率 |
|----------|------------------------------|
| 0 | 100% |
| 1 | 99.6% |
| 10 | 96.1% |
| 50 | 82.5% |
| 100 | 67.3% |
| 200 | 44.7% |
| 255 | 36.8% |

## 六、LRU vs LFU 选型

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| 访问模式稳定，热点明显 | `allkeys-lfu` | 频率更能反映热点 |
| 访问模式变化快 | `allkeys-lru` | 最近访问更有参考价值 |
| 有冷热数据区分 | `volatile-lfu` | 只淘汰有过期时间的冷数据 |
| 短期突发访问 | `allkeys-lru` | 防止历史高频永远占用 |

## 七、内存碎片

### 7.1 碎片产生原因

```
内存碎片产生原因：
1. 操作系统分配策略
   ├── jemalloc 按大小分级分配（8B/16B/32B/.../4KB/...）
   └── 请求 10B 实际分配 16B，产生 6B 碎片

2. 键值对频繁修改和删除
   ├── 删除 key 后释放的空间可能不连续
   └── 新分配的 key 大小与释放的空间不匹配

3. 不同编码转换
   ├── Hash 从 listpack 转为 hashtable
   └── 旧内存释放，新内存分配，产生间隙

4. fork 子进程
   └── COW 期间父进程修改数据产生新页
```

### 7.2 主动碎片整理（4.0+）

```bash
# 查看碎片率
INFO memory | grep mem_fragmentation_ratio

# 开启自动碎片整理（Redis 4.0+）
CONFIG SET activedefrag yes

# 查看碎片整理配置
CONFIG GET activedefrag
CONFIG GET active-defrag-threshold-lower    # 触发整理的碎片率下限（默认 10）
CONFIG GET active-defrag-threshold-upper    # 强制整理的碎片率上限（默认 100）
CONFIG GET active-defrag-cycle-min          # 整理最小 CPU 占比（默认 1）
CONFIG GET active-defrag-cycle-max          # 整理最大 CPU 占比（默认 25）
CONFIG GET active-defrag-max-scan-fields    # 单次扫描最大字段数（默认 1000）
```

### 7.3 碎片处理方案

| 方案 | 命令 | 适用 |
|------|------|------|
| 自动整理 | `CONFIG SET activedefrag yes` | 4.0+ 长期运行 |
| 重启整理 | `SHUTDOWN` + 重启加载 RDB | 碎片极严重时 |
| 内存预分配 | 合理设置 maxmemory | 预防 |

## 八、对象共享

### 8.1 整数共享机制

Redis 预缓存 0-9999 的整数对象，当值是这个范围内的整数时，RedisObject 的 ptr 直接指向共享对象，不需要额外分配 SDS，节省内存。

```
共享对象机制：
┌─────────────────────────────────────┐
│  共享对象池（0-9999）                │
│  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐  │
│  │0 │1 │2 │3 │4 │5 │..│..│..│9999│ │
│  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘  │
└─────────────────────────────────────┘
       ▲
       │
SET k1 5  → ptr 直接指向共享对象 5（refcount++）
SET k2 5  → ptr 也指向共享对象 5（refcount++）
DEL k1    → refcount--，不释放对象
```

### 8.2 配置共享对象数量

```bash
# 查看共享对象数量上限
CONFIG GET maxmemory-policy

# 通过源码宏定义（不可配置）
# OBJ_SHARED_INTEGERS = 10000
```

> **注意**：共享对象仅适用于整数 String 类型，且仅在没有 LRU/LFU 跟踪需求时（共享对象不能记录独立的访问时间）。

### 8.3 zerocopy 与共享对象对比

| 机制 | 说明 | 适用 |
|------|------|------|
| 整数共享 | 0-9999 整数复用对象 | 小整数 String |
| embstr 紧凑存储 | RedisObject + SDS 一次分配 | ≤44B String |
| listpack 连续内存 | 元素紧凑排列 | 小数据量 Hash/List/Set/ZSet |
| zerocopy（部分模块） | 直接复用客户端缓冲 | RedisJSON 等模块场景 |

## 十、内存监控实战

### 10.1 Python 监控代码

```python
import redis
import json

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class RedisMemoryMonitor:
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client

    def get_metrics(self) -> dict:
        info = self.redis.info("memory")
        return {
            "used_memory_mb": round(info.get("used_memory", 0) / 1024 / 1024, 2),
            "used_memory_rss_mb": round(info.get("used_memory_rss", 0) / 1024 / 1024, 2),
            "used_memory_peak_mb": round(info.get("used_memory_peak", 0) / 1024 / 1024, 2),
            "maxmemory_mb": round(info.get("maxmemory", 0) / 1024 / 1024, 2),
            "fragmentation_ratio": info.get("mem_fragmentation_ratio", 1.0),
            "allocator": info.get("mem_allocator", "unknown"),
            "usage_percent": self._calc_usage(info),
        }

    def _calc_usage(self, info: dict) -> str:
        used = info.get("used_memory", 0)
        maxmem = info.get("maxmemory", 0)
        if maxmem == 0:
            return "N/A (no limit)"
        return f"{used / maxmem * 100:.1f}%"

    def check_health(self) -> dict:
        metrics = self.get_metrics()
        alerts = []
        if metrics["fragmentation_ratio"] > 1.5:
            alerts.append(f"内存碎片率过高: {metrics['fragmentation_ratio']}")
        if metrics["fragmentation_ratio"] < 1.0:
            alerts.append("正在使用 Swap，性能严重下降")
        usage = metrics["usage_percent"]
        if "N/A" not in usage and float(usage.rstrip('%')) > 80:
            alerts.append(f"内存使用率过高: {usage}")
        return {"metrics": metrics, "alerts": alerts}

monitor = RedisMemoryMonitor(r)
health = monitor.check_health()
print(json.dumps(health, indent=2, ensure_ascii=False))
```

### 10.2 告警阈值建议

| 类别 | 指标 | 告警阈值 |
|------|------|----------|
| 内存 | used_memory / maxmemory | >80% 警告，>90% 严重 |
| 内存 | mem_fragmentation_ratio | >1.5 警告，>2.0 严重 |
| 内存 | mem_fragmentation_ratio | <1.0 严重（SWAP） |
| 淘汰 | evicted_keys | >0 需关注 |
| 客户端 | connected_clients / maxclients | >80% |

## 十一、生产 maxmemory 与淘汰策略选型表

| 业务场景 | maxmemory | 淘汰策略 | samples | 备注 |
|----------|-----------|----------|---------|------|
| 纯缓存（无持久化） | 物理内存 70% | allkeys-lru | 10 | 热点变化快 |
| 纯缓存（热点稳定） | 物理内存 70% | allkeys-lfu | 10 | 热点明显 |
| 缓存 + 持久化 | 物理内存 60% | volatile-lru | 10 | 持久化 key 不淘汰 |
| Session 缓存 | 物理内存 60% | volatile-lru | 5 | Session 有 TTL |
| 计数器/统计 | 物理内存 50% | noeviction | — | 数据不能丢，应用降级 |
| 排行榜 | 物理内存 60% | noeviction | — | 数据重要，需提前扩容 |
| 消息队列（Stream） | 物理内存 60% | noeviction | — | 配合 MAXLEN 裁剪 |

### 11.1 生产 redis.conf 内存片段

```conf
# ============== 内存配置（生产推荐） ==============

# 最大内存（建议为物理内存的 60-70%）
maxmemory 4gb

# 淘汰策略（缓存场景）
maxmemory-policy allkeys-lru

# LRU/LFU 采样数（10 较平衡）
maxmemory-samples 10

# 主动碎片整理（4.0+）
activedefrag yes
active-defrag-threshold-lower 10
active-defrag-threshold-upper 100
active-defrag-cycle-min 1
active-defrag-cycle-max 25
active-defrag-max-scan-fields 1000

# LFU 配置（若使用 LFU）
lfu-log-factor 10
lfu-decay-time 1
```

### 11.2 内存优化实战建议

| 优化方向 | 具体措施 | 预期收益 |
|----------|---------|---------|
| 编码优化 | 控制 Hash/Set/ZSet 元素数，保持在 listpack 编码 | 减少 50%+ 内存 |
| Key 命名 | 使用简短前缀（如 `u:1` 代替 `user:1`） | 海量 key 节省 MB 级 |
| 过期策略 | 不用的 key 及时设置 TTL 或删除 | 释放占用 |
| 大 Key 拆分 | 大 Hash 按范围分片，大 List 拆短 | 避免阻塞与碎片 |
| 避免不必要持久化 | 纯缓存场景关闭 AOF | 减少 fork 内存放大 |
| 共享对象利用 | 计数器值保持在 0-9999 | 复用共享对象 |
| ziplist/listpack 阈值调优 | 适度调大 `*-max-listpack-entries` | 提升紧凑编码覆盖率 |

```bash
# 找出内存占用最大的 key
redis-cli --memkeys --memkeys-samples 1000

# 找出可设置 TTL 但未设置的 key
redis-cli --bigkeys

# 扫描未设置过期的 key
redis-cli SCAN 0 MATCH "*" COUNT 1000 | xargs -I {} redis-cli TTL {}

# 估算 key 内存占用并排序
for key in $(redis-cli --scan --pattern "user:*" | head -100); do
  size=$(redis-cli MEMORY USAGE $key)
  echo "$size $key"
done | sort -rn | head -10
```

## 小思考题帮你巩固

1. **`used_memory > used_memory_rss` 意味着什么？为什么会发生？**（提示：RSS<used 通常表示内存被换出到磁盘（SWAP），见 2.3。）
2. **`volatile-lru` 与 `allkeys-lru` 的关键差异是什么？缓存+持久化混合场景该选哪个？**（提示：前者只淘汰带 TTL 的 key，后者全库淘汰，见 3.1/3.3。）
3. **为什么说 Redis 的 LRU 是"近似"的？把 `maxmemory-samples` 调到很大能 100% 精确吗？**（提示：随机采样 N 个而非全量；调大更接近但有 CPU 代价，见 4.1。）
4. **LFU 的 `lfu-log-factor` 越大，计数器"涨得越快还是越慢"？为什么这样设计？**（提示：因子越大越难刷到高计数，避免突发热点虚高，见 5.1/5.3。）
5. **`activedefrag` 是怎么做到"整理碎片不阻塞业务"的？**（提示：渐进式、受 cycle-min/max（CPU 占比）限制，见 7.2。）
6. **Redis 0-9999 整数共享对象为什么能省内存？它有什么使用限制？**（提示：多个 key 的 ptr 指向同一对象；共享对象不记录独立访问时间，见八。）

<details>
<summary>参考答案（点击展开）</summary>

1. 表示 OS 视角的内存（RSS）小于分配器分配量（used_memory）——通常意味着部分内存被换出（SWAP），磁盘 IO 会让延迟暴涨，是严重信号（<1.0）。可能诱因：maxmemory 设得过高、内存压力大；先看 `INFO memory` 确认该比例，再排查是否有换页。
2. `volatile-lru` 只对**设了 TTL 的 key** 做 LRU 淘汰，`allkeys-lru` 对所有 key 淘汰。缓存+持久化混合（有些 key 要在 AOF/RDB 里留底）时选 `volatile-lru`，把"可丢的缓存"都设上过期时间，持久的 key 不带 TTL 就不会被淘汰。
3. 因为它只在每次淘汰时**随机采样 `maxmemory-samples`（默认 5）个 key**，从中挑最久未用的淘汰，而不是遍历全局。samples 越大越接近理论 LRU（10→约九成），但要付出 CPU（单线程），一般不超 10。
4. 越慢。`lfu-log-factor` 越大，计数要升得越高才困难（每个计数档需要更多真实访问），防止"一次刷屏就虚高"；反过来因子太小会让短期突发把计数冲满、长期真实热点反而被误杀。默认 10，热点稳定场景可调小，易变场景调大。
5. activedefrag 在后台**渐进式**地"挑空隙搬数据"，并且用 `active-defrag-cycle-min/max`（CPU 占用 1%~25%）限制每轮工作量，主线程只让出一小段来搬，所以几乎无感（碎片率在下限阈值之上才启动、上限强制）。
6. 0-9999 的整数在 Redis 里是**预建共享对象**，多个 key 的 RedisObject.ptr 指向同一个对象、只 `refcount++`，省下重复的 SDS 分配。限制：仅整数 String、且需要"每 key 独立访问时间"的计数场景不用它（共享对象没法记各自的 LRU/LFU 时间），所以共享池的值不会进 LRU/LFU 采样淘汰比较。

</details>

## 最佳实践与常见陷阱

> 本节的每条都来自 Redis 内存治理实战，按"现象 → 原因 → 处置"组织。

| # | 陷阱 | 现象 | 原因 | 处置 |
|---|------|------|------|------|
| 1 | 内存满后写入报 OOM 错误 | `-OOM command not allowed when used memory > 'maxmemory'` | 策略是 `noeviction` 且达到上限 | 缓存场景改 `allkeys-lru/lfu`；数据不可丢场景应用做降级/扩容 |
| 2 | 只设 `maxmemory` 不设策略 | 满后写入全部失败（默认 noeviction） | 生产默认没改策略 | 显式 `maxmemory-policy`（缓存用 lru/lfu），见 3.1 |
| 3 | RSS 涨到两倍 used_memory | 碎片率 >2、进程内存超预期 | jemalloc 碎片 + 大 key 频繁增删；未开 activedefrag | `CONFIG SET activedefrag yes`；大 key 拆分（见 11 篇） |
| 4 | LFU 下历史热点永不淘汰 | 新热点进不来 | `lfu-decay-time` 太大/未设置衰减 | 调小 decay-time；或换 allkeys-lru（访问模式变化快） |
| 5 | `MEMORY USAGE` 对大结构卡主线程 | 大 Hash/List 统计耗时数秒 | 默认 SAMPLES=5 也需遍历采样 | 大结构用 `SAMPLES 0` 前评估，或用 `--bigkeys` 在低峰执行 |
| 6 | 以为关闭 AOF 很省内存 | 内存没降反升 | 关闭 AOF 不回收内存；内存靠淘汰/TTL | 内存治理优先"删无用 key + 紧凑编码 + maxmemory"，持久化开关不直接影响 used_memory |
| 7 | 服务启动即内存占用偏高 | 启动就占几百 MB | jemalloc 预分配 + 加载 RDB 的峰值 | 属正常（`INFO memory` 的 startup.allocated），按"峰值规划容量"而非启动值 |

> **一句话总结**：Redis 内存治理三板斧——**设限**（maxmemory + 合适策略，推荐 allkeys-lfu 热点稳定/allkeys-lru 易变）、**看账**（used_memory/RSS/碎片率 + MEMORY USAGE 定位大头）、**理账**（紧凑编码优先、大 key 拆分、activedefrag 兜底）；记住"碎片≠泄漏、RSS<used=SWAP、采样=近似"，就能把内存问题从"玄学"变成"菜单"。
