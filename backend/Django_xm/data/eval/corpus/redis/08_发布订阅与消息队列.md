# 08 发布订阅与消息队列

> Redis 通过 Pub/Sub 提供轻量实时广播，通过 Stream 提供持久化消费者组模型，配合 ZSet 实现延迟队列，覆盖中小规模消息场景。

## 零基础前置认知

**这篇在讲什么**：Redis 有两套"通知人"的机制，别混着用——**Pub/Sub** 是"广播喇叭"（发布消息立刻推给所有在线订阅者，**不落盘、离线就丢**，只适合实时通知）；**Stream** 是"带记账本的消息队列"（消息落盘、可分组消费、ACK 确认、超时重投、死信，对标 Kafka 但轻量）；**ZSet 延迟队列**是"到点才提醒的闹钟本"。读完你能用 Stream 搭出**可靠消费闭环**（XREADGROUP → 处理 → XACK，超时 XAUTOCLAIM，超重试进死信），并做对选型。配套可运行代码见 [codes/](./codes/)（pubsub_demo.py、stream_mq.py，真实运行通过）。

> 辅助类比：**Pub/Sub** 是"店门口的广播喇叭"——喊一声所有在场的人听见，**人不在（离线）就错过了、也没人补发**；**Stream** 是"前台登记簿 + 分诊叫号"——每条消息先写进登记簿（落盘），护士（消费者组）按顺序叫号处理，处理完签收（XACK）；签收超时的会**标记未结（Pending）**由别人再叫（XAUTOCLAIM）；叫了 N 次没人能处理就进"疑难件"（死信队列）。**延迟队列**是"定时闹钟盒"——每个任务设一个到点时刻（score=时间戳），到点才取出执行。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| Pub/Sub | 发布/订阅实时广播（频道 + 模式订阅） | 不持久化、无 ACK；离线即丢，只做实时通知 |
| Stream | Redis 5.0 消息流类型（Radix Tree + listpack 节点） | 持久化、按 ID 有序、可回溯；对标"轻量 Kafka" |
| 消息 ID | `<毫秒时间戳>-<序列号>`，全局递增 | XADD 自动生成；是排序/回溯/XACK 的依据 |
| 消费者组（Group） | 组内消息只投递一次、独立游标互不干扰 | 与 Kafka 消费组类似；`$`=只消费新消息、`0`=从头 |
| Pending（PEL） | 已投递未 ACK 的消息清单 | XACK 后移除；是"至少一次投递"与超时重投的账本 |
| XAUTOCLAIM | 自动认领超时（min_idle_time）未 ACK 消息 | 崩溃/慢消费者恢复的手段；配合重试次数判断死信 |
| 死信队列 | 超最大重试次数转出的消息流 | 惯例关键 `stream:dead`；避免无限重投 |
| 延迟队列 | ZSet 实现：score=执行时间戳，到期轮询 | 用 Lua 保证"取到期任务+删除"原子 |

> 区分/注意：**Pub/Sub 不是消息队列**——它不持久化、无 ACK、消息即发即弃，Kafka/RabbitMQ/Stream 的"可靠投递"它一项都没有；生产"可靠消息"一律 Stream。**Stream 消费者组是"至少一次投递"（At-Least-Once）**：消息可能因重投被消费多次，业务处理必须**幂等**。**延迟队列不是 Stream**：Stream 不支持"定时到期"语义，延迟任务惯例用 ZSet（score=执行时间戳）。

## 一、Pub/Sub 发布订阅

### 1.1 Pub/Sub 模型

Pub/Sub 是 Redis 最轻量的消息广播机制，发布者将消息发送到频道，所有订阅该频道的客户端实时收到。

```
发布订阅模型：
┌──────────┐                    ┌──────────┐
│ 发布者    │ ── PUBLISH ──────► │ 频道      │
└──────────┘                    └────┬─────┘
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
              ┌──────────┐    ┌──────────┐    ┌──────────┐
              │ 订阅者1   │    │ 订阅者2   │    │ 订阅者3   │
              └──────────┘    └──────────┘    └──────────┘

Redis 内部数据结构：
1. pubsub_channels 字典
   ├── key：频道名（如 "channel1"）
   └── value：订阅该频道的客户端链表

2. pubsub_patterns 链表
   ├── 每个节点包含：模式（如 "news.*"） + 客户端
   └── glob 风格通配符

PUBLISH 执行流程：
1. 在 pubsub_channels 查找频道 → 遍历客户端链表发送
2. 遍历 pubsub_patterns 匹配模式 → 向匹配客户端发送
```

### 1.2 基础命令

```bash
# 终端1：订阅频道
SUBSCRIBE channel1 channel2

# 终端2：发布消息
PUBLISH channel1 "Hello Redis"

# 终端1 收到消息：
# 1) "message"
# 2) "channel1"
# 3) "Hello Redis"

# 取消订阅
UNSUBSCRIBE channel1

# 查看活跃频道
PUBSUB CHANNELS
PUBSUB CHANNELS news.*

# 查看频道订阅数
PUBSUB NUMSUB channel1 channel2

# 查看模式订阅数
PUBSUB NUMPAT
```

### 1.3 模式订阅（PSUBSCRIBE）

```bash
# 订阅所有以 news 开头的频道
PSUBSCRIBE news.*

# 发布到具体频道
PUBLISH news.sports "体育新闻"
PUBLISH news.tech "科技新闻"

# 终端1 收到（注意是 pmessage 类型）：
# 1) "pmessage"
# 2) "news.*"          ← 匹配的模式
# 3) "news.sports"     ← 实际频道
# 4) "体育新闻"         ← 消息内容

# 取消模式订阅
PUNSUBSCRIBE news.*
```

### 1.4 Pub/Sub 的两大局限

| 局限 | 后果 | 解决方案 |
|------|------|----------|
| **无持久化** | 离线订阅者丢失所有消息 | 改用 Stream |
| **无消费确认** | 订阅者处理失败无法重投 | 改用 Stream 消费者组 |

> **重要提示**：Pub/Sub 消息直接推送，不写入任何数据结构，订阅者离线即丢失。生产环境可靠消息必须用 Stream。

### 1.5 Pub/Sub Python 示例

```python
import redis
import threading

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class PubSubService:
    def __init__(self):
        self.pubsub = r.pubsub()

    def publish(self, channel: str, message: str):
        r.publish(channel, message)

    def subscribe(self, channel: str, handler):
        self.pubsub.subscribe(**{channel: handler})
        thread = threading.Thread(target=self.pubsub.run_in_thread, daemon=True)
        thread.start()

def message_handler(message):
    print(f"收到消息：频道={message['channel']}, 数据={message['data']}")

service = PubSubService()
service.subscribe("notifications", message_handler)
service.publish("notifications", "系统启动完成")
```

## 二、Stream 消息队列

### 2.1 Stream 核心概念

Stream 是 Redis 5.0 引入的消息流数据类型，对标 Kafka 的消费者组模型，支持持久化、消费确认、消息回溯。

```
Stream 结构：
┌─────────────────────────────────────────────────────────┐
│  Stream (有序消息队列)                                   │
│                                                          │
│  Entry1          Entry2          Entry3                  │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐           │
│  │ID: 1630-0│   │ID: 1630-1│   │ID: 1631-0│           │
│  │field:val │   │field:val │   │field:val │           │
│  └──────────┘   └──────────┘   └──────────┘           │
│       ▲                                                │
│       │  Consumer Group A                              │
│       │  ┌──────────────────────────────────────┐     │
│       │  │ Consumer1: last_delivered_id=1630-1  │     │
│       │  │ Consumer2: last_delivered_id=1630-0  │     │
│       │  │ Pending: [未 ACK 的消息列表]          │     │
│       │  └──────────────────────────────────────┘     │
│       │                                                  │
│       │  Consumer Group B (独立消费，互不影响)          │
│       │  ┌──────────────────────────────────────┐     │
│       │  │ Consumer3: last_delivered_id=1631-0  │     │
│       │  └──────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────┘

消息 ID 格式：<毫秒时间戳>-<序列号>
  示例：1630000000000-0、1630000000000-1
  自动生成，全局递增，保证有序
```

### 2.2 基础命令

```bash
# 1. 生产消息（* 表示自动生成 ID）
XADD orders * user_id 1001 product_id 5001 amount 99.9
XADD orders * user_id 1002 product_id 5002 amount 199.9

# 2. 限制 Stream 长度（防止内存无限增长）
XADD orders MAXLEN 10000 * user_id 1003 product_id 5003 amount 299.9
# 近似裁剪（性能更好，~ 表示允许少量误差）
XADD orders MAXLEN ~ 10000 * user_id 1004 product_id 5004 amount 399.9

# 3. 查看消息数量
XLEN orders

# 4. 范围读取（- + 表示从头到尾）
XRANGE orders - +
XRANGE orders - + COUNT 2
XRANGE orders 1630000000000-0 1630000000000-5
XREVRANGE orders + - COUNT 5

# 5. 单条读取（XGET 为 Redis 8.0 新增，等价 XRANGE 单条）
XGET orders 1630000000000-0

# 6. 非阻塞读取（独立消费者，无消费组）
XREAD COUNT 10 STREAMS orders 0     # 读取 ID > 0 的消息
XREAD COUNT 10 BLOCK 5000 STREAMS orders $   # 阻塞等待新消息

# 7. 查看 Stream 信息
XINFO STREAM orders
XINFO STREAM orders FULL

# 8. 手动裁剪
XTRIM orders MAXLEN 1000
XTRIM orders MINID 1630000000000-0   # 删除 ID 小于指定值的消息

# 9. 删除消息
XDEL orders 1630000000000-0
```

### 2.3 消费者组完整流程

消费者组实现"一条消息组内只投递一次"+ "至少一次消费（At-Least-Once）"语义。

```
消息可靠消费闭环：

  生产者
    │
    │ XADD
    ▼
┌─────────┐  XREADGROUP(>)  ┌──────────┐  XACK   ┌──────────┐
│ Stream  │ ───────────────► │ 消费者    │ ──────► │ 完成确认  │
│         │                  │ 处理消息  │         │ (PEL 移除)│
└─────────┘                  └────┬─────┘         └──────────┘
     ▲                            │ 处理失败/超时
     │                            ▼
     │                       ┌──────────┐
     │  XCLAIM              │ Pending  │
     └───────────────────── │ (PEL)    │
                             └──────────┘
                                  │ 超时未 ACK
                                  ▼
                             XAUTOCLAIM / XCLAIM
                             由其他消费者重新认领
```

```bash
# 1. 创建消费者组
#    $ 表示只消费组创建后的新消息
#    0 表示从头消费所有历史消息
#    MKSTREAM 表示 Stream 不存在时自动创建
XGROUP CREATE orders order_workers $ MKSTREAM
XGROUP CREATE orders notify_group 0

# 2. 消费者读取消息（> 表示尚未投递的新消息）
XREADGROUP GROUP order_workers consumer1 COUNT 1 BLOCK 5000 STREAMS orders >

# 3. 确认消息已处理（必须 ACK，否则进入 Pending）
XACK orders order_workers 1630000000000-0

# 4. 查看 Pending 列表（已投递未确认）
XPENDING orders order_workers
# 返回：pending 数量、最小 ID、最大 ID、各消费者待处理数

# 5. 查看 Pending 详情
XPENDING orders order_workers - + 10
# 返回：message_id、consumer、idle_time、delivery_count

# 6. 转移超时消息给其他消费者（手动）
#    参数：组名、新消费者、min_idle_time(毫秒)、消息ID
XCLAIM orders order_workers consumer2 60000 1630000000000-0

# 7. 自动转移超时消息（推荐）
#    参数：组名、消费者、min_idle_time、起始 ID、COUNT
XAUTOCLAIM orders order_workers consumer2 60000 0-0 COUNT 10

# 8. 查看消费者组信息
XINFO GROUPS orders
XINFO CONSUMERS orders order_workers

# 9. 删除消费者组（需先无 Pending）
XGROUP DESTROY orders order_workers

# 10. 删除消费者
XGROUP DELCONSUMER orders order_workers consumer1
```

### 2.4 XPENDING 输出详解

```bash
XPENDING orders order_workers
# 1) (integer) 5                 ← Pending 消息总数
# 2) "1630000000000-0"           ← 最小 ID
# 3) "1630000000004-0"           ← 最大 ID
# 4) 1) 1) "consumer1"           ← consumer1 待处理数
#       2) (integer) 3
#    2) 1) "consumer2"
#       2) (integer) 2

XPENDING orders order_workers - + 10
# 1) 1) "1630000000000-0"        ← message_id
#    2) "consumer1"              ← 当前持有者
#    3) (integer) 120000          ← idle 时间（毫秒）
#    4) (integer) 3               ← 投递次数（delivery_count）
```

## 三、延迟队列（ZSet 实现）

### 3.1 延迟队列原理

利用 ZSet 的 score 存储任务执行时间戳，消费者轮询获取到期任务。

```
延迟队列工作流程：
┌──────────┐  ZADD(score=执行时间戳)  ┌──────────────────┐
│ 生产者    │ ──────────────────────► │ ZSet delay:queue │
└──────────┘                         └────────┬─────────┘
                                              │
                                              │ 消费者轮询
                                              ▼
                                     ┌──────────────────┐
                                     │ ZRANGEBYSCORE    │
                                     │ (0, now]         │ ← 获取到期任务
                                     └────────┬─────────┘
                                              │
                                              ▼
                                     ┌──────────────────┐
                                     │ 处理任务          │
                                     │ ZREM 删除已处理   │
                                     └──────────────────┘
```

### 3.2 延迟队列实现

```bash
# 1. 添加延迟任务（score 为执行时间戳）
ZADD delay:queue 1700000000 '{"task":"send_email","to":"a@b.com"}'
ZADD delay:queue 1700000060 '{"task":"cancel_order","orderId":"ORD001"}'

# 2. 消费者轮询获取到期任务
ZRANGEBYSCORE delay:queue 0 1700000000 LIMIT 0 10

# 3. 处理完成后删除（必须保证原子，用 Lua）
EVAL "
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, 10)
if #tasks == 0 then
    return {}
end
-- 注意：Lua 中操作 ZSet 必须传 member，不能直接按 score 删
for i, task in ipairs(tasks) do
    redis.call('ZREM', KEYS[1], task)
end
return tasks
" 1 delay:queue 1700000000
```

完整 Python 实现：

```python
import redis
import json
import time
import uuid

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

# Lua 脚本保证"读取+删除"原子性
POP_DELAYED_SCRIPT = """
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #tasks == 0 then
    return {}
end
for i, task in ipairs(tasks) do
    redis.call('ZREM', KEYS[1], task)
end
return tasks
"""

class DelayQueue:
    def __init__(self, redis_client: redis.Redis, queue_name: str = "delay:queue"):
        self.redis = redis_client
        self.key = queue_name
        self.sha = self.redis.script_load(POP_DELAYED_SCRIPT)

    def add(self, task: dict, delay_seconds: int) -> str:
        execute_at = int(time.time()) + delay_seconds
        task_id = uuid.uuid4().hex
        task["_id"] = task_id
        self.redis.zadd(self.key, {json.dumps(task, ensure_ascii=False): execute_at})
        return task_id

    def pop(self, count: int = 10) -> list[dict]:
        now = int(time.time())
        results = self.redis.evalsha(self.sha, 1, self.key, str(now), str(count))
        return [json.loads(t) for t in results]

# 使用示例
dq = DelayQueue(r)
dq.add({"task": "send_email", "to": "user@example.com"}, delay_seconds=60)
dq.add({"task": "cancel_order", "order_id": "ORD001"}, delay_seconds=120)

# 消费者轮询
while True:
    tasks = dq.pop(count=10)
    for task in tasks:
        print(f"处理任务: {task}")
    time.sleep(1)
```

## 四、Stream vs Kafka vs RabbitMQ

| 维度 | Redis Stream | Kafka | RabbitMQ |
|------|-------------|-------|----------|
| 消息持久化 | AOF/RDB（内存限制） | 磁盘日志（可无限堆积） | 可选持久化 |
| 消费者组 | 原生支持 | 原生支持 | 需插件 |
| 消息确认 | XACK | Offset 提交 | ACK |
| 消息回溯 | 按 ID 范围 | 按 Offset | 不支持 |
| 消息堆积 | 受内存限制 | 磁盘无限 | 队列限制 |
| 吞吐量 | 10 万+/秒 | 百万/秒 | 万/秒 |
| 延迟 | 微秒级 | 毫秒级 | 毫秒级 |
| 顺序保证 | 单 Stream 内有序 | 单 Partition 有序 | 单队列有序 |
| 分区扩展 | 不支持（单 key 单槽） | Partition 水平扩展 | 镜像队列 |
| 运维复杂度 | 低（Redis 一体化） | 高（Zookeeper/KRaft） | 中 |
| 适用场景 | 轻量消息队列、中小规模 | 大数据流、日志聚合 | 复杂路由、企业消息 |
| 客户端生态 | redis-py/ioredis | Kafka 客户端成熟 | AMQP 多语言 |

**选型建议**：

| 场景 | 推荐 |
|------|------|
| 日均消息量 < 1 亿、单机 Redis 已有 | Redis Stream |
| 日均消息量 > 10 亿、需水平扩展 | Kafka |
| 复杂路由、消息优先级、TTL | RabbitMQ |
| 实时通知、无需持久化 | Redis Pub/Sub |

## 五、实战：订单异步处理 Stream 消费者组

### 5.1 架构设计

```
订单异步处理架构：

  Web 应用                Redis Stream              消费者集群
┌──────────┐  XADD      ┌────────────┐  XREADGROUP  ┌──────────────┐
│ 订单服务  │ ─────────► │ orders     │ ──────────► │ worker-1      │
│          │            │            │             │ 扣库存、发邮件 │
└──────────┘            └────────────┘             └──────────────┘
                              │  XREADGROUP              │
                              │ ──────────────────────► │ worker-2     │
                              │                         │ 支付回调      │
                              │                         └──────────────┘
                              │
                              ▼ XPENDING + XAUTOCLAIM
                        ┌────────────┐
                        │ 监控进程    │ 转移超时消息
                        │ 死信处理   │ 超过 N 次重试 → 死信队列
                        └────────────┘
```

### 5.2 生产者实现

```python
import redis
import json
import time
from dataclasses import dataclass, asdict

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

@dataclass
class OrderEvent:
    order_id: str
    user_id: int
    amount: float
    status: str
    created_at: int

class OrderProducer:
    def __init__(self, redis_client: redis.Redis, stream: str = "orders"):
        self.redis = redis_client
        self.stream = stream

    def send(self, event: OrderEvent) -> str:
        """发送订单事件，限制 Stream 长度 10 万"""
        msg_id = self.redis.xadd(
            self.stream,
            {k: str(v) for k, v in asdict(event).items()},
            maxlen=100000,
            approximate=True,
        )
        return msg_id

    def send_order_created(self, order_id: str, user_id: int, amount: float) -> str:
        return self.send(OrderEvent(
            order_id=order_id, user_id=user_id, amount=amount,
            status="created", created_at=int(time.time())
        ))

# 使用
producer = OrderProducer(r)
for i in range(100):
    producer.send_order_created(f"ORD{i:04d}", 1000 + i, 99.9 + i)
```

### 5.3 消费者实现（含可靠消费）

```python
import os
import redis
import json
import time
import signal
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logger = logging.getLogger(__name__)

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class OrderConsumer:
    def __init__(
        self,
        redis_client: redis.Redis,
        stream: str,
        group: str,
        consumer_name: str,
        block_ms: int = 5000,
        batch_size: int = 10,
        max_delivery: int = 3,
    ):
        self.redis = redis_client
        self.stream = stream
        self.group = group
        self.consumer = consumer_name
        self.block_ms = block_ms
        self.batch_size = batch_size
        self.max_delivery = max_delivery
        self._running = True
        self._ensure_group()

    def _ensure_group(self):
        try:
            self.redis.xgroup_create(self.stream, self.group, id="$", mkstream=True)
            logger.info(f"创建消费者组 {self.group}")
        except redis.ResponseError as e:
            if "BUSYGROUP" in str(e):
                logger.info(f"消费者组 {self.group} 已存在")
            else:
                raise

    def process(self, msg_id: str, fields: dict) -> bool:
        """业务处理逻辑，返回 True 表示成功"""
        try:
            logger.info(f"[{self.consumer}] 处理订单 {fields.get('order_id')}")
            # 模拟业务：扣库存、发邮件、记录日志
            time.sleep(0.1)
            return True
        except Exception as e:
            logger.error(f"处理失败 {msg_id}: {e}")
            return False

    def _handle_dead_letter(self, msg_id: str, fields: dict, delivery_count: int):
        """超过最大重试次数 → 死信队列"""
        dead_stream = f"{self.stream}:dead"
        self.redis.xadd(dead_stream, {
            "original_id": msg_id,
            "delivery_count": str(delivery_count),
            **fields,
        })
        self.redis.xack(self.stream, self.group, msg_id)
        logger.warning(f"消息 {msg_id} 进入死信队列，重试 {delivery_count} 次")

    def _claim_stale_messages(self) -> int:
        """认领超时消息（60 秒未 ACK）"""
        claimed = 0
        # 1. 查询 pending 消息
        pending = self.redis.xpending_range(
            self.stream, self.group, min="-", max="+", count=20
        )
        for p in pending:
            if p.get("time_since_delivered", 0) < 60000:
                continue
            # 2. 检查投递次数
            if p.get("times_delivered", 0) >= self.max_delivery:
                msgs = self.redis.xrange(self.stream, p["message_id"], p["message_id"])
                for _, fields in msgs:
                    self._handle_dead_letter(p["message_id"], fields, p["times_delivered"])
                continue
            # 3. 转移给当前消费者
            self.redis.xclaim(
                self.stream, self.group, self.consumer,
                min_idle_time=60000, message_ids=[p["message_id"]]
            )
            claimed += 1
        return claimed

    def run(self):
        logger.info(f"消费者 {self.consumer} 启动")
        signal.signal(signal.SIGINT, lambda *_: setattr(self, "_running", False))
        signal.signal(signal.SIGTERM, lambda *_: setattr(self, "_running", False))

        while self._running:
            # 1. 先处理历史 Pending（崩溃恢复）
            self._claim_stale_messages()

            # 2. 读取新消息
            messages = self.redis.xreadgroup(
                self.group, self.consumer,
                {self.stream: ">"},
                count=self.batch_size,
                block=self.block_ms,
            )
            if not messages:
                continue

            for stream, msgs in messages:
                for msg_id, fields in msgs:
                    success = self.process(msg_id, fields)
                    if success:
                        self.redis.xack(self.stream, self.group, msg_id)

        logger.info(f"消费者 {self.consumer} 退出")

# 启动多个消费者
if __name__ == "__main__":
    consumer = OrderConsumer(
        r, stream="orders", group="order_workers",
        consumer_name=f"worker-{os.getpid()}",
    )
    consumer.run()
```

### 5.4 消费者组监控

class StreamMonitor:
    def __init__(self, redis_client: redis.Redis, stream: str, group: str):
        self.redis = redis_client
        self.stream = stream
        self.group = group

    def stats(self) -> dict:
        info = self.redis.xinfo_stream(self.stream)
        groups = self.redis.xinfo_groups(self.stream)
        target_group = next((g for g in groups if g["name"] == self.group), {})
        pending = self.redis.xpending(self.stream, self.group)
        return {
            "stream_length": info.get("length", 0),
            "last_id": info.get("last-generated-id"),
            "group_consumers": target_group.get("consumers", 0),
            "group_pending": target_group.get("pending", 0),
            "group_last_delivered": target_group.get("last-delivered-id"),
            "pending_detail": {
                "min": pending.get("min"),
                "max": pending.get("max"),
                "count": pending.get("pending", 0),
            },
        }

monitor = StreamMonitor(r, "orders", "order_workers")
import pprint
pprint.pprint(monitor.stats())

## 小思考题帮你巩固

1. **为什么 Pub/Sub 不适合做"订单通知"这类业务消息？两个致命点是什么？**（提示：不持久化 + 无消费确认；订阅者离线即丢、处理失败无人重投，见 1.4。）
2. **Stream 消费者组是"At-Least-Once"投递，业务处理代码要额外注意什么？**（提示：同一消息可能因重投被处理多次；处理逻辑必须幂等，见 6.2。）
3. **消费者崩溃没来得及 XACK，消息去哪了？其他消费者怎么接手？**（提示：进 Pending（PEL）；`XAUTOCLAIM ... min_idle_time` 把超时消息转给别的消费者，见 2.3。）
4. **同一消息被反复投递且反复失败，怎么避免死循环？**（提示：看 Pending 的 delivery_count，超过 `max_delivery` 转入死信队列并 ACK，见 5.3/6.2。）
5. **延迟队列为什么"取到期任务+删除"必须用 Lua 包起来？**（提示：ZRANGEBYSCORE 与 ZREM 不是原子；并发消费者可能重复取到同一任务，见 3.2。）

<details>
<summary>参考答案（点击展开）</summary>

1. ① 无持久化：消息只实时广播，订阅者离线就再也收不到（不写任何数据结构）；② 无消费确认：投递后订阅者处理失败也没有重投机制。这两点让 Pub/Sub 无法保证"业务消息不丢不漏"，只能用于配置推送/在线状态等可丢场景。
2. 消息可能因"超时重投/XAUTOCLAIM"被同一或不同消费者处理**多次**。业务必须做到幂等：同样的处理结果（如扣库存用 `SETNX`/状态机加唯一键、发通知可去重），否则重投=重复扣减。
3. 未被 ACK 的消息进入 Pending（PEL），等待超过 `min_idle_time`（如 60s）后，其他消费者用 `XAUTOCLAIM orders 组 消费者 60000 0-0 COUNT 10` 自动认领，继续处理；认领后会更新持有者与 delivery_count。
4. 检查 Pending 的投递次数（delivery_count），达到阈值（如 3）后不再重投，把消息转存到 `orders:dead` 死信流并 XACK 原消息——避免"永不失败的毒丸消息"卡住队列。
5. 因为"查到期任务（ZRANGEBYSCORE）+ 删除（ZREM）"两步之间可能有其他消费者并发了同样的操作，导致同一任务被多人处理。用 Lua 在一个脚本里"取出即删"（见 3.2 的 `POP_DELAYED_SCRIPT`），Redis 单线程保证整段原子。

## 六、生产注意事项

### 6.1 Stream 内存控制

| 方案 | 命令 | 适用场景 |
|------|------|----------|
| 添加时限制 | `XADD stream MAXLEN 10000 *` | 推荐，写入即裁剪 |
| 近似裁剪 | `XADD stream MAXLEN ~ 10000 *` | 性能优先，允许少量误差 |
| 手动裁剪 | `XTRIM stream MAXLEN 10000` | 历史数据已存在时补救 |
| 按 ID 裁剪 | `XTRIM stream MINID <id>` | 精确删除指定时间前数据 |

### 6.2 消费者组可靠性要点

| 要点 | 说明 |
|------|------|
| 幂等处理 | 消费者处理逻辑必须幂等，至少一次投递可能重复 |
| ACK 时机 | 业务处理成功后再 ACK，失败保留在 Pending 等重投 |
| Pending 监控 | 定期检查 Pending 数量，超阈值告警 |
| 死信处理 | 超过最大重试次数进入死信队列，避免无限重投 |
| 消费者优雅退出 | 收到 SIGTERM 后停止读取新消息，处理完 Pending 再退出 |

### 6.3 Cluster 下 Stream 限制

- Stream 单 key 位于单槽，无法跨节点分片
- 高吞吐场景需业务层分片：`orders:0`、`orders:1`、`orders:2`... 路由到不同槽
- 消费者组操作必须在 key 所在节点执行，客户端需支持 MOVED/ASK 重定向

## 本章小结

| 知识点 | 核心结论 | 实战要点 |
|--------|---------|---------|
| Pub/Sub | 实时广播，无持久化 | 仅用于配置广播、实时通知 |
| Stream 基础 | 持久化 + 消费者组 + ACK | 必设 MAXLEN 控制内存 |

| XAUTOCLAIM | 超时消息自动重投 | min_idle_time 通常 60 秒 |

| 选型 | 中小规模选 Stream，大规模选 Kafka | Redis Stream 单 key 单槽是瓶颈 |
