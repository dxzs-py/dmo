# 10 分布式锁与限流

> 分布式锁从 SETNX 演进到 Redlock，限流算法从固定窗口到令牌桶，二者都是高并发系统的稳定性基石。

## 零基础前置认知

**这篇在讲什么**：**分布式锁**解决"多个进程/实例抢占同一资源"（秒杀扣库存、缓存重建互斥、分布式任务调度互斥），**限流**解决"单位时间放行多少请求"（防突发打爆下游）。读完你能：① 写出一把"SET NX EX 加锁 + Lua 判断 UUID 再释放 + 看门狗续期"的生产锁（[codes/redis_lock.py](./codes/redis_lock.py)、[codes/redlock.py](./codes/redlock.py) 实测可运行）；② 说清 Redlock 是什么、它为什么有争议（Kleppmann vs antirez）；③ 用 ZSet 滑动窗口 / Lua 令牌桶（HSET + 时间戳）写出可用的限流器。

> 辅助类比：分布式锁像"多人共用一个卫生间的门锁"——**SET NX EX** 是"挂上'有人'牌 + 自动定时锁上"（防死锁：执行者挂了门也会自动开）；可重入锁是"同一个主人连续进几次只要挂一次牌、记次数"；看门狗是"预计超时前自动续牌"；**Redlock** 是"5 个卫生间同时挂同一块牌、坚持多数派（≥3）才算占用"——它过于复杂且仍非严格共识，故有著名争论。**限流**像"景区门票窗口"——固定窗口=每分钟固定放 N 张（瞬时峰值可打满后一批）；滑动窗口=按过去 1 分钟实时盘点（不准瞬时突峰）；令牌桶=按固定速率补票、允许攒票应对突发（推荐）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| SETNX → SET NX EX | 加锁原语：NX 不存在才写、EX 过期自动释放 | 演进关键：EXPIRE 原子合一，杜绝"加锁后宕机死锁" |
| Lua 释放锁 | `if GET==uuid then DEL` 原子判断+删除 | 杜绝"超时后误删别人的锁"（见 1.2 缺陷 2） |
| 看门狗（Watchdog） | 业务未完成自动续期（Redisson 模式） | 与"锁超时释放"是矛盾两面：续期太勤=锁不释放，太疏=锁被抢 |
| 可重入锁 | 同线程重复加锁用 Hash 记重入次数 | 由 Redisson 等封装；计数归零才真正删除 |
| Redlock | 对 N 个独立实例多数派加锁（N=5，≥3 成功即得锁） | 有"非严格共识 + 时钟漂移"争议；单实例锁多数场景够用 |
| 固定窗口限流 | 每分钟（/每窗口）最多 N 次 | 实现最简；窗口边界瞬时可能放行 2N |
| 滑动窗口限流 | 以"过去 window 内实时计数"判 | ZSet score=时间戳每次清理窗口外（见 5.2） |
| 令牌桶 | 按 rate 补令牌、桶深 burst，可取用则放行 | 允许突发；补令牌与扣令牌用 Lua 原子（HSET tokens/last_time） |

> 区分/注意：**锁 ≠ 限流**——锁保证"同一时刻只有一方"（互斥），限流保证"单位时间只放 N 个"（非互斥、允许排队）；前者防并发写冲突，后者防流量超载。**锁一定要带 owner 标识（UUID）再 Lua 释放**：不带 UUID 的裸 DEL 会误删别人刚拿到的锁（经典 BUG）。**Redlock 只是"更安全的分布式锁"，不是"一致共识"**：它在 5 节点多数派上加锁，仍无法严格证明"只有一个客户端持有"（Martin Kleppmann 反驳的核心）——绝大多数业务用**单实例 SET NX EX + 看门狗**即可，不要为了"高端"而盲目上 Redlock。

## 一、分布式锁演进

### 1.1 演进时间线

```
分布式锁演进：

1. SETNX（早期，有缺陷）
   SETNX lock:order 1      ← 原子获取
   EXPIRE lock:order 10     ← 非原子，宕机可能死锁
   ↓
2. SET NX EX（Redis 2.6.12+，推荐基础版）
   SET lock:order "uuid" NX EX 10  ← 获取+过期原子
   释放：DEL（可能误删别人的锁）↓
3. Lua 释放锁（判断+删除原子）
   if GET key == uuid then DEL key end
   ↓
4. 看门狗续期（Redisson）
   业务未完成自动延长 TTL
   ↓
5. 可重入锁（Hash + 计数器）
   同一线程可多次获取同一把锁
   ↓
6. Redlock（多节点投票，强一致）
   N 个独立实例，多数派成功才算加锁
```

### 1.2 SETNX 的两大缺陷

```bash
# 缺陷 1：SETNX + EXPIRE 非原子
SETNX lock:order 1       # 成功返回 1
# 此时宕机 → 没来得及 EXPIRE → 死锁
EXPIRE lock:order 10

# 解决：SET NX EX（Redis 2.6.12+）
SET lock:order "uuid-12345" NX EX 10

# 缺陷 2：DEL 误删别人的锁
# 场景：
T0  客户端 A 获取锁（TTL 10s）
T1  客户端 A 业务执行 15s（锁已过期自动释放）
T2  客户端 B 获取同一把锁（新 uuid）
T3  客户端 A 业务完成，执行 DEL → 误删 B 的锁！

# 解决：Lua 脚本判断 uuid 后再删
EVAL "
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
" 1 lock:order "uuid-12345"
```

### 1.3 完整基础分布式锁实现

```python
import redis
import time
import uuid

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

# 获取锁脚本（与 SET NX EX 等价，便于扩展）
LOCK_SCRIPT = """
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'EX', ARGV[2]) then
    return 1
end
return 0
"""

# 释放锁脚本（判断 + 删除原子）
UNLOCK_SCRIPT = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
"""

class DistributedLock:
    """基础分布式锁：SET NX EX + Lua 释放"""
    def __init__(self, redis_client: redis.Redis, lock_name: str, timeout: int = 10):
        self.redis = redis_client
        self.lock_key = f"lock:{lock_name}"
        self.timeout = timeout
        self.identifier = str(uuid.uuid4())
        self._lock_sha = self.redis.script_load(LOCK_SCRIPT)
        self._unlock_sha = self.redis.script_load(UNLOCK_SCRIPT)

    def acquire(self, retry_interval: float = 0.1, max_retries: int = 100) -> bool:
        for _ in range(max_retries):
            result = self.redis.evalsha(self._lock_sha, 1, self.lock_key, self.identifier, str(self.timeout))
            if result == 1:
                return True
            time.sleep(retry_interval)
        return False

    def release(self) -> bool:
        result = self.redis.evalsha(self._unlock_sha, 1, self.lock_key, self.identifier)
        return result == 1

    def __enter__(self):
        if not self.acquire():
            raise TimeoutError(f"获取锁 {self.lock_key} 超时")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.release()
        return False

# 使用
with DistributedLock(r, "order:12345", timeout=10) as lock:
    print("执行业务逻辑")
```

## 二、可重入锁与看门狗

### 2.1 可重入锁原理

可重入锁允许同一线程多次获取同一把锁，通过 Hash 结构记录持有者与重入次数。

```
可重入锁数据结构：
Key: lock:order:12345
Type: Hash
Field: <thread_uuid>     ← 持有者标识
Value: <reentrant_count> ← 重入次数

加锁逻辑（Lua）：
1. 如果 lock 不存在 → HSET key thread 1 + EXPIRE → 返回成功
2. 如果 lock 存在且 field 是当前 thread → HINCRBY key thread 1 + EXPIRE → 返回成功
3. 否则 → 返回失败

释放逻辑（Lua）：
1. 如果 field 不是当前 thread → 返回失败（非持有者）
2. HINCRBY key thread -1
3. 如果计数 ≤ 0 → DEL key
4. 否则 → 刷新 EXPIRE
```

```python
import redis
import time
import uuid
import threading

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

REENTRANT_LOCK_SCRIPT = """
local key = KEYS[1]
local thread_id = ARGV[1]
local timeout = tonumber(ARGV[2])

if redis.call('EXISTS', key) == 0 then
    redis.call('HSET', key, thread_id, 1)
    redis.call('EXPIRE', key, timeout)
    return 1
end

if redis.call('HEXISTS', key, thread_id) == 1 then
    redis.call('HINCRBY', key, thread_id, 1)
    redis.call('EXPIRE', key, timeout)
    return 1
end
return 0
"""

REENTRANT_UNLOCK_SCRIPT = """
local key = KEYS[1]
local thread_id = ARGV[1]

if redis.call('HEXISTS', key, thread_id) == 0 then
    return 0
end

local count = redis.call('HINCRBY', key, thread_id, -1)
if count <= 0 then
    redis.call('DEL', key)
    return 1
end
return 1
"""

RENEW_SCRIPT = """
if redis.call('HEXISTS', KEYS[1], ARGV[1]) == 1 then
    return redis.call('EXPIRE', KEYS[1], ARGV[2])
end
return 0
"""

class ReentrantDistributedLock:
    """可重入分布式锁 + 看门狗续期"""
    def __init__(self, redis_client: redis.Redis, lock_name: str,
                 timeout: int = 30, retry_delay: float = 0.1):
        self.redis = redis_client
        self.lock_key = f"lock:{lock_name}"
        self.timeout = timeout
        self.retry_delay = retry_delay
        # 标识 = 进程ID + 线程ID（保证同进程同线程可重入）
        self.identifier = f"{uuid.uuid4().hex}:{threading.get_ident()}"
        self._stop_renewal = True
        self._lock_sha = self.redis.script_load(REENTRANT_LOCK_SCRIPT)
        self._unlock_sha = self.redis.script_load(REENTRANT_UNLOCK_SCRIPT)
        self._renew_sha = self.redis.script_load(RENEW_SCRIPT)

    def acquire(self, max_wait: float = 10.0) -> bool:
        end_time = time.time() + max_wait
        while time.time() < end_time:
            result = self.redis.evalsha(
                self._lock_sha, 1, self.lock_key, self.identifier, str(self.timeout)
            )
            if result == 1:
                self._start_renewal_thread()
                return True
            time.sleep(self.retry_delay)
        return False

    def release(self) -> bool:
        self._stop_renewal = True
        result = self.redis.evalsha(self._unlock_sha, 1, self.lock_key, self.identifier)
        return result == 1

    def _start_renewal_thread(self):
        """看门狗：每 timeout/3 秒续期一次"""
        self._stop_renewal = False
        def renew():
            while not self._stop_renewal:
                time.sleep(self.timeout / 3)
                if not self._stop_renewal:
                    self.redis.evalsha(
                        self._renew_sha, 1, self.lock_key, self.identifier, str(self.timeout)
                    )
        threading.Thread(target=renew, daemon=True).start()

    def __enter__(self):
        if not self.acquire(max_wait=5.0):
            raise TimeoutError(f"获取锁 {self.lock_key} 超时")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.release()
        return False

# 使用：同线程可重入
lock = ReentrantDistributedLock(r, "order:process", timeout=30)
def nested_call():
    """同线程嵌套调用，复用锁"""
    with lock:
        print("嵌套获取锁成功")

with lock:
    print("外层获取锁成功")
    nested_call()  # 同线程可重入
```

### 2.2 看门狗续期机制

```
看门狗工作流程：
T0    获取锁（TTL=30s）→ 启动看门狗线程
T10   看门狗第 1 次续期（30/3=10s 后）→ EXPIRE key 30
T20   看门狗第 2 次续期
T25   业务完成 → release() → 停止看门狗
T30   即使未释放，看门狗已续期至 T40

异常场景：
T15   进程崩溃 → 看门狗停止 → 锁 TTL 自然过期（30s 后）

设计要点：
1. 续期间隔 = TTL / 3（Redisson 默认 10s 续期 30s 锁）
2. 续期用 Lua 脚本判断持有者，避免续期别人的锁
3. 看门狗线程设为 daemon，进程退出自动结束
4. release() 先停止看门狗，再执行 Lua 释放
```

## 三、Redlock 算法

### 3.1 Redlock 算法流程

Redlock 由 antirez 提出，在 N 个**独立**的 Redis 实例上同时获取锁，超过半数成功才算加锁成功。

```
Redlock 流程（5 个独立 Redis 实例）：

1. 客户端记录当前时间 T1
2. 依次向 5 个实例请求加锁（相同 key、相同 uuid、短 TTL）
   ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
   │ R1  │  │ R2  │  │ R3  │  │ R4  │  │ R5  │
   │ ✓   │  │ ✓   │  │ ✓   │  │ ✗   │  │ ✓   │
   └─────┘  └─────┘  └─────┘  └─────┘  └─────┘
   成功 4 个（≥3 = N/2+1，加锁成功）

3. 计算 T2 = 当前时间，加锁耗时 = T2 - T1
4. 校验：
   ├── 成功数 ≥ N/2 + 1 = 3 ✓
   └── 耗时 < TTL ✓
   两个条件都满足 → 加锁成功
   实际有效时间 = TTL - (T2 - T1)

5. 失败时：向所有实例发起释放（不论是否加锁成功）

容错性：
- 5 节点可容忍 2 节点宕机
- 3 节点可容忍 1 节点宕机
- 建议 5 节点起步
```

### 3.2 Redlock Python 实现

```python
import redis
import time
import uuid
import threading

class RedlockError(Exception):
    pass

class Redlock:
    """
    Redlock 算法实现
    需要传入 N 个独立的 Redis 实例（不能是主从或集群）
    """
    def __init__(self, redis_nodes: list[redis.Redis], lock_name: str,
                 ttl: int = 10000, retry_count: int = 3, retry_delay: int = 200):
        """
        :param redis_nodes: 独立的 Redis 实例列表（建议 5 个）
        :param lock_name: 锁名称
        :param ttl: 锁有效期（毫秒）
        :param retry_count: 加锁失败重试次数
        :param retry_delay: 重试间隔（毫秒）
        """
        self.nodes = redis_nodes
        self.quorum = len(redis_nodes) // 2 + 1  # 多数派
        self.lock_name = lock_name
        self.ttl = ttl
        self.retry_count = retry_count
        self.retry_delay_ms = retry_delay
        self.identifier = str(uuid.uuid4())
        self._unlock_script = """
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        else
            return 0
        end
        """

    def _acquire_instance(self, node: redis.Redis) -> bool:
        """对单个实例加锁"""
        try:
            return bool(node.set(self.lock_name, self.identifier, nx=True, px=self.ttl))
        except redis.RedisError:
            return False

    def _release_instance(self, node: redis.Redis):
        """对单个实例释放锁"""
        try:
            node.eval(self._unlock_script, 1, self.lock_name, self.identifier)
        except redis.RedisError:
            pass

    def acquire(self) -> bool:
        for attempt in range(self.retry_count):
            success_count = 0
            t1 = time.time() * 1000  # 毫秒

            # 并发加锁（降低总耗时）
            results = []
            threads = []
            def worker(node):
                results.append(self._acquire_instance(node))
            for node in self.nodes:
                t = threading.Thread(target=worker, args=(node,))
                t.start()
                threads.append(t)
            for t in threads:
                t.join()
            success_count = sum(results)

            t2 = time.time() * 1000
            elapsed = t2 - t1
            drift = self.ttl * 0.01 + 2  # 时钟漂移补偿

            # 校验：多数派成功 + 耗时合理
            if success_count >= self.quorum and elapsed < self.ttl - drift:
                return True

            # 失败：向所有实例释放
            self._release_all()
            time.sleep(self.retry_delay_ms / 1000)

        raise RedlockError(f"获取 Redlock {self.lock_name} 失败")

    def _release_all(self):
        for node in self.nodes:
            self._release_instance(node)

    def release(self):
        self._release_all()

    def __enter__(self):
        self.acquire()
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.release()
        return False

# 使用：5 个独立 Redis 实例
nodes = [
    redis.Redis(host="localhost", port=7000, decode_responses=True),
    redis.Redis(host="localhost", port=7001, decode_responses=True),
    redis.Redis(host="localhost", port=7002, decode_responses=True),
    redis.Redis(host="localhost", port=7003, decode_responses=True),
    redis.Redis(host="localhost", port=7004, decode_responses=True),
]

lock = Redlock(nodes, "critical:resource", ttl=10000)
try:
    lock.acquire()
    print("Redlock 加锁成功，执行关键业务")
finally:
    lock.release()
```

### 3.3 Redlock 的争议

Martin Kleppmann（《Designing Data-Intensive Applications》作者）在 2016 年发文质疑 Redlock 的正确性：

| 争议点 | Kleppmann 的批评 | antirez 的回应 |
|--------|------------------|----------------|
| 时钟跳跃 | NTP 时钟回拨会导致锁失效判断错误 | 实际生产时钟跳跃极小，且 Redlock 算入 drift |
| GC 暂停 | 客户端 STW 期间锁过期，恢复后误以为持有锁 | 这是任何分布式锁的通用问题，需 fencing token |
| 网络延迟 | 网络分区下客户端可能误判锁状态 | Redlock 设计已考虑网络延迟（elapsed < TTL） |
| 持久性 | Redis 异步持久化可能丢锁 | 开启 AOF `everysec` 折中，强一致用 ZK |

```
GC 暂停导致的问题示例：
T0  客户端 A 获取锁（TTL=10s）
T1  客户端 A STW GC 暂停 15s
T2  锁过期自动释放
T3  客户端 B 获取锁
T4  客户端 A GC 结束，仍以为自己持有锁 → 写入冲突！

解决方案：fencing token
T0  客户端 A 获取锁，token=1
T4  客户端 B 获取锁，token=2
T5  客户端 A 写 DB，附带 token=1
T6  DB 校验 token=1 < 已记录的 2 → 拒绝写入

但 Redlock 不提供 fencing token，需业务自行实现
```

### 3.4 选型建议

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| 单机 Redis 缓存场景 | 单节点 SET NX EX + Lua | 简单够用 |
| 主从 Redis | Redisson 单锁 + 看门狗 | 故障转移期间可能丢锁，业务可容忍 |
| 强一致要求高 | Redlock | 多数派投票，容忍少数节点宕机 |
| 极强一致 + 严格正确 | ZooKeeper / etcd | 基于 Paxos/Raft，CP 系统 |
| 短期临界区 | Redisson | 性能高，偶发冲突业务可接受 |

## 四、限流算法

### 4.1 四种限流算法对比

```
1. 固定窗口计数器
   时间窗口：|---60s---|---60s---|
   计数：    |   100   |   80    |
   问题：窗口边界 1 秒内可能有 200 请求（2 倍流量）

2. 滑动窗口计数器
   细分窗口为格子（如每格 1s，窗口 60 格）
   滑动计算窗口内总数
   比固定窗口更平滑

3. 令牌桶（Token Bucket）
   固定速率向桶中放入令牌（如 100 个/秒）
   请求消耗令牌，桶空则拒绝
   允许突发（桶满时可瞬时消费全部令牌）
   ┌─────────┐
   │ 令牌生成 │ ──► ┌─────────┐  请求来取令牌
   │ 速率 R  │     │  桶容量C │ ────► 允许/拒绝
   └─────────┘     └─────────┘

4. 漏桶（Leaky Bucket）
   请求进入桶中，以固定速率流出
   超出桶容量则拒绝
   输出速率恒定，平滑流量
   ┌─────────┐         ┌─────────┐
   │ 请求流入 │ ──► 桶 ──► │ 固定速率 │ ──► 处理
   │ 突发    │      │  满则丢弃 │     流出    │
   └─────────┘     └─────────┘         └─────────┘
```

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 固定窗口 | 实现简单、内存省 | 窗口边界突发 2 倍流量 | 严格限制总量 |
| 滑动窗口 | 平滑、精度高 | 实现稍复杂 | API 限流（推荐） |
| 令牌桶 | 支持突发、灵活 | 需维护令牌状态 | 大多数限流场景 |
| 漏桶 | 输出绝对平滑 | 无法应对突发 | 保护下游弱系统 |

## 五、Redis 限流实现

### 5.1 固定窗口限流

```bash
# 思路：INCR + 首次 EXPIRE
# KEYS[1] = rate_limit:user:1001
# ARGV[1] = 窗口大小（秒）
# ARGV[2] = 最大请求数
EVAL "
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
" 1 rate_limit:user:1001 60 100
```

### 5.2 滑动窗口限流（推荐）

```bash
# 基于 ZSet：score=时间戳，member=唯一标识
# KEYS[1] = rate_limit:user:1001
# ARGV[1] = 窗口大小（毫秒）
# ARGV[2] = 最大请求数
# ARGV[3] = 当前时间戳（毫秒）
# ARGV[4] = 唯一标识

EVAL "
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local member = ARGV[4]

-- 1. 清理窗口外记录
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- 2. 统计当前窗口内请求数
local count = redis.call('ZCARD', key)
-- 3. 未超限则记录
if count < limit then
    redis.call('ZADD', key, now, member)
    redis.call('EXPIRE', key, window / 1000)
    return 1
end
return 0
" 1 rate_limit:user:1001 60000 100 1700000000000:req1
```

### 5.3 令牌桶限流

```bash
# 基于 Hash：存储当前令牌数和上次刷新时间
# KEYS[1] = token_bucket:user:1001
# ARGV[1] = 桶容量
# ARGV[2] = 令牌生成速率（个/毫秒）
# ARGV[3] = 当前时间戳（毫秒）
# ARGV[4] = 本次请求消耗的令牌数

EVAL "
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local info = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(info[1]) or capacity
local last_time = tonumber(info[2]) or now

-- 计算时间间隔内生成的令牌
local elapsed = now - last_time
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, math.floor(capacity / rate) + 10)
    return 1
end
redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
return 0
" 1 token_bucket:user:1001 100 0.1 1700000000000 1
```

### 5.4 完整限流器封装

```python
import redis
import time
import uuid

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

SLIDING_WINDOW_SCRIPT = """
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local member = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, member)
    redis.call('EXPIRE', key, window / 1000)
    return 1
end
return 0
"""

TOKEN_BUCKET_SCRIPT = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local info = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(info[1]) or capacity
local last_time = tonumber(info[2]) or now

local elapsed = now - last_time
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= requested then
    tokens = tokens - requested
    redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
    redis.call('EXPIRE', key, math.floor(capacity / rate) + 10)
    return 1
end
redis.call('HSET', key, 'tokens', tokens, 'last_time', now)
return 0
"""

class RateLimiter:
    """综合限流器：支持滑动窗口与令牌桶"""
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self._sw_sha = self.redis.script_load(SLIDING_WINDOW_SCRIPT)
        self._tb_sha = self.redis.script_load(TOKEN_BUCKET_SCRIPT)

    def sliding_window_allow(self, key: str, window_ms: int, limit: int) -> bool:
        """滑动窗口限流
        :param key: 限流 key（如 api:user:1001）
        :param window_ms: 窗口大小（毫秒）
        :param limit: 窗口内最大请求数
        """
        now = int(time.time() * 1000)
        member = f"{now}:{uuid.uuid4().hex[:8]}"
        result = self.redis.evalsha(
            self._sw_sha, 1, key, str(window_ms), str(limit), str(now), member
        )
        return result == 1

    def token_bucket_allow(self, key: str, capacity: int,
                            rate_per_sec: float, requested: int = 1) -> bool:
        """令牌桶限流
        :param key: 限流 key
        :param capacity: 桶容量（允许突发）
        :param rate_per_sec: 令牌生成速率（个/秒）
        :param requested: 本次请求消耗的令牌数
        """
        now = int(time.time() * 1000)
        rate_per_ms = rate_per_sec / 1000.0
        result = self.redis.evalsha(
            self._tb_sha, 1, key, str(capacity), str(rate_per_ms), str(now), str(requested)
        )
        return result == 1

# 使用示例
limiter = RateLimiter(r)

# 滑动窗口：每用户每分钟最多 100 次
for i in range(15):
    allowed = limiter.sliding_window_allow("api:user:1001", 60000, 10)
    print(f"滑动窗口 请求{i+1}: {'允许' if allowed else '拒绝'}")

# 令牌桶：容量 10，每秒生成 5 个令牌
for i in range(20):
    allowed = limiter.token_bucket_allow("api:user:1002", capacity=10, rate_per_sec=5)
    print(f"令牌桶 请求{i+1}: {'允许' if allowed else '拒绝'}")
    time.sleep(0.1)
```

## 六、对比与选型

### 6.1 Redlock vs ZooKeeper vs etcd

| 维度 | Redlock | ZooKeeper | etcd |
|------|---------|-----------|------|
| 一致性模型 | 多数派投票（最终一致） | ZAB（CP，强一致） | Raft（CP，强一致） |
| 锁类型 | 临时 TTL 锁 | 临时节点（session 绑定） | Lease（TTL） |
| 性能 | 极高（10 万+ QPS） | 中（万级 QPS） | 较高（万级 QPS） |
| 故障恢复 | TTL 过期自动释放 | Session 超时自动释放 | Lease 过期自动释放 |
| 可重入 | 业务层实现（Redisson） | 不原生支持 | 不原生支持 |
| 阻塞等待 | 客户端轮询 | Watch 通知 | Watch 通知 |
| fencing token | 不提供 | 版本号（zxid） | revision |
| 部署复杂度 | 中（5 节点 Redis） | 高（Java + JVM） | 中（Go 二进制） |
| 适用场景 | 性能优先、容忍偶发冲突 | 强一致传统分布式系统 | 云原生基础设施 |

### 6.2 限流算法选型决策

```
需要限流？
├── 单机限流 → 本地限流（如 Sentinel、Guava RateLimiter）
└── 分布式限流 → Redis + Lua
    ├── 严格限制总量 → 固定窗口
    ├── 平滑限流、API 网关 → 滑动窗口
    ├── 允许突发流量 → 令牌桶（最常用）
    └── 保护下游弱系统、严格平滑 → 漏桶
```

### 6.3 分布式锁 vs 限流对比

| 维度 | 分布式锁 | 限流 |
|------|----------|------|
| 目标 | 互斥访问共享资源 | 控制请求速率 |
| 粒度 | 单个资源 | 接口/用户/IP 维度 |
| 失败行为 | 等待或拒绝 | 直接拒绝（429） |
| 持续时间 | 业务执行期间 | 单次请求 |
| Redis 数据结构 | String + Lua | ZSet/Hash + Lua |
| 典型场景 | 库存扣减、订单防重 | API 网关、爬虫防御 |

## 小思考题帮你巩固

1. **为什么 `SETNX + EXPIRE` 会死锁，`SET key uuid NX EX 10` 就好了？**（提示：两步非原子，第一步后宕机锁永不释放；SET NX EX 把加锁与过期原子合一，见 1.2 缺陷 1。）
2. **为什么"释放锁"必须用 Lua 做"GET 判断 + DEL"？直接 `DEL lock` 行不行？**（提示：锁超时后可能已被别人持有，裸 DEL 误删别人的锁，见 1.2 缺陷 2 / 1.3。）
3. **看门狗续期与"锁超时释放"是矛盾的，处理好坏的标准是什么？**（提示：续期要与业务实际执行时长匹配——续太勤锁迟迟不释放，续太疏业务没跑完锁就被抢；Redisson 默认每 10s 检查续期（锁 30s），按业务最坏执行时间设定，见 2.2。）
4. **Redlock 为什么有争议？它的"多数派加锁"不能保证什么？**（提示：Kleppmann 指出锁的语义证明不成立（无 Fencing Token、时钟跳变、GC 停顿）；antirez 辩称工程上足够。它比单实例锁"更抗单点"，但不是严格互斥共识，见 3.3。）
5. **固定窗口限流在窗口边界为什么可能放行 2N 个？滑动窗口如何解决？**（提示：如每分钟 100 次，59.9s 与 60.1s 各放 100=200；滑动窗口按"过去 1 分钟"实时计数，边界不再突发，见 4.1/5.2。）

<details>
<summary>参考答案（点击展开）</summary>

1. 旧写法是两条命令：`SETNX` 成功后再 `EXPIRE` 设过期——若进程在两者之间宕机/网络中断，锁没有过期时间就永远死了（其他客户端永远拿不到）。`SET key uuid NX EX 10` 是 Redis 2.6.12+ 提供的原子复合（NX+EX 同一条命令保证），不存在"只加锁没设过期"的窗口。
2. 裸 `DEL lock` 会在"锁已过期、另一客户端 B 已获取同 key 锁"时把 B 的锁删掉，导致两个客户端同时持锁（互斥被破坏）。正确做法：锁值存"持有者身份（uuid）"，释放时用 Lua `if GET(key)==uuid then DEL(key) end` 原子判断——只有本人能删自己的锁。
3. 续期与超时的平衡点是"锁的生命周期 ≈ 业务真实执行时间"：太长→持有期间其他客户端等待过久甚至不等（变成事实占坑）；太短→业务没跑完锁就自动释放、被他人抢占。看门狗按业务最大执行时长动态续期；同时锁内业务要带版本号/幂等验证防"过期后两份执行"。工程上市面通则是"锁 TTL 设为业务最坏耗时的数倍 + 看门狗兜底续期"。
4. 争议核心：单靠"多数派加锁"无法排除——① 多节点时钟各自漂移导致过期判断不一致；② 客户端在拿到锁后 STW（GC/停机）期间锁已过期，别人又拿到锁，原客户端恢复后继续执行却以为自己还持锁；③ 无 fencing token，旧持有者可能写入新持有者之后。Martin Kleppmann 主张用"不会过期的租约+fencing"，antirez 认为工程上多数派加锁已足够——结论：资金/强一致场景别把 Redlock 当共识，用 ZooKeeper/etcd 的租约锁；普通业务单实例锁+看门狗即可。
5. 固定窗口只记"当前窗口计数"，在整点边界前后各能各放满一个窗口的额度（最大约 2N）。滑动窗口用 ZSet 记录"过去 window 内每个请求的时间点"，每请求前 `ZREMRANGEBYSCORE 0 now-window` 清出过期、`ZCARD` 实时统计——边界不再出现"两个窗口合并放行"，代价是每个 key 的 ZSet 开销。

</details>

## 七、生产实战要点

### 7.1 分布式锁常见陷阱

| 陷阱 | 后果 | 解决方案 |
|------|------|----------|
| 锁误删 | 误删他人持有的锁 | Lua 脚本判断 uuid 后删 |
| 锁无法释放 | 业务异常未释放 | try-finally + TTL 兜底 |
| 业务超时 | 锁过期后他人加锁，原持有者误判 | 看门狗续期 + fencing token |
| 主从切换丢锁 | 故障转移期间锁丢失 | Redlock 或 ZK |
| 死锁 | 获取锁后进程崩溃 | 必设 TTL，禁用无过期锁 |
| 锁竞争激烈 | 大量重试拖垮 Redis | 退避重试 + 限流 |

### 7.2 限流器性能优化

| 优化点 | 方案 |
|--------|------|
| 减少 Lua 调用 | 启动时 SCRIPT LOAD，运行期 EVALSHA |
| 控制内存 | 滑动窗口 ZSet 必设 EXPIRE |
| 避免热 key | 多级限流（网关层 + 应用层） |
| 客户端降级 | Redis 异常时退化为本地限流 |
| 监控告警 | 限流次数、拒绝率、Top 限流对象 |
