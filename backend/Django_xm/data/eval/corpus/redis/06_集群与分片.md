# 06 集群与分片

> Redis Cluster 提供去中心化的数据分片与高可用，16384 哈希槽 + Gossip 协议实现自动路由与故障转移，是大规模生产环境的标准方案。

## 零基础前置认知

**这篇在讲什么**：单机内存放不下、单点扛不住时，就要"把数据拆开放多台机器"——**哈希槽**决定每个 key 去哪个节点（16384 槽 + CRC16 路由）、**Gossip** 让节点互相发现与同步状态、**MOVED/ASK** 把"访问错节点"的请求优雅地引到正确节点、**哈希标签 `{}`** 让相关 key 落在同槽（否则 multi-key 命令直接 CROSSSLOT 报错）。读完你能理解"为什么 MSET 两个 key 会报 CROSSSLOT、为什么客户端要 `-c`、槽迁移时 ASK 和 MOVED 差在哪"，并搭出 3 主 3 从的本地测试集群（现成配置见 [codes/](./codes/)）。*搭建/运维类操作（扩缩容、备份、故障转移演练）本篇只留一句话思路，完整命令在 codes/ 与 99 附录。*

> 辅助类比：把哈希槽想成"银行 16384 个抽屉分给 3 个金库"——**CRC16(key) % 16384** 决定"这个客户的存单进哪个抽屉"（稳定路由）；**MOVED** 是"这抽屉已经搬到 B 金库了，以后都去 B"（客户更新地址、永久有效）；**ASK** 是"这抽屉正在从 A 搬往 B，这次先去 B 取，地址别记"（临时一次）；**哈希标签 `{}`** 是"同一个家庭的所有存单打上同一编号，必须放同一抽屉"（关联数据同槽）；**Gossip** 是"金库之间低声互相传话，口口相传让所有人都知道谁在哪儿"（去中心化状态同步）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| 哈希槽（slot） | 16384 个槽，`CRC16(key) % 16384` 定位 | 槽是数据迁移/路由的最小单位，属主在节点间可搬 |
| Cluster Bus | 节点间专用通信端口（客户端端口+10000） | 走 Gossip（PING/PONG/MEET/FAIL），与客户端端口隔离 |
| Gossip | 每节点定期随机向若干节点交换集群状态 | 槽位图/节点状态最终一致；去中心化无协调者 |
| MOVED | key 槽不在本节点的稳定重定向 | 客户端更新槽→节点映射，后续直连（永久） |
| ASK | 槽迁移中 key 在目标节点的临时重定向 | 客户端发 `ASKING` 后再发原命令，**不更新**映射（临时） |
| 哈希标签（Hash Tag） | `{tag}` 只对 tag 内文本做 CRC16 | 让相关 key 同槽，规避 CROSSSLOT（multi-key/事务/Lua 前提） |
| CROSSSLOT | 一次命令涉及多个槽的 key | multi-key 命令/事务在 Cluster 下必须同槽或用标签 |
| reshard | 槽从源节点迁到目标节点（以槽为单位） | `redis-cli --cluster reshard`；扩容/缩容的核心动作 |

> 区分/注意：**MOVED 更新客户端路由表，ASK 不更新**——前者是"槽的属主已经变了"（稳定），后者是"槽正在搬，这次算临时"（迁移窗口）。**哈希标签 ≠ 保证数据一致性**：它只保证 key 同槽使命令合法；同槽仍不代表"原子"（Redis 命令本身原子，跨命令事务才需要 ACK/脚本）。**Cluster 只能使用 DB0**、`KEYS *` 只见本节点——生产查询要按节点 SCAN 或 `CLUSTER GETKEYSINSLOT`，这是开发最容易踩的坑。

## 一、Cluster 架构

### 1.1 核心特性

- **去中心化**：无中心节点，所有节点互相通信（Gossip 协议）
- **数据分片**：16384 个哈希槽分布在不同节点
- **高可用**：每个主节点可有从节点，主节点故障自动故障转移

### 1.2 Cluster 架构图

```
Redis Cluster 架构（3 主 3 从）：
┌─────────────────────────────────────────────────────┐
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Master1  │  │ Master2  │  │ Master3  │           │
│  │ 槽 0-5460│  │ 槽5461-  │  │ 槽10923- │           │
│  │          │  │  10922   │  │  16383   │           │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘           │
│       │              │              │                 │
│  ┌────┴─────┐  ┌────┴─────┐  ┌────┴─────┐           │
│  │ Slave1   │  │ Slave2   │  │ Slave3   │           │
│  │(Master1  │  │(Master2  │  │(Master3  │           │
│  │ 的从节点)│  │ 的从节点)│  │ 的从节点)│           │

```

### 1.3 节点角色与职责

| 角色 | 职责 | 端口 |
|------|------|------|
| Master | 处理槽位读写、参与 Gossip | 6379（或自定义） |
| Slave | 复制主节点、故障时升主 | 6380（或自定义） |
| Cluster Bus | 节点间通信 | 客户端端口 + 10000 |

## 二、数据分片与哈希槽

### 2.1 哈希槽分配算法

```
slot = CRC16(key) % 16384

示例：
key = "user:1001"
CRC16("user:1001") = 12567
slot = 12567 % 16384 = 12567
→ 路由到负责槽 12567 的节点

默认槽分配（3 主节点）：
  Master1: 槽 0-5460      (共 5461 个)
  Master2: 槽 5461-10922  (共 5462 个)
  Master3: 槽 10923-16383 (共 5461 个)
```

### 2.2 哈希标签（Hash Tag）

使用 `{}` 将 key 的部分内容作为哈希计算依据，确保相关 key 在同一个槽：

```bash
# 这两个 key 会在同一个槽（只计算 {} 内的部分）
SET {user}.1001:name "张三"
SET {user}.1001:age 25

# 查看key所在的槽
CLUSTER KEYSLOT {user}.1001:name
CLUSTER KEYSLOT {user}.1001:age
# 结果相同（只对 user 计算 CRC16）
```

适用场景：multi-key 操作（MGET、事务、Lua 脚本）需保证 key 在同槽。

### 2.3 为什么是 16384 个槽

| 原因 | 说明 |
|------|------|
| 心跳包大小 | Gossip 消息需携带节点负责的槽数据位图，16384 bit = 2KB，可接受 |
| 集群规模 | 官方建议节点数 ≤1000，16384/1000 ≈ 16 槽/节点，足够分散 |
| 压缩效率 | 位图压缩后较小，网络开销可控 |

## 三、节点通信（Gossip 协议）

### 3.1 Gossip 协议原理

Cluster 节点通过 Gossip 协议互相交换集群状态信息：

```
Gossip 通信流程：
1. 每个节点定期（每秒）随机选择 N 个节点发送 PING
2. PING 消息包含：
   ├── 发送者负责的槽位图
   ├── 发送者已知节点列表（部分）
   └── 集群状态信息
3. 接收者回复 PONG，同样携带自身信息
4. 节点间最终达到状态一致

Gossip 消息类型：
├── PING：探测节点存活
├── PONG：响应 PING
├── MEET：加入集群（新节点）
└── FAIL：广播某节点故障
```

### 3.2 Cluster Bus 通信

```
Cluster Bus 端口 = 客户端端口 + 10000

示例：
  Master1 客户端端口：7000
  Cluster Bus 端口：  17000

  Master2 客户端端口：7001
  Cluster Bus 端口：  17001

节点间通过 Cluster Bus 通信，客户端连接客户端端口
```

### 3.3 节点状态

| 状态 | 说明 |
|------|------|
| `online` | 在线，正常服务 |
| `possiblefail` | 疑似故障（Gossip 怀疑） |
| `fail` | 客观下线（多数节点确认） |
| `handshake` | 握手中（新加入节点） |
| `noflags` | 无标志位 |

## 四、MOVED 与 ASK 重定向

### 4.1 MOVED 重定向

当客户端访问的 key 不在当前节点的槽位范围时，节点返回 MOVED：

```bash
# 连接 Master1（槽 0-5460），访问槽 12567 的 key
redis-cli -c -p 7000
SET user:1001 "value"
# (error) MOVED 12567 127.0.0.1:7002

# -c 选项自动重定向到正确节点
# 不带 -c 则报错，客户端需自行处理
```

```
MOVED 响应格式：
MOVED <slot> <ip>:<port>

MOVED 12567 127.0.0.1:7002

客户端行为：
1. 收到 MOVED 后更新本地槽位路由表
2. 重新向新节点发送命令
3. 后续相同槽位的请求直接路由到新节点
```

### 4.2 ASK 重定向

槽迁移过程中，key 可能临时在源节点或目标节点，节点返回 ASK：

```bash
# 槽迁移中
GET user:1001
# (error) ASK 12567 127.0.0.1:7002
```

```
ASK 响应格式：
ASK <slot> <ip>:<port>

客户端行为：
1. 这次请求向新节点发送 ASKING 命令后再发送原命令
2. 不更新本地槽位路由表（临时重定向）
3. 下次相同 key 仍尝试原节点

ASKING 命令：
告诉目标节点"我要访问正在迁移的槽"
```

### 4.3 MOVED vs ASK

| 对比项 | MOVED | ASK |
|--------|-------|-----|
| 触发场景 | 槽位不在当前节点（稳定状态） | 槽迁移过程中（临时状态） |
| 客户端路由表更新 | 更新 | 不更新 |
| 是否需要 ASKING | 不需要 | 需要 |
| 持续性 | 永久 | 临时 |

### 5.1 节点规划

| 节点 | 端口 | 角色 | Cluster Bus |
|------|------|------|-------------|
| Node1 | 7000 | Master | 17000 |
| Node2 | 7001 | Master | 17001 |
| Node3 | 7002 | Master | 17002 |

| Node5 | 7004 | Slave | 17004 |
| Node6 | 7005 | Slave | 17005 |

### 5.2 节点配置文件（现成模板见 codes/）

节点配置只需在普通 Redis 配置上加 4 个 cluster 指令（完整模板见 [codes/redis_node_7000.conf](./codes/redis_node_7000.conf)，7001-7005 改端口与路径即可）：

```conf
# 集群四要素（其余 port/daemonize/dir/appendonly 等同单机）
cluster-enabled yes                    # 开启集群模式
cluster-config-file nodes-7000.conf    # 节点状态文件（自动生成）
cluster-node-timeout 5000              # 节点超时（毫秒）
cluster-require-full-coverage yes      # 全槽覆盖才对外服务（生产建议 yes）
cluster-migration-barrier 1            # 从节点迁移保护

# 一键创建 3 主 3 从（含节点启动）：bash codes/create_cluster.sh（见 codes/README）
```

### 5.3 启动与创建集群

```bash
# 启动 6 个 Redis 实例
redis-server redis-7000.conf
redis-server redis-7001.conf
redis-server redis-7002.conf
redis-server redis-7003.conf
redis-server redis-7004.conf
redis-server redis-7005.conf

# 创建集群（--cluster-replicas 1 表示每个主节点 1 个从节点）
redis-cli --cluster create \
  127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002 \
  127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005 \
  --cluster-replicas 1

# 验证集群
redis-cli --cluster check 127.0.0.1:7000
```

### 5.4 连接与查询

```bash
# 连接集群（-c 启用集群模式，自动重定向）
redis-cli -c -p 7000

# 查看集群信息
CLUSTER INFO

# 查看集群节点
CLUSTER NODES

# 查看哈希槽分布
CLUSTER SLOTS

# 查看 key 所在槽
CLUSTER KEYSLOT mykey

# 统计各节点 key 数量
CLUSTER COUNTKEYSINSLOT 12567

# 获取指定槽的 key
CLUSTER GETKEYSINSLOT 12567 10
```

### 5.5 CLUSTER INFO 关键字段

| 字段 | 说明 |
|------|------|
| `cluster_state` | 集群状态（ok/fail） |
| `cluster_slots_assigned` | 已分配槽数 |
| `cluster_slots_ok` | 正常槽数 |
| `cluster_slots_fail` | 故障槽数 |
| `cluster_known_nodes` | 已知节点数 |
| `cluster_size` | 主节点数 |
| `cluster_current_epoch` | 当前纪元 |

## 六、扩缩容（速查）

**原理**：扩容 = 加节点 + 迁槽（add-node → reshard），缩容 = 迁空槽 + 删节点（reshard → del-node）；每步都能用 `--cluster check` 复核。一键脚本见 [codes/create_cluster.sh](./codes/create_cluster.sh)：

```bash
# 扩容：启动新节点 → 加入集群 → 迁槽给它
redis-server redis-7006.conf
redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000
redis-cli --cluster reshard 127.0.0.1:7000     # 交互式：移多少槽 → 目标节点 ID → 源（all=均分）

# 加从节点（--cluster-slave + --cluster-master-id <主ID>）
redis-cli --cluster add-node 127.0.0.1:7007 127.0.0.1:7000 --cluster-slave --cluster-master-id <主节点40位ID>

# 缩容：先把主节点的槽迁走（迁移到空槽才可删）
redis-cli --cluster reshard 127.0.0.1:7000
redis-cli --cluster del-node 127.0.0.1:7000 <待删节点ID>

# 运维复核/修复/均衡
redis-cli --cluster check 127.0.0.1:7000     # 健康检查
redis-cli --cluster fix 127.0.0.1:7000       # 异常修复
redis-cli --cluster rebalance 127.0.0.1:7000 # 槽位自动均衡
```

## 七、一致性哈希 vs 哈希槽

### 7.1 一致性哈希

```
一致性哈希（0-2^32 环）：
       0
       │
  NodeA ──── NodeB
       │
       │
  NodeC ──── 2^32

key 路由：顺时针找到第一个节点
节点增删：仅影响相邻节点数据
问题：节点少时数据倾斜（用虚拟节点解决）
```

### 7.2 哈希槽

```
哈希槽（固定 16384 个）：
┌──────┬──────┬──────┐
│Slot 0│Slot 1│ ...  │ Slot 16383
└──┬───┴──┬───┴──────┴──┬───────┘
   │      │              │
   ▼      ▼              ▼
 Master1 Master2      Master3

key 路由：CRC16(key) % 16384
节点增删：迁移槽位（明确可控）
优势：槽位固定，迁移粒度可控
```

### 7.3 对比

| 对比项 | 一致性哈希 | 哈希槽 |
|--------|-----------|--------|
| 哈希空间 | 2^32 | 16384 |
| 路由算法 | 顺时针找节点 | CRC16 % 16384 |
| 节点增删影响 | 相邻节点 | 仅迁移指定槽 |
| 数据倾斜 | 用虚拟节点解决 | 槽位均匀分配 |
| 迁移粒度 | 不可控 | 槽为单位可控 |
| 客户端复杂度 | 需维护环 | 需维护槽映射 |
| 代表实现 | Memcached 客户端 | Redis Cluster |

Redis 选择哈希槽的原因：迁移可控、客户端实现简单、便于运维。

## 九、Cluster 限制

### 9.1 主要限制

| 限制 | 说明 | 解决方案 |
|------|------|----------|
| multi-key 限制 | `MGET` 等批量命令的 key 必须在同一槽 | 使用哈希标签 `{}` |
| 事务限制 | 事务中的 key 必须在同一槽 | 使用哈希标签 `{}` |
| 数据库限制 | 只能使用 DB0 | 无 |
| key 批量操作 | `KEYS *` 只能看到当前节点的 key | 使用 `CLUSTER GETKEYSINSLOT` 或 SCAN 各节点 |
| 集群规模 | 官方建议不超过 500 个节点，实际生产建议控制在百级 | 合理规划分片 |
| Pub/Sub | 普通 Pub/Sub 全集群广播（7.0 前无解） | 使用 Sharded Pub/Sub（7.0+） |
| SELECT 命令 | 不支持 | 使用 DB0 |

### 9.2 multi-key 操作示例

```bash
# ❌ 错误：不同槽的 key 无法批量操作
MSET user:1001 "a" user:1002 "b"
# (error) CROSSSLOT Keys in request don't hash to the same slot

# ✅ 正确：使用哈希标签确保同槽
MSET {user}.1001 "a" {user}.1002 "b"
# OK

# ❌ 错误：不同槽的 key 无法事务
MULTI
SET user:1001 "a"
SET user:1002 "b"
EXEC
# (error) CROSSSLOT

# ✅ 正确：使用哈希标签
MULTI
SET {user}.1001 "a"
SET {user}.1002 "b"
EXEC
```

### 9.3 跨节点操作解决方案

| 场景 | 方案 |
|------|------|
| 批量获取 | 客户端按槽分组后并行 MGET |
| 跨节点事务 | 客户端拆分为多个事务，或使用 Lua 脚本 |
| 跨节点聚合 | 客户端收集各节点结果后聚合 |
| 跨节点 JOIN | 在应用层完成 |
| 全局统计 | 各节点分别统计后聚合 |

## 十一、Cluster 集群运维实战

### 11.1 备份与恢复（一句话）

备份按**从节点**逐个执行（备份循环：各端口 `BGSAVE` → 复制 dump.rdb）；恢复=停节点 → 替换 RDB → 重启，与单机流程一致（完整脚本见 [03 篇 codes/backup_restore.sh](../03_持久化机制/codes/backup_restore.sh)）。生产备份应选从节点做，避免影响主节点。

### 11.2 故障转移测试

```bash
# 模拟主节点故障
redis-cli -p 7000 DEBUG SEGFAULT  # 或 SHUTDOWN NOSAVE

# 观察集群状态（5-30 秒内自动故障转移）
redis-cli -p 7001 CLUSTER NODES

# 手动故障转移（在从节点执行）
redis-cli -p 7003 CLUSTER FAILOVER

# CLUSTER FAILOVER 选项：
# FORCE      强制故障转移（不要求主节点确认）
# TAKEOVER   直接接管（不与其他节点协商，慎用）
```

### 11.3 监控关键指标

| 指标 | 命令 | 告警阈值 |
|------|------|----------|
| `cluster_state` | `CLUSTER INFO` | ≠ ok |
| `cluster_slots_fail` | `CLUSTER INFO` | >0 |
| `cluster_known_nodes` | `CLUSTER INFO` | 突变需关注 |
| 节点状态 | `CLUSTER NODES` | fail/possiblefail |
| 主从延迟 | `INFO replication` | offset 差 >10MB |

### 11.4 常见问题排查

```bash
# 1. 集群状态异常
redis-cli --cluster check 127.0.0.1:7000
redis-cli --cluster fix 127.0.0.1:7000

# 2. 槽位未覆盖
CLUSTER SLOTS
# 查找缺失槽位并分配

# 3. 节点失联
CLUSTER NODES
# 检查失联节点的网络与进程

# 4. 客户端连接错误
redis-cli -c -p 7000   # 必须加 -c 启用集群模式
```

## 本章小结

| 要点 | 说明 |
|------|------|
| Cluster 架构 | 去中心化，16384 哈希槽 |
| 路由算法 | CRC16(key) % 16384 |
| Gossip 协议 | 节点间状态同步 |
| MOVED | 永久重定向，客户端更新路由表 |
| ASK | 临时重定向（槽迁移中） |
| 哈希标签 | `{}` 确保 multi-key 同槽 |
| 扩缩容 | add-node / reshard / del-node |
| vs 一致性哈希 | 槽迁移可控，客户端简单 |
| Cluster 限制 | multi-key 同槽、仅 DB0、Pub/Sub 广播 |
| 高可用方案 | 主从 < Sentinel < Cluster |

## 小思考题帮你巩固

1. **为什么 `MSET user:1001 a user:1002 b` 在 Cluster 会报 CROSSSLOT，而 `MSET {user}.1001 a {user}.1002 b` 不报？**（提示：CRC16 只对 `{}` 内文本计算，见二 2.2/九 9.2。）
2. **MOVED 与 ASK 都让客户端"去另一个节点"，为什么 ASK 还需要 `ASKING` 命令？**（提示：槽的属主没变、只是数据正在迁移，目标节点默认只对'本属于自己槽'的 key 服务，见四 4.2。）
3. **客户端如果不做任何重定向处理、也不带 `-c`，访问错节点的 key 会怎样？**（提示：命令报 MOVED 错误返回，客户端需解析并重发或维护槽映射，见四。）
4. **Cluster 里执行 `KEYS *` 为什么"数据不全"？要用什么替代？**（提示：KEYS 只扫当前节点；按节点 SCAN 或用 CLUSTER GETKEYSINSLOT，见九 9.1。）
5. **扩容一台新主节点后，为什么必须 reshard？直接 add-node 能立刻分担流量吗？**（提示：新节点槽数为 0，不迁槽就不持有任何 key，见六。）

<details>
<summary>参考答案（点击展开）</summary>

1. `CRC16(key) % 16384` 对**整个 key** 计算；不带标签时 `user:1001` 与 `user:1002` 是两个独立 key，槽号大概率不同，跨槽的 multi-key 命令直接拒绝。用 `{user}` 后只对括号内 `user` 计算，两个 key 落同一槽，命令合法。（生产上用 `{业务ID}` 统一关联数据的槽归属。）
2. ASK 场景槽还在源节点名下（迁移中），目标节点此时只"暂时放了一批迁移中的 key"；不更新客户端映射、不改变槽属主。加 `ASKING` 是告诉目标节点"这次放行一次迁移中的访问"，否则目标节点会按"槽不属于我"拒绝。
3. 客户端收到 `(error) MOVED 12567 127.0.0.1:7002` 后要么自己解析 IP:port 重发、要么维护"槽→节点"映射表；`redis-cli -c` 就是替你做了这件事（连接模式下自动跟随 MOVED/ASK）。生产客户端（redis-py-cluster / Lettuce / ioredis-cluster）内置此逻辑。
4. `KEYS *` 只遍历当前连接节点的 keyspace——Cluster 数据分散在 6 节点，单节点只能看到自己的那份。替代：对每个主节点分别 `SCAN` 汇总，或针对已知槽用 `CLUSTER GETKEYSINSLOT`。
5. 不能。add-node 只把节点**加入集群**，槽仍是空集（0 槽）——不 reshard 就不持有任何 key，流量不会过去。扩容的完整动作=join + reshard（迁多少槽给新节点，`all` 从各主均分）。

</details>

## 最佳实践与常见陷阱

> 本节的每条都来自 Redis Cluster 实战，按"现象 → 原因 → 处置"组织。

| # | 陷阱 | 现象 | 原因 | 处置 |
|---|------|------|------|------|
| 1 | 关联数据没用哈希标签 | multi-key/事务/Lua 报 CROSSSLOT | key 槽不同 | 用 `{业务ID}` 前缀统一同业务 key 的槽（见 2.2/9.2） |
| 2 | 用 `KEYS *` 遍历"全库" | 结果显然不全（只有本节点） | KEYS 只扫当前节点 | 对每个主节点 SCAN 汇总；维护期用 `CLUSTER GETKEYSINSLOT` |
| 3 | 直连单节点且不处理 MOVED | 访问错槽 key 一直报 MOVED | 客户端没启用集群模式 | `redis-cli -c`；生产用支持 Cluster 的客户端库 |
| 4 | 新节点 add-node 后以为已扩容 | 流量没过去、数据没分布 | 新节点 0 槽，未 reshard | add-node 后执行 reshard/rebalance（见六） |
| 5 | 删主节点没先迁空槽 | del-node 报 槽未迁移/数据残留 | 主节点仍有槽 | 先 reshard 把槽迁走再 del-node（见六） |
| 6 | `cluster-require-full-coverage yes` 下某主挂了停止服务 | 单个主节点故障整片不可写 | 全槽覆盖要求任一槽不可达即拒写 | 小集群可容忍；大规模建议按需求权衡该参数（yes 保一致 / no 保可用） |
| 7 | 没配 `-c` 就把监控/脚本捞到错数据 | 每个节点数据都不一样还以为是故障 | 集群客户端语义未启用 | 监控按每个 master 分别统计并汇总；脚本统一走集群客户端 |

> **一句话总结**：Cluster 的杠杆在"**槽位思维**"——写 key 前先想"槽与跨槽"（关联数据打 `{}`），读数据别用 `KEYS`（按节点 SCAN 汇总），客户端必须集群模式（自动处理 MOVED/ASK），扩容=join+reshard、缩容=迁空+del；运维上盯 `cluster_state` 与全槽覆盖，生产高可用就稳了。
