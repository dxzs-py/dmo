# 03 持久化机制

> Redis 提供 RDB 快照、AOF 日志、混合持久化三种方案，分别权衡恢复速度、数据安全与性能开销，生产环境推荐混合持久化（RDB + AOF 增量）。

## 零基础前置认知

**这篇在讲什么**：Redis 是内存数据库，**断电/重启数据就没了**，除非你把它"定期拍照"（RDB 二进制快照）或"全程录下来"（AOF 命令日志）存进磁盘。本篇讲清三件事：**RDB 怎么靠 fork+COW"不打扰业务地拍照"、AOF 怎么在"丢 1 秒 vs 慢一点"之间选同步策略、Redis 7 的 Multi-part AOF 与混合持久化怎么把"恢复快 + 不丢数据"两个好处兼得**。读完你能给任何 Redis 实例配出合适的持久化组合，并懂得在故障时用什么命令自检。*备份脚本与生产配置等运维向内容在篇末「速查卡」浓缩，完整见 99 附录。*

> 辅助类比：把持久化想成"写论文的存档策略"——**RDB** 是"每过一会儿整个文档照一张相"（快照：恢复快，但最后几分钟的修改可能丢）；**AOF** 是"每次按键都记进日志本"（命令日志：改完即记，最多丢最后 1 秒，但文件大、恢复要重放）；**混合持久化**是"先放一张最近的照片 + 照片后的小段修改日志"（RDB 段负责快、AOF 段负责补齐）——生产推荐，正是"旧照片 + 新注释"的组合；**fsync 策略**是"日志本多久合上写死（flush 到磁盘）一次"：每句写完就写死（丢最少但慢）、每秒写死一次（推荐）、交给系统自便（快但可能多丢）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| RDB | Redis Database 二进制快照（dump.rdb） | 与 AOF 二选一/可混合；恢复快、可能丢数分钟数据 |
| AOF | Append Only File 命令日志 | 与 RDB 可混合；实时性高、文件大、恢复重放慢 |
| fork + COW | 父进程 fork 子进程、写时复制共享页 | RDB/AOF 重写的共同底座：子进程读 fork 时快照，父进程改页才复制 |
| fsync | 把 OS 缓冲区刷到磁盘的系统调用 | AOF 策略 always/everysec/no 决定调用频次，权衡"丢多少"与"IO 多快" |
| AOF 重写 | 用当前状态压缩出最小命令集重建 AOF | 与 RDB 触发同源（fork）；重写期间新旧 AOF 并存，结束后原子替换 |
| 混合持久化 | AOF 文件 = RDB 段 + AOF 增量段 | `aof-use-rdb-preamble yes`（4.0+ 默认开）：加载快 + 丢秒级 |
| Multi-part AOF | Redis 7 把 AOF 拆为 base+incr+manifest | 重写不阻塞、单段损坏不影响其他段 |
| THP（Transparent Huge Pages） | 内核大页透明化 | 关闭它（never）以减小 COW 时页复制放大 |

> 区分/注意：**"RDB 恢复快" 与 "AOF 丢得少" 不是互相排斥**——混合持久化两者兼得，生产默认用混合而非二选一。**AOF 重写 ≠ 备份**：重写只是把命令日志压缩（旧命令折叠），落盘的文件仍可能因断电丢最后 1 秒；真正的灾备要靠定期把 RDB 文件搬到异地。**`SAVE`（同步阻塞）与 `BGSAVE`（fork 异步）完全不同**：前者阻塞主线程，生产禁用。

## 一、持久化总览

Redis 内存数据库，重启后数据丢失。持久化机制决定数据是否落盘与恢复策略。

### 1.1 三种方案概览

| 方案 | 原理 | 数据安全 | 恢复速度 | 文件大小 | 适用 |
|------|------|----------|----------|----------|------|
| RDB | 二进制快照 | 可能丢数分钟 | 快 | 小 | 备份、灾备 |
| AOF | 命令日志追加 | 最多丢 1 秒 | 慢 | 大 | 数据安全要求高 |
| 混合 | RDB + AOF 增量 | 最多丢 1 秒 | 快 | 中 | 生产推荐 |

### 1.2 持久化架构

```
┌───────────────────────────────────────────────────┐
│              Redis Server (内存)                  │
│                                                   │
│  命令执行 ──► 内存数据库                          │
│              │                                    │
│              ├──► RDB 触发 ──► fork 子进程 ──► dump.rdb
│              │                                    │
│              └──► AOF 缓冲区 ──► BIO fsync ──► appendonly.aof
│                                                   │
│  重启加载：dump.rdb → appendonly.aof → 内存      │
└───────────────────────────────────────────────────┘
```

## 二、RDB 持久化

### 2.1 原理与 COW

Redis 通过 fork 子进程生成 RDB 文件，利用操作系统的**写时复制（Copy-On-Write）**机制：

```
RDB 生成过程：
┌──────────────┐    fork()    ┌──────────────┐
│  父进程       │ ──────────► │  子进程       │
│  (处理命令)   │   COW 机制  │  (生成 RDB)   │
│              │ 共享内存页   │              │
│  修改数据时   │             │  遍历内存     │
│  才复制页     │             │  写入磁盘     │
└──────────────┘             └──────────────┘

COW 工作机制：
1. fork 后父子进程共享同一份物理内存页（只读）
2. 父进程写入某页时，内核复制该页（仅修改的页）
3. 子进程始终读取 fork 时刻的内存快照
4. 大页内存（Huge Pages）会放大 COW 内存开销，建议关闭
```

### 2.2 触发方式

| 触发方式 | 命令/配置 | 说明 |
|----------|-----------|------|
| 手动同步 | `SAVE` | 阻塞主线程，**禁用** |
| 手动异步 | `BGSAVE` | fork 子进程，推荐 |
| 自动触发 | `save 900 1` | 900 秒内至少 1 个 key 变更 |
| 自动触发 | `save 300 10` | 300 秒内至少 10 个 key 变更 |
| 自动触发 | `save 60 10000` | 60 秒内至少 10000 个 key 变更 |
| 关闭触发 | `SHUTDOWN` | 安全关闭时自动执行 |
| 主从复制 | 全量同步 | 主节点 BGSAVE 发送给从节点 |
| AOF 重写 | — | AOF 重写同时触发 RDB |

### 2.3 RDB 文件结构

```
┌────────┬──────────┬──────────┬──────────┬──────────┐
│ REDIS  │ db_version│ databases│  EOF     │  check_sum│
│(魔数)  │ (版本号)  │ (数据)   │(结束标记)│ (校验和)  │
└────────┴──────────┴──────────┴──────────┴──────────┘

databases 部分：
┌─────────┬────────────────────┬─────────┐
│ SELECT  │ db_number 的键值对 │ SELECT  │ ...
│ db_num  │ ( expire, type,   │ db_num  │
│         │   key, value )    │         │
└─────────┴────────────────────┴─────────┘
```

### 2.4 实战命令

```bash
# 手动触发 RDB 持久化（后台执行）
BGSAVE

# 查看最近一次 RDB 保存状态
LASTSAVE

# 查看 RDB 配置
CONFIG GET dir
CONFIG GET dbfilename
CONFIG GET save

# 修改 RDB 自动保存策略
CONFIG SET save "900 1 300 10 60 10000"

# 禁用 RDB（删除所有 save 配置）
CONFIG SET save ""

# 从 RDB 文件恢复数据
# 将 dump.rdb 文件放到 Redis 的 dir 目录下，启动 Redis 即可自动加载

# 验证 RDB 文件完整性
redis-check-rdb /var/lib/redis/dump.rdb
```

### 2.5 RDB 优缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑，适合备份与远程传输 | 无法做到实时/秒级持久化，故障会丢数据 |
| fork 子进程执行，不影响主线程性能 | fork 时若数据量大，会瞬间阻塞主线程 |
| 恢复速度快（直接加载二进制） | 不同版本 RDB 格式不兼容 |
| 适合灾备、归档场景 | 不适合对数据安全性要求高的场景 |

## 三、AOF 持久化

### 3.1 原理

每执行一条写命令，就将该命令追加到 AOF 缓冲区，再根据同步策略写入磁盘。

```
AOF 写入流程：
命令执行 → 写入 AOF 缓冲区 → 根据策略同步到磁盘 → AOF 重写（压缩）

┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 命令执行  │───►│ AOF 缓冲区│───►│ OS 缓冲区 │───►│  磁盘文件 │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
                                 │
                          fsync 策略控制
```

### 3.2 三种 fsync 策略

| 策略 | 说明 | 数据安全性 | 性能 |
|------|------|-----------|------|
| `always` | 每条命令都 fsync | 最高，最多丢 1 条 | 最低 |
| `everysec` | 每秒 fsync 一次 | 最多丢 1 秒数据 | 折中（推荐） |
| `no` | 由 OS 决定何时 fsync | 可能丢较多数据 | 最高 |

### 3.3 AOF 重写

随着命令不断追加，AOF 文件越来越大。AOF 重写通过读取当前数据库状态，用最少的命令重新生成 AOF 文件。

```
重写前 AOF：
SET counter 1
INCR counter
INCR counter
INCR counter
（4 条命令）

重写后 AOF：
SET counter 4
（1 条命令，等效结果）

重写流程：
1. 主进程 fork 子进程
2. 子进程遍历内存，生成新 AOF（RDB preamble + 增量命令）
3. 重写期间新命令同时写入旧 AOF 与 AOF 重写缓冲区
4. 子进程完成后通知主进程
5. 主进程将重写缓冲区内容追加到新 AOF
6. 原子替换旧 AOF 文件
```

### 3.4 实战命令

```bash
# 开启 AOF 持久化
CONFIG SET appendonly yes

# 设置 AOF 同步策略
CONFIG SET appendfsync everysec

# 手动触发 AOF 重写
BGREWRITEAOF

# 查看 AOF 配置
CONFIG GET appendonly
CONFIG GET appendfsync
CONFIG GET auto-aof-rewrite-percentage
CONFIG GET auto-aof-rewrite-min-size
CONFIG GET aof-use-rdb-preamble

# AOF 重写时是否禁用 fsync（避免大量磁盘 I/O）
CONFIG SET no-appendfsync-on-rewrite yes

# 验证 AOF 文件
redis-check-aof /var/lib/redis/appendonly.aof

# 修复损坏的 AOF 文件
redis-check-aof --fix /var/lib/redis/appendonly.aof
```

### 3.5 AOF 自动重写触发条件

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `auto-aof-rewrite-percentage` | 100 | AOF 文件大小较上次重写后增长百分比 |
| `auto-aof-rewrite-min-size` | 64mb | AOF 文件最小触发重写大小 |

两个条件**同时满足**才触发自动重写。

### 3.6 AOF 优缺点

| 优点 | 缺点 |
|------|------|
| 数据安全性高，最多丢 1 秒 | 文件比 RDB 大 |
| 命令日志可读，可手动修复 | 恢复速度慢（重放命令） |
| 重写后文件大小可控 | fsync 影响 IO 性能 |
| 兼容性好，可跨版本恢复 | 重写期间 fork 仍有开销 |

## 四、混合持久化（Redis 4.0+）

### 4.1 原理

AOF 重写时前半部分用 RDB 格式（加载快），后半部分用 AOF 格式（增量数据不丢失）。

```
混合持久化 AOF 文件结构：
┌────────────────────┬─────────────────────┐
│   RDB 格式数据      │   AOF 格式增量数据    │
│  （全量快照，加载快）│  （增量命令，数据完整）│
└────────────────────┴─────────────────────┘

恢复流程：
1. 加载 RDB 部分（快速恢复大部分数据）
2. 重放 AOF 增量命令（恢复 RDB 之后产生的数据）
```

### 4.2 实战配置

```bash
# 开启混合持久化（Redis 4.0+ 默认开启）
CONFIG SET aof-use-rdb-preamble yes

# 查看混合持久化配置
CONFIG GET aof-use-rdb-preamble
```

### 4.3 混合持久化优势

| 对比项 | 纯 AOF | 混合持久化 |
|--------|--------|-----------|
| 加载速度 | 慢（全部重放命令） | 快（RDB 部分直接加载） |
| 数据完整性 | 最多丢 1 秒 | 最多丢 1 秒 |
| 文件大小 | 大 | 中（RDB 压缩） |
| 兼容性 | Redis 2.6+ | Redis 4.0+ |

## 五、Redis 7 Multi-part AOF

Redis 7 对 AOF 进行重大重构，引入 Multi-part AOF：

### 5.1 文件结构

```
appendonlydir/
├── manifest.aof                           # 清单文件（记录所有 AOF 段）
├── appendonly.aof.1.base.rdb              # 基础文件（重写时的 RDB 或 AOF 全量）
├── appendonly.aof.1.incr.aof              # 增量文件（基础之后的命令）
├── appendonly.aof.2.base.rdb              # 第二次重写后的基础文件
└── appendonly.aof.2.incr.aof              # 第二次重写后的增量
```

### 5.2 manifest 文件示例

```
file appendonly.aof.1.base.rdb seq 1 type b
file appendonly.aof.1.incr.aof seq 1 type i
file appendonly.aof.2.base.rdb seq 2 type b
file appendonly.aof.2.incr.aof seq 2 type i
```

### 5.3 Multi-part AOF 优势

| 对比项 | Redis 6 单文件 AOF | Redis 7 Multi-part AOF |
|--------|-------------------|----------------------|
| 重写阻塞 | 重写完成时主进程需追加缓冲，可能短暂阻塞 | 不阻塞 |
| 文件损坏风险 | 单文件损坏全丢 | 仅影响损坏的段 |
| 并发性能 | 重写期间性能下降 | 重写期间性能更好 |
| AOF 加载 | 全文件顺序加载 | 按 manifest 顺序加载各段 |

## 六、三种方案对比

| 对比项 | RDB | AOF | 混合持久化 |
|--------|-----|-----|-----------|
| 数据安全性 | 可能丢数分钟数据 | 最多丢 1 秒 | 最多丢 1 秒 |
| 文件大小 | 小（二进制压缩） | 大（命令日志） | 中 |
| 恢复速度 | 快（直接加载） | 慢（重放命令） | 快（RDB 部分快） |
| 系统资源 | fork 时可能影响性能 | 写入频繁影响性能 | 折中 |
| fork 开销 | 有 | 重写时有 | 重写时有 |
| 适用场景 | 备份、灾备 | 数据安全要求高 | 推荐生产使用 |

## 七、RDB vs AOF vs 混合 选型决策

```
                需要持久化？
                ┌─── 否 ───► 仅作缓存，关闭持久化
                │
                是
                │
       数据安全性要求？
       ┌─── 高（不能丢数据）───┐
       │                       │
       是                      否（容忍分钟级丢失）
       │                       │
   混合持久化                  RDB
   (RDB+AOF)                  (定期 BGSAVE)
   everysec                   适合灾备
       │                       │
       ▼                       ▼
   生产推荐                  备份场景
```

### 7.1 决策表

| 场景 | 推荐方案 | 配置 |
|------|----------|------|
| 纯缓存（可重建） | 关闭持久化 | `save ""` + `appendonly no` |
| 缓存 + 数据存储 | 混合持久化 | `appendonly yes` + `aof-use-rdb-preamble yes` |
| 备份归档 | RDB 定期备份 | `save 900 1` + 定时 BGSAVE |
| 数据安全极高 | AOF always（慎用） | `appendfsync always` |
| 灾备恢复 | RDB 远程传输 | BGSAVE + rsync 到异地 |

## 八、生产环境推荐配置

### 8.1 redis.conf 持久化片段

```conf
# ============== 持久化配置（生产推荐） ==============

# RDB 自动保存策略
save 900 1
save 300 10
save 60 10000

# RDB 文件名与目录
dbfilename dump.rdb
dir /var/lib/redis

# RDB 压缩与校验
rdbcompression yes
rdbchecksum yes

# fork 后若发生写入错误，停止接受写入（避免数据不一致）
stop-writes-on-bgsave-error yes

# AOF 开启
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"           # Redis 7 Multi-part AOF 目录
appendfsync everysec

# 混合持久化（4.0+ 默认 yes）
aof-use-rdb-preamble yes

# AOF 自动重写触发条件
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# AOF 重写期间禁用 fsync（避免高 IO 负载）
no-appendfsync-on-rewrite yes

# AOF 加载时遇到截断的处理（yes 继续，no 报错停止）
aof-load-truncated yes

# AOF 文件损坏时是否启动（yes 尽量恢复）
aof-timestamp-enabled no
```

### 8.2 fork 性能与 COW 内存放大

fork 利用 COW 机制避免复制全部内存，但仍有开销：

| 数据量 | fork 耗时 | COW 内存放大 |
|--------|-----------|-------------|
| 1GB | <50ms | 父进程写入页才复制 |
| 10GB | 200-500ms | 写入越多放大越大 |
| 50GB | 1-3 秒 | 可能触发 OOM |
| 100GB | 5-10 秒 | 强烈建议关闭 THP |

```
COW 内存放大问题：
fork 后父子共享内存页（只读）
父进程写入某页时，内核复制该页
若 fork 期间写入量大，复制页数接近总页数
→ RSS 可能翻倍

缓解方案：
1. 关闭 Transparent Huge Pages（THP）
   echo never > /sys/kernel/mm/transparent_hugepage/enabled
2. 控制写入速率（重写期间降低 QPS）
3. 使用无盘复制（repl-diskless-sync yes）
4. 监控 used_memory_rss 峰值
```

### 8.3 性能调优建议

| 项 | 建议 |
|----|------|
| fork 耗时 | 数据量 > 10GB 时 fork 可能阻塞秒级，建议关闭 THP |
| 磁盘 IO | AOF 与 RDB 文件分盘存放，避免相互影响 |
| 备份策略 | 每小时 BGSAVE + 异地备份，保留 7 天 |
| 监控指标 | `rdb_last_bgsave_status`、`aof_last_bgrewrite_status` 必须为 ok |
| 重写时机 | 选择业务低峰期，避免与 RDB 重叠 |
| fsync 频次 | everysec 折中，always 仅极敏感场景 |

## 九、AOF 重写深度解析

### 9.1 重写期间命令缓冲机制

AOF 重写期间，主进程仍处理命令，新旧 AOF 需要保持一致：

```
AOF 重写流程（含缓冲机制）：

时间轴 ──────────────────────────────────────────►

T1: 主进程触发 BGREWRITEAOF
    │
    ├── fork 子进程
    │   └── 子进程开始遍历内存生成新 AOF
    │
T2: 主进程继续处理新命令
    │   ├── 写入旧 AOF（保证故障时可恢复）
    │   └── 同时写入 AOF 重写缓冲区（aof_rewrite_buf）
    │
T3: 子进程完成新 AOF 写入
    │   └── 发送信号通知主进程
    │
T4: 主进程处理信号
    │   ├── 将 aof_rewrite_buf 内容追加到新 AOF
    │   ├── 原子重命名新 AOF 覆盖旧 AOF
    │   └── 后续命令写入新 AOF
    │
T5: 重写完成

关键点：
- 重写期间主进程写入旧 AOF 是为了重写失败时数据不丢
- aof_rewrite_buf 大小有限，若重写过慢可能溢出
- 重写完成后通过原子 rename 保证一致性
```

### 9.2 重写触发条件与控制

| 触发方式 | 配置 | 说明 |
|----------|------|------|
| 手动 | `BGREWRITEAOF` | 命令行触发 |
| 自动 | `auto-aof-rewrite-percentage 100` | AOF 较上次重写后增长 100% |
| 自动 | `auto-aof-rewrite-min-size 64mb` | AOF 最小 64MB 才触发 |
| AOF 开启时 | — | 首次开启 AOF 时自动重写 |

### 9.3 重写期间 fsync 控制

```bash
# 重写期间是否禁用 fsync（避免高 IO 负载）
CONFIG SET no-appendfsync-on-rewrite yes

# yes：重写期间主进程的 AOF 不 fsync，依赖 OS 写回
# no：重写期间仍按 appendfsync 策略 fsync（可能影响性能）
```

| 选项 | 数据安全 | 性能 | 推荐 |
|------|----------|------|------|
| `yes` | 重写期间可能丢 30 秒日志 | 高 | 生产推荐 |
| `no` | 严格按策略 | 低 | 极端数据安全场景 |

## 十、备份与恢复（速查）

**原理**：备份的精髓是"**先落盘、再搬走**"——`BGSAVE`/`BGREWRITEAOF` 让 Redis 自己把内存落成文件，再把文件复制到备份目录/异地；恢复反过来：停止实例 → 替换 RDB/AOF 文件 → 重启加载。配套可运行脚本见 [codes/backup_restore.sh](./codes/backup_restore.sh)（`backup|restore [rdb|aof]`，含 sha256 完整性校验）：

```bash
# 备份 RDB（触发 BGSAVE → 等待完成 → 复制 + sha256 校验）
bash codes/backup_restore.sh backup rdb

# 恢复 RDB（停止 Redis → 替换 dump.rdb → 启动 → PING 验证）
bash codes/backup_restore.sh restore rdb /tmp/redis_backup/dump_xxx.rdb
```

恢复流程要点（手动版）：
1. `redis-cli SHUTDOWN NOSAVE` —— 停止实例且不触发保存（避免覆盖备份）
2. 暂时移走旧 `dump.rdb` 与 `appendonlydir`（Redis 7）——**先禁 AOF 再恢复 RDB**，否则启动时 AOF 可能覆盖 RDB 数据
3. 放入备份的 `dump.rdb` 后启动，`redis-cli DBSIZE` 验证数量
4. 确认无误后再 `CONFIG SET appendonly yes` 重开 AOF（会立即触发重写）

> 灾备建议：**每小时 BGSAVE + RDB 文件异地同步，保留 7 天**；恢复脚本与完整命令见 [codes/backup_restore.sh](./codes/backup_restore.sh) 与 99 附录「运维速查」。

### 11.1 常见故障

| 故障现象 | 可能原因 | 排查命令 |
|---------|---------|---------|
| BGSAVE 失败 | 磁盘满 / fork 失败 / 权限 | `INFO persistence` |

| fork 阻塞 | THP 未关闭 / 内存大 | 检查 `latest_fork_usec` |

### 11.2 排查命令

```bash
INFO persistence | grep -E "rdb_last_bgsave_status|aof_last_bgrewrite_status|aof_last_write_status"
# 期望: 三个字段均为 ok → 持久化链路正常

INFO stats | grep latest_fork_usec            # fork 耗时（µs）；过大 → 查 THP/内存
INFO persistence | grep -E "aof_rewrite|aof_pending"   # AOF 重写进度与待追加缓冲
redis-check-rdb <dump.rdb>                    # RDB 完整性

```

### 11.3 监控告警

| 指标 | 告警阈值 | 处理 |
|------|----------|------|

| `aof_last_bgrewrite_status` | ≠ ok | 立即排查 |
| `latest_fork_usec` | > 1000000（1 秒） | 检查 THP、内存 |

## 本章小结

| 要点 | 说明 |
|------|------|
| RDB | 二进制快照，fork + COW，恢复快但可能丢数据 |
| AOF | 命令日志，everysec 推荐策略 |

## 小思考题帮你巩固

1. **为什么 RDB"恢复快但丢得多、AOF"丢得少但恢复慢"？**（提示：RDB 是二进制快照直接加载；AOF 要逐条重放命令，见一/六。）
2. **fork + COW 里，为什么"父进程写入某页才复制该页"？不 COW 的话会怎样？**（提示：fork 后父子共享只读页；子进程要的是"fork 时刻的快照"，父进程改了才需要复制隔离，见二 2.1/八 8.2。）
3. **AOF `everysec` 说"最多丢 1 秒"，它是靠什么实现的？**（提示：上一秒的 fsync 已完成落盘；每秒只攒最后 1 秒缓冲，见三 3.2。）
4. **混合持久化为什么"恢复快 + 丢得少"能兼得？加载时先做什么后做什么？**（提示：AOF 文件=RDB 段+增量段；先加载 RDB 段再重放 AOF 增量，见四。）
5. **AOF 重写期间，主进程会同时写两份 AOF，是哪两份？为什么必须这样？**（提示：旧 AOF（防重写失败丢数据）+ AOF 重写缓冲区（重写期间新命令），见九 9.1。）
6. **为什么 THP 开着会放大 COW 的内存开销？**（提示：大页最小 2MB，父进程改一个小字节也要复制整页 2MB，见八 8.2。）

<details>
<summary>参考答案（点击展开）</summary>

1. RDB 是 fork 时内存的二进制快照，加载只需按格式读入内存（快）；但它只在触发时刻拍照，两次快照之间的写命令没被记录（丢数分钟）。AOF 逐条追加写命令，恢复需要全部重放（慢），但 last fsync 之后的命令都还在（最多丢 1 秒）。
2. fork 时父子共享同一物理页且只读；子进程读的是自己视角的"fork 时内存"。若父进程修改数据，直接把整页"物归原主"复制一份给父进程（写时复制），子进程仍拿原页——保证子进程快照一致且没有全量复制。若不做 COW，fork 就要复制全部内存（毫秒级→秒级拉起+翻倍内存）。
3. 主线程把命令写进 AOF 缓冲，后台（BIO）线程**每秒调一次 fsync** 把缓冲刷到磁盘。崩溃最多丢"last fsync 之后 1 秒内"的写命令——这就是"最多丢 1 秒"。
4. 混合时 AOF 文件以 RDB 格式开头（fork 快照，直接加载快）+ 之后以 AOF 命令续写。加载：先读入 RDB 段（快速恢复全量），再重放 AOF 段（补齐快照后的增量），两端兼得。
5. 旧 AOF（保证重写失败时数据仍可恢复）+ AOF 重写缓冲区（aof_rewrite_buf，记录重写期间新命令以便最终拼进新文件）。重写结束原子 rename 后，后续命令写新 AOF。
6. THP 开启后内存页 2MB，COW 以页为单位复制：父进程即使只改一个字节，整页（最多 2MB）也要复制一次，写密集时 RSS 可能翻倍。关闭 THP（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`）能显著降低 fork 后内存放大（见八 8.2）。

</details>

## 最佳实践与常见陷阱

> 本节的每条都来自 Redis 持久化实战，按"现象 → 原因 → 处置"组织。

| # | 陷阱 | 现象 | 原因 | 处置 |
|---|------|------|------|------|
| 1 | 手动备份用 `SAVE` | 主线程卡住秒级、线上 QPS 掉坑 | SAVE 同步阻塞命令执行 | 一律 `BGSAVE`（fork 异步）；`SAVE` 仅在停机维护时考虑 |
| 2 | RDB 恢复了数据却"少了" | 恢复后数据比崩溃前少 | 只开 RDB、最后一两次快照之间的写命令没落盘 | 数据敏感则混合持久化（appendonly yes + preamble yes） |
| 3 | 恢复 RDB 时被 AOF 覆盖 | 拷入 dump.rdb，启动后数据是旧的/空的 | 启动时 AOF 优先级高于 RDB，旧 AOF 重放覆盖了 RDB | 恢复前先移走 appendonlydir/禁 AOF，验证后再开（见十） |
| 4 | `appendfsync always` 拖垮写性能 | 写 QPS 暴跌、磁盘 IO 飙高 | 每条命令都 fsync，syscall 开销巨大 | everysec（丢≤1s）通常足够；always 仅极敏感场景 |
| 5 | 大数据量 fork 后内存暴涨/OOM | BGSAVE 后 RSS 近乎翻倍 | THP 开着，COW 复制 2MB 整页 | 关 THP；重写选低峰期；必要时 diskless 复制（见八 8.2） |
| 6 | 以为"AOF 重写=备份" | 重写完没搬文件，服务器磁盘坏了一切归零 | 重写只压缩命令日志，不产生异地副本 | 定期 `backup rdb` + RDB 异地同步（见十/99 运维速查） |
| 7 | 磁盘写满才想起 BGSAVE | `rdb_last_bgsave_status:err`、AOF 停止增长 | 落盘失败会 stop-writes 保护（stop-writes-on-bgsave-error） | 监控 rdb/aof 状态字段（=ok）与磁盘空间（见 11.3） |

> **一句话总结**：Redis 持久化的杠杆在"**快照兜底 + 日志兜边**"——RDB 管"快速恢复与灾备"、AOF 管"秒级不丢"、混合两者兼得（生产默认）；性能的三个开关是 fsync 策略（everysec）、fork 时机（低峰）与 THP（关闭）；纪律是一句"**先落盘、再搬走**"，备份文件一定要离开本机。
