### 2.2 String 字符串

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `SET key value [EX s] [PX ms] [NX\|XX]` | 设置值（NX 不存在才设，XX 已存在才设） | O(1) |
| `SETNX key value` | 不存在才设置 | O(1) |
| `SETEX key seconds value` | 设置带过期时间 | O(1) |
| `PSETEX key ms value` | 设置带毫秒过期时间 | O(1) |
| `MSET key val [key val ...]` | 批量设置 | O(N) |
| `MSETNX key val [key val ...]` | 批量设置（全部不存在才执行） | O(N) |
| `GET key` | 获取值 | O(1) |
| `MGET key [key ...]` | 批量获取 | O(N) |
| `GETSET key value` | 设置新值返回旧值 | O(1) |
| `GETDEL key` | 获取并删除 | O(1) |
| `GETEX key [EX s\|PX ms\|EXAT ts\|PXAT ts]` | 获取并设置过期 | O(1) |
| `APPEND key value` | 追加字符串 | O(1) |
| `STRLEN key` | 字符串长度 | O(1) |
| `INCR key` | 自增 1 | O(1) |
| `INCRBY key n` | 自增 n | O(1) |
| `INCRBYFLOAT key n` | 浮点自增 | O(1) |
| `DECR key` | 自减 1 | O(1) |
| `DECRBY key n` | 自减 n | O(1) |
| `SETRANGE key offset value` | 覆盖子串 | O(1) |
| `GETRANGE key start end` | 获取子串 | O(N) |
| `APPEND key value` | 追加字符串 | O(1) |

```bash
# 分布式锁标准用法
SET lock:order:1001 "uuid-xxx" EX 30 NX

# 计数器
INCR pv:homepage        # 浏览量自增
INCRBY stock:1001 -1    # 库存扣减

# 批量优化（减少 RTT）
MSET k1 v1 k2 v2 k3 v3
MGET k1 k2 k3
```

```bash
LRANGE recent:msg 0 -1
```

### 2.7 Stream 流

| 命令 | 说明 |
|------|------|
| `XADD key [NOMKSTREAM] [MAXLEN\|MINID [=\\~] threshold [LIMIT count]] * \| id field value [field value ...]` | 添加消息 |
| `XLEN key` | 消息数量 |
| `XRANGE key start end [COUNT count]` | 范围查询 |
| `XREVRANGE key end start [COUNT count]` | 反向范围 |
| `XREAD [COUNT count] [BLOCK ms] STREAMS key [key ...] id [id ...]` | 读取消息 |
| `XGROUP CREATE key group id [MKSTREAM]` | 创建消费者组 |
| `XGROUP CREATECONSUMER key group consumer` | 创建消费者 |
| `XGROUP DELCONSUMER key group consumer` | 删除消费者 |
| `XGROUP DESTROY key group` | 删除消费者组 |
| `XGROUP SETID key group id` | 设置消费位点 |
| `XREADGROUP GROUP group consumer [COUNT count] [BLOCK ms] [NOACK] STREAMS key [key ...] id [id ...]` | 消费者组读取 |
| `XACK key group id [id ...]` | 确认消息 |
| `XCLAIM key group consumer min-idle-time id [id ...]` | 转移消息所有权 |
| `XAUTOCLAIM key group consumer min-idle-time start [COUNT count]` | 自动认领超时消息 |
| `XPENDING key group [start end count] [consumer]` | 待处理消息 |
| `XINFO STREAM key [FULL [COUNT count]]` | Stream 信息 |
| `XINFO GROUPS key` | 消费者组列表 |
| `XINFO CONSUMERS key group` | 消费者列表 |
| `XDEL key id [id ...]` | 删除消息 |
| `XTRIM key MAXLEN\|MINID [=\\~] threshold [LIMIT count]` | 修剪 |
| `XSETID key last-id` | 设置最后消息 ID |

```bash
# 完整消费者组流程
XADD orders * user_id 1001 amount 99.9         # 生产消息
XGROUP CREATE orders order_group $ MKSTREAM    # 创建组
XREADGROUP GROUP order_group consumer1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders order_group 1630000000000-0        # 确认
XPENDING orders order_group                    # 待处理
XAUTOCLAIM orders order_group consumer2 60000 0 COUNT 10  # 自动认领超时
```

详见 [08 发布订阅与消息队列](../08_发布订阅与消息队列/08_发布订阅与消息队列.md)。

#### 4.3.3 完整 RAG Agent

```python
from langchain_redis import RedisVectorStore, RedisChatMessageHistory
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

# 1. 初始化组件
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

vectorstore = RedisVectorStore(
    embeddings,
    index_name="knowledge_base",
    redis_url="redis://localhost:6379",
)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

def get_history(session_id: str):
    return RedisChatMessageHistory(
        session_id=session_id,
        redis_url="redis://localhost:6379",
        ttl=3600,
    )

# 2. RAG Prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "基于以下上下文回答问题。\n上下文：{context}"),
    MessagesPlaceholder(variable_name="history"),
    ("human", "{question}"),
])

# 3. RAG Chain
def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

rag_chain = (
    {"context": retriever | format_docs, "history": lambda x: get_history(x["session_id"]).messages, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

# 4. 调用
session_id = "user_1001"
question = "Redis 有哪些数据类型？"
answer = rag_chain.invoke({"question": question, "session_id": session_id})

# 5. 保存对话
history = get_history(session_id)
history.add_user_message(question)
history.add_ai_message(answer)
```

## 六、常见问题排查表

### 6.1 连接问题

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| `Could not connect to Redis at 127.0.0.1:6379: Connection refused` | Redis 未启动 / 端口错误 | `redis-server --daemonize yes`；检查 `port` |
| `NOAUTH Authentication required` | 启用了密码但未认证 | `redis-cli -a password` 或 `AUTH password` |
| `WRONGPASS invalid username-password pair` | 密码错误 / ACL 用户名错误 | 检查 `requirepass`、`aclfile` |
| `LOADING Redis is loading the dataset in memory` | 启动中加载 RDB/AOF | 等待加载完成；优化 `appendonly` 启用 `aof-use-rdb-preamble` |
| `MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk` | 磁盘满 / 权限不足 | 检查 `df -h`、目录权限；临时 `CONFIG SET stop-writes-on-bgsave-error no` |
| `NOREPLICAS Not enough good replicas to write` | `min-replicas-to-write` 配置但副本不足 | 调整 `min-replicas-to-write`；检查从节点状态 |
| 客户端连接数过多 | `maxclients` 限制 / 连接泄漏 | `CONFIG GET maxclients`；应用侧使用连接池；`CLIENT LIST` 排查 |
| `MOVED 1234 127.0.0.1:7002` | Cluster 重定向（客户端不支持 MOVED） | 用支持 Cluster 的客户端（redis-py cluster、jedis cluster） |
| `ASK 1234 127.0.0.1:7002` | Cluster 槽迁移中重定向 | 客户端处理 ASK；避免迁移期访问 |
| `CROSSSLOT Keys in request don't hash to the same slot` | 多 Key 操作跨槽 | 使用 Hash Tag `{tag}` 保证同槽 |

### 6.2 内存问题

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| `OOM command not allowed when used memory > 'maxmemory'` | 内存超 `maxmemory` 且策略为 `noeviction` | 修改 `maxmemory-policy` 为 `allkeys-lfu`；扩容 |
| `used_memory_rss` 远大于 `used_memory` | 内存碎片率高 | 开启 `activedefrag yes`；重启释放 |
| 内存持续增长不释放 | 大 Key 累积 / 未设置 TTL | `MEMORY USAGE key` 排查大 Key；定期 `SCAN` 清理 |
| `RDB BGSAVE` 期间内存翻倍 | COW 写时复制 | 避免写高峰期 BGSAVE；开启 `repl-diskless-sync` |
| `fork()` 失败 | 大内存 fork 慢或失败 | 调整 `vm.overcommit_memory=1`；减少内存或用副本持久化 |
| 内存碎片率 `mem_fragmentation_ratio < 1` | 使用了 swap | 检查 swap 使用，关闭 swap 或增加物理内存 |
| 客户端输出缓冲区占用大 | 慢客户端订阅 Pub/Sub | `CLIENT LIST` 找慢客户端；调小 `client-output-buffer-limit` |
| AOF 重写消耗内存 | 重写期间双份内存 | 开启 `no-appendfsync-on-rewrite`；错峰重写 |

### 6.3 持久化问题

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| AOF 文件损坏无法启动 | 写入中断 / 磁盘故障 | `redis-check-aof --fix appendonly.aof` |
| RDB 文件损坏 | 磁盘故障 | `redis-check-rdb dump.rdb`；从备份恢复 |
| BGSAVE 频繁失败 | 磁盘满 / fork 失败 | 检查磁盘；调 `vm.overcommit_memory` |
| AOF 重写频繁 | 写入量大 / 阈值低 | 调大 `auto-aof-rewrite-percentage` 和 `min-size` |
| 启动加载 AOF 慢 | AOF 文件大 | 启用混合持久化 `aof-use-rdb-preamble yes` |
| 持久化导致延迟突增 | fork 阻塞主线程 | 减少内存；用副本持久化；调整 `save` 策略 |
| `fork time` 长（>100ms） | 大内存 | 监控 `info stats latest_fork_usec`；限制内存或用副本 |
| 数据恢复后丢失 | AOF everysec 丢 1 秒 | 改 `appendfsync always`（性能下降） |

### 6.4 复制问题

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| 从节点数据落后 | 异步复制延迟 | `INFO replication` 查 `lag`；网络优化；`repl-backlog-size` 调大 |
| 全量同步频繁 | backlog 不足 / 从重启 | `repl-backlog-size` 调大到 256mb+；从节点持久化 offset |
| `MASTERDOWN Link with MASTER is down` | 主节点不可达 | 检查主节点；网络；密码 `masterauth` |
| 主从复制断开 | `repl-timeout` 超时 | `repl-ping-replica-period` 减小；`repl-timeout` 调大 |
| 从节点无法晋升 | `replica-priority=0` | 调整 `replica-priority` > 0 |
| 全量同步阻塞主节点 | fork 大内存 / 网络打满 | 开启 `repl-diskless-sync yes`；错峰添加从节点 |
| 复制认证失败 | `masterauth` 未配置或错误 | 配置 `masterauth`；ACL 用户检查 |
| 从节点 OOM | 从节点写流量过大 | 限制从节点业务读；扩容 |

### 6.5 集群问题

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| `CLUSTERDOWN The cluster is down` | 多节点故障 / 槽未全覆盖 | `CLUSTER NODES` 检查节点状态；恢复故障节点 |
| `CLUSTERDOWN Hash slot not served` | 槽未分配 | `CLUSTER SETSLOT` 手动分配；`redis-cli --cluster fix` |
| 节点间无法通信 | 集群总线端口未开放 | 开放 `port+10000` 端口；检查防火墙 |
| 集群脑裂 | 网络分区 | `cluster-node-timeout` 调整；`min-replicas-to-write` |
| 槽迁移中断 | 节点故障 | `redis-cli --cluster fix`；`CLUSTER SETSLOT slot STABLE` |
| 多 Key 操作失败 | Key 跨槽 | 用 Hash Tag `{tag}` 保证同槽 |
| `cluster-require-full-coverage yes` 导致整体不可用 | 单节点故障 | 评估业务可容忍，设为 `no` |
| 集群扩容慢 | 大量 Key 迁移 | 错峰扩容；用 `redis-cli --cluster reshard` |

### 6.6 大 Key 与热 Key

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| 单 Key 占用 >10KB | Hash/List/Set 过大 | 拆分 Key；用 `UNLINK` 异步删除 |
| 删除大 Key 阻塞主线程 | `DEL` 同步删除 | 用 `UNLINK` 异步删除；分批 `HSCAN`+`HDEL` |
| `redis-cli --bigkeys` 发现大 Key | 业务设计不合理 | 拆分；分桶；冷热分离 |
| 热 Key 导致单点压力 | 热点数据访问集中 | 多副本读；本地缓存；`redis-cli --hotkeys`（LFU） |
| ZSet 大 Key | 排行榜全量数据 | 分桶（按分数区间）；只存 Top N |
| Hash 大 Key | 字段过多 | 分片（按字段哈希）；用 `HSCAN` 避免阻塞 |
| List 大 Key | 队列堆积 | `XTRIM` 或 `LTRIM`；用 Stream + MAXLEN |
| 大 Key 迁移失败 | `MIGRATE` 超时 | 用 `redis-cli --cluster reshard` 或分批迁移 |

### 6.7 慢查询

| 问题 | 可能原因 | 解决方案 |
|------|---------|---------|
| `KEYS *` 阻塞 | 全量扫描 | 用 `SCAN`；禁用 `KEYS`（rename） |
| `SMEMBERS` 大 Set 阻塞 | Set 过大 | 用 `SSCAN`；拆分 Set |
| `HGETALL` 大 Hash 阻塞 | Hash 过大 | 用 `HSCAN`；拆分 Hash |
| `SORT` 大集合阻塞 | 数据量大且未建索引 | 用 ZSet 替代；预排序 |
| `LRANGE 0 -1` 大 List 阻塞 | List 过大 | 分页 `LRANGE 0 99`；用 Stream |
| `FLUSHDB` 阻塞 | 大量 Key 同步删除 | 用 `FLUSHDB ASYNC` |
| `SUNION`/`SINTER` 大集合 | 集合过大 | 拆分；预计算 |
| Lua 脚本执行慢 | 复杂逻辑 | 优化脚本；拆分；用 Functions |
| `DEL` 大 Key 慢 | 同步删除 | 用 `UNLINK`；开启 `lazyfree-lazy-server-del` |

详见 [11 性能调优与监控](../11_性能调优与监控/11_性能调优与监控.md)。

## 七、面试高频问题

### 7.1 原理类

**Q1：Redis 为什么用单线程还这么快？**
纯内存操作（纳秒级）+ IO 多路复用（epoll）+ 高效数据结构（SDS/skiplist/listpack）+ 单线程无锁无上下文切换开销。

**Q2：Redis 6.0 为什么引入多线程？**
网络 IO 成为瓶颈（>10 万 QPS 时），单线程 IO 处理不过来。引入 IO 多线程处理 socket 读写，但命令执行仍单线程，保持简单与无锁。

**Q3：RESP3 协议相比 RESP2 有什么改进？**
支持推送（Push 类型）、客户端缓存（invalidation 通知）、流式响应、二进制安全字符串、Map/Set 等新类型。

**Q4：Redis 的事件循环机制？**
基于 epoll/kqueue 的事件循环：IO 事件 → 命令解析 → 命令执行 → 结果返回。时间事件（如过期清理、统计）穿插在事件循环空闲时执行。

**Q5：Redis 的 SDS 相比 C 字符串有什么优势？**
O(1) 获取长度、二进制安全（不依赖 `\0`）、空间预分配（减少 realloc）、惰性释放、兼容部分 C 字符串函数。

### 7.2 数据类型类

**Q6：Redis 9 大数据类型分别是什么？**
String、List、Hash、Set、ZSet、Bitmap（基于 String）、HyperLogLog（基于 String）、Geo（基于 ZSet）、Stream。模块扩展：RedisJSON、RedisTimeSeries、RedisGraph（**2024 起停止开发**）、RediSearch（Redis 8.0 起内置）。

**Q7：ZSet 为什么用跳表而不是红黑树？**
范围查询 O(logN) 高效、实现简单、内存可控（节点指针数可调）、并发友好（局部锁即可）、适合 ZSet 的核心场景（范围查询 + 排名）。

**Q8：listpack 相比 ziplist 有什么改进？**
listpack 解决了 ziplist 的连锁更新问题（中间节点扩张导致后续节点全部 cascade 更新），更高效、更安全。Redis 7.0 用 listpack 替代 ziplist。

**Q9：Hash 何时从 listpack 转换为 hashtable？**
元素数量 > `hash-max-listpack-entries`（默认 128）或单元素长度 > `hash-max-listpack-value`（默认 64）时转换。

**Q10：Stream 与 Pub/Sub 的区别？**
Stream 持久化（AOF/RDB），支持消费者组、ACK、消息回溯；Pub/Sub 不持久化，消息无 ACK，离线消费者丢失消息。

### 7.3 持久化类

**Q11：RDB 和 AOF 怎么选？**
生产推荐混合持久化：AOF `everysec` 保证数据安全（最多丢 1 秒），RDB 加速恢复。两者同时开启，AOF 文件优先加载（包含 RDB 前导）。

**Q12：AOF 重写过程？**
fork 子进程 → 子进程遍历当前数据生成新 AOF → 父进程继续处理命令并将增量写入 aof_rewrite_buffer → 子进程完成后父进程将 buffer 追加到新 AOF → 原子替换旧文件。

**Q13：fork 为什么会阻塞主线程？**
fork 本身需复制页表（与内存大小成正比），大内存（如 32GB）fork 可能消耗数百毫秒，期间主线程阻塞。优化：限制单实例内存、用副本持久化。

**Q14：混合持久化原理？**
AOF 文件 = RDB 全量快照（前导）+ 增量 AOF 命令。加载时先加载 RDB（快速恢复大部分数据），再回放增量 AOF。兼顾恢复速度与数据安全。

**Q15：appendfsync 三种策略？**
- `always`：每条命令 fsync，最安全但性能差
- `everysec`：每秒 fsync 一次，最多丢 1 秒，生产推荐
- `no`：由 OS 决定，性能好但数据安全无保证

### 7.4 复制与集群类

**Q16：Redis 主从复制过程？**
全量同步：从发送 PSYNC ? -1 → 主 BGSAVE 生成 RDB → 主发送 RDB → 从加载 RDB → 主发送缓冲区命令。
增量同步：从断线重连发送 PSYNC <replid> <offset> → 主检查 backlog 中有 offset → 发送后续命令。

**Q17：Sentinel 故障转移流程？**
1. 主观下线（SDOWN）：单哨兵 ping 超时
2. 客观下线（ODOWN）：≥ quorum 个哨兵确认
3. 选举 Leader 哨兵（Raft）
4. Leader 选新主（优先级 > offset > runid）
5. 提升新主，其他从指向新主

**Q18：Cluster 为什么是 16384 个槽？**
CRC16 是 16 位（65536），但 16384 节点间心跳包大小合适（2KB），且 16384 节点已足够（实际部署远小于）。

**Q19：Cluster 的 Gossip 协议？**
节点间周期性（每秒）交换集群信息（节点状态、槽分布），通过 PING/PONG 传播。Gossip 收敛性保证最终一致。

**Q20：Cluster 多 Key 操作限制？**
多 Key 操作（MGET/MSET/事务/Lua）要求所有 Key 在同一槽。解决方案：Hash Tag `{tag}` 强制同槽（如 `{user:1001}:name` 和 `{user:1001}:age`）。

### 7.5 缓存问题类

**Q21：缓存穿透及解决方案？**
查询不存在数据绕过缓存直击 DB。解决：1）缓存空值（短 TTL）；2）布隆过滤器前置拦截。

**Q22：缓存击穿及解决方案？**
热点 Key 过期瞬间高并发请求直击 DB。解决：1）互斥锁（SETNX）重建缓存；2）热点 Key 永不过期（异步更新）；3）逻辑过期。

**Q23：缓存雪崩及解决方案？**
大量 Key 同时过期或 Redis 宕机。解决：1）TTL 加随机扰动；2）多级缓存；3）Redis 高可用（Sentinel/Cluster）；4）限流降级。

**Q24：缓存与数据库一致性方案？**
- Cache Aside（推荐）：先更新 DB，再删缓存
- 延迟双删：先删缓存 → 更新 DB → 延迟 N 秒再删
- Canal 监听 binlog 异步删缓存（强一致）

**Q25：Cache Aside 为什么是删缓存而不是更新缓存？**
1）避免并发更新顺序问题；2）有些缓存计算复杂，写多读少时浪费；3）删除是幂等的。

### 7.6 分布式锁类

**Q26：Redis 分布式锁如何实现？**
基础：`SET lock:key uuid EX 30 NX`（原子获取）。释放：Lua 脚本判断 UUID 匹配后 DEL（原子释放）。续期：后台线程定期 EXPIRE（看门狗）。

**Q27：Redlock 算法原理？**
向 N 个独立 Redis 实例申请锁，超过半数（N/2+1）成功且耗时小于 TTL，则锁获取成功。解决单点 Redis 主从切换丢锁问题。

**Q28：Redis 分布式锁的问题？**
1）主从切换丢锁（异步复制）；2）时钟漂移（依赖 TTL）；3）网络分区。强一致需求用 Zookeeper 或 etcd。

### 7.7 性能类

**Q29：如何排查 Redis 慢？**
1）`SLOWLOG GET` 查慢命令；2）`INFO commandstats` 查命令统计；3）`LATENCY DOCTOR` 查延迟事件；4）监控 `latest_fork_usec`、`used_memory_rss/used_memory`；5）`CLIENT LIST` 查客户端。

**Q30：Pipeline 的作用与限制？**
批量发送命令减少 RTT，提升吞吐（10 倍以上）。限制：1）非原子（命令间可被其他客户端插入）；2）缓冲区占用内存；3）单次 Pipeline 不宜过大。

**Q31：大 Key 如何处理？**
1）`redis-cli --bigkeys` 扫描；2）`MEMORY USAGE key` 评估；3）拆分（Hash 分桶、List 分段）；4）异步删除 `UNLINK`；5）迁移到其他存储。

**Q32：如何优化 Redis 内存？**
1）选择合适编码（调 `*-listpack-entries`）；2）使用共享对象（小整数）；3）缩短 Key 名；4）设置合理 TTL；5）压缩存储（ziplist/listpack）；6）启用 `activedefrag`。

详见各对应章节。
