# 09 缓存模式与实战

> 缓存模式决定读写策略，穿透/击穿/雪崩三大问题决定系统稳定性，多级缓存与一致性方案是大规模系统的工程必修课。

## 零基础前置认知

**这篇在讲什么**：把 Redis 当缓存用，核心是三件事：**读写姿势**（Cache-Aside：先查缓存、未命中查库回填、写库后删缓存）、**三大危机**（穿透=查不存在的 key 打爆 DB；击穿=热点 key 过期瞬间打爆 DB；雪崩=大量 key 同时过期打爆 DB）、**一致性**（缓存与 DB 怎么避免长期不一致：延迟双删、Canal 订阅 binlog）。读完你能给任意业务写出一套带"空值缓存+互斥锁+随机 TTL"的 Cache-Aside 封装（见 [codes/cache_aside.py](./codes/cache_aside.py) 实测可运行），并说清三种危机的区分。*Write-Through/Write-Behind 属特定场景，懂概念即可。*

> 辅助类比：把缓存想成"点餐柜台前的今日菜单小黑板"——**Cache-Aside** 是"先看黑板，没有就问后厨（DB），同时把答案写黑板上；后厨改菜就擦黑板"（读多写少的默认姿势）；**穿透** 是"客人问的菜菜单和后厨都没有，还每次都去问后厨"（恶意/无效查询打爆后厨 → 黑板记"这道菜没有"=空值缓存，或门口放价目总表=布隆过滤器）；**击穿** 是"招牌菜刚好擦掉的那几秒，全店客人同时冲进后厨问"（→ 后厨门口放"正在问，别重复进"的牌子=互斥锁）；**雪崩** 是"打烊时所有黑板同时被擦掉，客人都冲进后厨"（→ 错开擦黑板时间=随机 TTL）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| Cache-Aside | 旁路缓存：查缓存→未命中查库回填；写库后删缓存 | 最常用模式；写后删缓存是防不一致关键 |
| 缓存穿透 | 查询数据库中也不存在的 key，请求绕过缓存直打 DB | 解法：空值缓存（短 TTL）/ 布隆过滤器 / 入参校验 |
| 缓存击穿 | 单个热点 key 过期瞬间的高并发重建请求 | 解法：互斥锁（SET NX）/ 永不过期 / 逻辑过期 |
| 缓存雪崩 | 大量 key 同时过期（或 Redis 宕机）导致 DB 被打满 | 解法：随机 TTL + 多级缓存 + 限流降级 |
| 布隆过滤器 | 概率型"是否存在"结构：不存在必然返回不存在 | Redis 8 内置 Bloom 模块（旧版需 redis-stack）；0.1% 误判率可配 |
| 延迟双删 | 删缓存→写库→延迟 N ms→再删缓存 | 修补"读回旧值写缓存"的并发窗口 |
| Canal | MySQL binlog 订阅工具，DB 变更 → 消息 → 删缓存 | 与业务解耦的最终一致方案（binlog 需 ROW 格式） |
| 预热 / 降级 | 启动/低峰灌热点 / Redis 故障走 DB 兜底 | 预热配合 Pipeline 批量；降级配合熔断器防 DB 被打穿 |

> 区分/注意：**穿透/击穿/雪崩要分清"谁是倒霉的"**——穿透是"查的不存在"全部打库；击穿是"一个热点 key 过期"打库；雪崩是"一批 key 同时过期"打库——解法完全不同（前置过滤器 / 单点锁 / 随机 TTL），混用是面试与技术债的重灾区。**"先删缓存后写 DB" 是被废弃的错误姿势**，标准是"先写 DB 再删缓存"（写后删）。**布隆过滤器有误判**：它保证"说不存在就不存在、说存在可能不存在"——只能用来拦截确定不存在的请求，不能代替缓存本身。

## 一、缓存模式对比

### 1.1 四种缓存模式总览

```
1. Cache-Aside（旁路缓存，最常用）
┌────────┐    1.查缓存    ┌────────┐
│  应用   │ ──────────────► │ Redis  │
│        │ ◄── 2.命中返回 ── │        │
│        │                  └────────┘
│        │ 3.未命中
│        │ ──────────────► ┌────────┐
│        │ ◄── 4.查询DB ── │  DB    │
│        │ ──────────────► │        │
│        │ 5.写入缓存       └────────┘
└────────┘

2. Read-Through / Write-Through（穿透缓存）
┌────────┐                    ┌────────────┐
│  应用   │ ──读/写──────────► │ 缓存层     │ ──同步──► DB
│        │ ◄──数据─────────── │ (代理DB)   │ ◄──同步──
└────────┘                    └────────────┘

3. Write-Behind（异步写入）
┌────────┐  写缓存    ┌────────────┐  异步批量  ┌────────┐
│  应用   │ ────────► │ 缓存层     │ ────────► │  DB    │
│        │ ◄──成功── │            │           │        │
└────────┘           └────────────┘           └────────┘
```

### 1.2 四种模式对比表

| 模式 | 读策略 | 写策略 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|--------|--------|------|--------|----------|
| Cache-Aside | 先缓存后 DB | 先 DB 后删缓存 | 较好 | 高 | 低 | 大多数业务（推荐） |
| Read-Through | 应用只读缓存 | 同 Write-Through | 好 | 高 | 中 | 缓存层封装完善 |
| Write-Through | 同 Read-Through | 同步写缓存+DB | 强 | 中 | 中 | 一致性要求高 |
| Write-Behind | 同 Read-Through | 先写缓存，异步批量写 DB | 弱 | 最高 | 高 | 写多读少、容忍丢数据 |

### 1.3 Cache-Aside 并发问题剖析

```
方案 A：先删缓存后更新 DB（不推荐）
时间线：
T1  线程A 删除缓存
T2  线程B 读缓存未命中，查 DB（旧值）
T3  线程B 将旧值写入缓存
T4  线程A 更新 DB（新值）
结果：缓存=旧值，DB=新值，长时间不一致

方案 B：先更新 DB 后删缓存（推荐）
T1  线程A 更新 DB（新值）
T2  线程A 删除缓存
T3  线程B 读缓存未命中，查 DB（新值）
T4  线程B 写入缓存（新值）
结果：一致

极端并发场景（方案 B 也可能不一致）：
T0  缓存过期
T1  线程B 读 DB（旧值）
T2  线程A 更新 DB（新值）
T3  线程A 删除缓存
T4  线程B 将旧值写入缓存
结果：缓存=旧值（概率极低，因为读 DB 通常远快于写 DB）
```

## 二、缓存三大问题

### 2.1 缓存穿透

**问题**：查询不存在的数据，请求绕过缓存直接打到数据库，可能被恶意利用。

```
客户端 → 缓存（未命中）→ 数据库（未命中）→ 返回空
                ↑                          │
                └── 不写入缓存 ←────────────┘
                （下次仍穿透）
```

**解决方案矩阵**：

| 方案 | 实现 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 缓存空值 | `SET user:9999 "NULL" EX 60` | 简单、实时 | 占内存、可能短期不一致 | 数据偶尔不存在 |
| 布隆过滤器 | 应用层前置，不存在直接返回 | 内存极省、查询 O(1) | 误判率、删除困难 | 数据稳定的大规模查询 |
| 接口层校验 | 拦截非法 ID（如负数） | 简单 | 业务耦合 | 入参可识别恶意 |

```bash
# 方案 1：缓存空值（短 TTL，建议 60 秒）
SET user:9999 "NULL" EX 60

# 方案 2：布隆过滤器（Redis 8.0 起 Bloom 模块内置；旧版需 Redis Stack）
# 创建布隆过滤器（容量 100 万，误判率 0.1%）
BF.RESERVE user_filter 0.001 1000000

# 用户写入 DB 时同步加入过滤器
BF.ADD user_filter "user1001"

# 查询前先检查
BF.EXISTS user_filter "user9999"
# 返回 0 → 一定不存在，直接返回，不查 DB
# 返回 1 → 可能存在，继续查缓存和 DB
```

```python
import redis
import random

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class CacheAside:
    def __init__(self, redis_client: redis.Redis, default_expire: int = 3600):
        self.redis = redis_client
        self.default_expire = default_expire

    def get(self, key: str, db_query) -> str | None:
        value = self.redis.get(key)
        if value == "NULL":
            return None  # 空值缓存命中
        if value is not None:
            return value
        # 未命中查 DB
        value = db_query(key)
        if value is not None:
            # 随机过期，防雪崩
            expire = self.default_expire + random.randint(0, 300)
            self.redis.set(key, value, ex=expire)
        else:
            # 穿透防护：缓存空值
            self.redis.set(key, "NULL", ex=60)
        return value

    def set(self, key: str, value: str, expire: int | None = None):
        self.redis.set(key, value, ex=expire or self.default_expire)

    def delete(self, key: str):
        self.redis.delete(key)

    def invalidate_after_write(self, key: str, db_write, value: str):
        """写后失效：先更新 DB，再删缓存"""
        db_write(key, value)
        self.redis.delete(key)
```

### 2.2 缓存击穿

**问题**：热点 Key 过期瞬间，大量并发请求同时打到数据库重建缓存。

```
缓存击穿时序：
T0  热点 key 过期
T1  线程 A 查缓存未命中，查 DB
T2  线程 B 查缓存未命中，查 DB
T3  线程 C 查缓存未命中，查 DB
... N 个线程同时打 DB
```

**解决方案**：

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| 互斥锁 | `SET lock:hot NX EX 10`，获取锁者重建缓存 | 简单可控 | 锁等待增加延迟 |
| 永不过期 | 热点 key 不设 TTL，由后台异步更新 | 性能最佳 | 数据短暂不一致 |
| 逻辑过期 | value 内嵌过期字段，过期后异步重建 | 不阻塞请求 | 短暂脏数据 |

```python
import redis
import time
import uuid

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

# 互斥锁重建缓存
LOCK_SCRIPT = """
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'EX', ARGV[2]) then
    return 1
end
return 0
"""

UNLOCK_SCRIPT = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
"""

class HotKeyCache:
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.lock_sha = self.redis.script_load(LOCK_SCRIPT)
        self.unlock_sha = self.redis.script_load(UNLOCK_SCRIPT)

    def get(self, key: str, db_query, ttl: int = 3600) -> str | None:
        value = self.redis.get(key)
        if value is not None:
            return value
        # 未命中，尝试获取互斥锁
        lock_key = f"lock:{key}"
        lock_id = uuid.uuid4().hex
        acquired = self.redis.evalsha(self.lock_sha, 1, lock_key, lock_id, "10")
        if acquired:
            try:
                # 双重检查（可能已被其他线程重建）
                value = self.redis.get(key)
                if value is not None:
                    return value
                # 查 DB 重建缓存
                value = db_query(key)
                if value is not None:
                    self.redis.set(key, value, ex=ttl)
                return value
            finally:
                self.redis.evalsha(self.unlock_sha, 1, lock_key, lock_id)
        else:
            # 未获锁，短暂等待后重试读缓存
            time.sleep(0.1)
            return self.redis.get(key)

cache = HotKeyCache(r)
def query_db(key):
    return f"value_of_{key}"

print(cache.get("hot:product:1", query_db))
```

### 2.3 缓存雪崩

**问题**：大量 Key 同时过期或 Redis 宕机，请求全部打到数据库。

**解决方案**：

| 场景 | 方案 | 实现 |
|------|------|------|
| 大量 key 同时过期 | 随机过期时间 | `EXPIRE key (3600 + random(0, 300))` |
| Redis 宕机 | 多级缓存 | L1 本地 + L2 Redis + L3 DB |
| Redis 宕机 | 限流降级 | 应用层限流，DB 直接返回兜底数据 |
| 集群故障 | 高可用 | Sentinel/Cluster 自动故障转移 |

```bash
# 方案 1：随机过期时间（防雪崩基础）
SET product:1:name "iPhone 15" EX 3600
SET product:2:name "iPhone 14" EX 3660
SET product:3:name "iPhone 13" EX 3720
# 业务代码中：expire = base + random(0, max_jitter)

# 方案 2：核心数据永不过期，由后台更新
SET config:app "..."    # 不设置 EX
```

### 2.4 三大问题对比表 + 解决方案矩阵

| 问题 | 触发条件 | 直接原因 | 核心解法 | 兜底方案 |
|------|----------|----------|----------|----------|
| 穿透 | 查询不存在的 key | 缓存未命中 + DB 未命中 | 布隆过滤器 / 空值缓存 | 接口层校验 |
| 击穿 | 热点 key 过期 | 高并发 + 单点重建 | 互斥锁 / 永不过期 | 逻辑过期 + 异步刷新 |
| 雪崩 | 大量 key 同时过期 / Redis 宕机 | 缓存批量失效 | 随机过期 + 多级缓存 | 限流降级 + 集群高可用 |

## 三、缓存一致性

### 3.1 四种一致性策略

```
策略 1：Cache-Aside（先更新 DB，后删缓存，推荐）
┌────────┐                    ┌────────┐
│  应用   │ ──1.更新DB──────► │  DB    │
│        │ ◄─2.返回成功────── │        │
│        │ ──3.删除缓存─────► │ Redis  │
└────────┘                    └────────┘
优点：实现简单，一致性较好
缺点：删除缓存失败会导致不一致
适用：大多数场景

策略 2：先删缓存，后更新 DB（不推荐）
┌────────┐                    ┌────────┐
│  应用   │ ──1.删除缓存─────► │ Redis  │
│        │ ──2.更新DB──────► │  DB    │
└────────┘                    └────────┘
缺点：并发时可能读到旧数据写入缓存
适用：一致性要求不高

策略 3：延迟双删
┌────────┐                    ┌────────┐
│  应用   │ ──1.删除缓存─────► │ Redis  │
│        │ ──2.更新DB──────► │  DB    │
│        │ ──3.延迟 N 毫秒───►│        │
│        │ ──4.再次删除缓存─► │ Redis  │
└────────┘                    └────────┘
优点：解决策略 2 的并发问题
缺点：延迟时间难以确定（通常 500ms-1s）
适用：中等一致性要求

策略 4：Canal 订阅 binlog 异步更新
┌────────┐  Binlog  ┌───────┐  消息  ┌────────┐
│  DB    │ ────────►│ Canal │ ─────► │  应用   │ ──删除缓存──► Redis
└────────┘          └───────┘        └────────┘
优点：最终一致性保证强，业务与缓存解耦
缺点：架构复杂，引入 Canal + MQ
适用：强一致性、大规模系统
```

### 3.2 策略对比表

| 策略 | 一致性 | 复杂度 | 性能影响 | 推荐场景 |
|------|--------|--------|---------|---------|
| Cache-Aside | 较好 | 低 | 低 | 大多数业务 |
| 先删后更新 | 一般 | 低 | 低 | 不推荐 |
| 延迟双删 | 好 | 中 | 中 | 中等一致性 |
| Canal 监听 | 最好 | 高 | 低 | 强一致性 |

### 3.3 延迟双删实现

```python
import redis
import threading
import time

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class DelayDoubleDeleteCache:
    def __init__(self, redis_client: redis.Redis, delay_ms: int = 500):
        self.redis = redis_client
        self.delay_ms = delay_ms

    def update(self, key: str, db_update, value: str):
        # 1. 第一次删除缓存
        self.redis.delete(key)
        # 2. 更新 DB
        db_update(key, value)
        # 3. 延迟后再次删除（异步，不阻塞主流程）
        def second_delete():
            time.sleep(self.delay_ms / 1000)
            self.redis.delete(key)
        threading.Thread(target=second_delete, daemon=True).start()

# 延迟时间设置依据：
# - 应大于一次 DB 读写耗时（通常 50-200ms）
# - 加上读线程写回缓存的耗时（通常 50ms）
# - 综合建议 500ms-1s
```

### 3.4 Canal binlog 方案架构

```
完整架构：
┌─────────┐   写入    ┌─────────┐  binlog  ┌─────────┐  消息   ┌─────────┐
│ 业务应用 │ ────────► │  MySQL  │ ────────►│  Canal  │ ───────►│  MQ     │
└─────────┘           └─────────┘          └─────────┘         └────┬────┘
                                                                    │
                              ┌─────────────────────────────────────┘
                              ▼
                         ┌─────────┐  删除缓存   ┌─────────┐
                         │ 缓存消费者│ ──────────►│  Redis  │
                         └─────────┘             └─────────┘

优势：
1. 业务代码不感知缓存（彻底解耦）
2. 严格按 DB 提交顺序失效缓存
3. 失败可重试（MQ 保证至少一次）
4. 支持多实例消费（一致性 hash 分配 key）

注意：
1. Canal 本身需要高可用（HA）
2. binlog 必须是 ROW 格式
3. 消费者处理需幂等（重复删除无害，但需考虑）
```

## 四、多级缓存

### 4.1 多级缓存架构

```
┌─────────────────────────────────────────────────────────┐
│                    多级缓存架构                          │
│                                                          │
```

### 4.2 L1 本地缓存选型

| 方案 | 特点 | 适用 |
|------|------|------|

### 4.3 L1 + L2 多级缓存实现

```python
import redis
import time
import random
from functools import wraps

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

# L1：进程内缓存（生产建议替换为 cachetools / 自实现 W-TinyLFU）
class L1Cache:
    def __init__(self, max_size: int = 10000):
        self._store = {}
        self._expire = {}
        self.max_size = max_size

    def get(self, key: str):
        if key in self._store:
            if self._expire[key] > time.time():
                return self._store[key]
            del self._store[key]
            del self._expire[key]
        return None

    def set(self, key: str, value: str, ttl: int = 60):
        if len(self._store) >= self.max_size:
            # 简单 FIFO 淘汰（生产用 LRU/LFU）
            oldest = next(iter(self._store))
            del self._store[oldest]
            del self._expire[oldest]
        self._store[key] = value
        self._expire[key] = time.time() + ttl

    def delete(self, key: str):
        self._store.pop(key, None)
        self._expire.pop(key, None)

class MultiLevelCache:
    """L1 本地 + L2 Redis + L3 DB"""
    def __init__(self, redis_client: redis.Redis, l1_ttl: int = 60, l2_ttl: int = 3600):
        self.redis = redis_client
        self.l1 = L1Cache()
        self.l1_ttl = l1_ttl
        self.l2_ttl = l2_ttl

    def get(self, key: str, db_query) -> str | None:
        # L1 本地缓存
        value = self.l1.get(key)
        if value is not None:
            return value
        # L2 Redis
        value = self.redis.get(key)
        if value is not None:
            # 回填 L1（短 TTL）
            self.l1.set(key, value, ttl=self.l1_ttl)
            return value
        # L3 DB
        value = db_query(key)
        if value is not None:
            expire = self.l2_ttl + random.randint(0, 300)
            self.redis.set(key, value, ex=expire)
            self.l1.set(key, value, ttl=self.l1_ttl)
        return value

    def invalidate(self, key: str):
        """失效时同时删 L1 和 L2"""
        self.l1.delete(key)
        self.redis.delete(key)

# 使用
cache = MultiLevelCache(r)
def query_db(key):
    return f"db_value_of_{key}"

print(cache.get("user:1001", query_db))
cache.invalidate("user:1001")
```

### 4.4 多级缓存一致性难点

```
多实例下 L1 缓存一致性问题：

实例A 写入：
1. 更新 DB
2. 删除自己的 L1
3. 删除 Redis（L2）
   ↓
实例B 的 L1 仍持有旧值 ← 问题！

解决方案：
1. Redis Pub/Sub 广播失效消息
   ┌─────────┐  PUBLISH invalidate:user:1001  ┌─────────┐
   │ 实例 A  │ ──────────────────────────────►│ 实例 B  │ → 删除本地 L1
   └─────────┘                                └─────────┘

2. Redis 6.0+ Client-Side Cache（推荐）
   ┌─────────┐  GET key                          ┌─────────┐
   │ 实例 A  │ ─────────────────────────────────►│  Redis  │
   │         │ ◄── value + tracking ─────────────│         │
   └─────────┘                                    └────┬────┘
                                                      │ key 修改时
                                                      ▼
                                                ┌─────────┐
                                                │ 实例 A  │ ← 收到 invalidation 消息
                                                └─────────┘
```

## 五、缓存预热与降级

### 5.1 缓存预热

```python
import redis
import logging

r = redis.Redis(host="localhost", port=6379, decode_responses=True)
logger = logging.getLogger(__name__)

class CacheWarmup:
    """系统启动或低峰期预热热点数据"""
    def __init__(self, redis_client: redis.Redis, batch_size: int = 500):
        self.redis = redis_client or r
        self.batch_size = batch_size

    def warmup_products(self, db_query_all):
        """预热商品列表（Pipeline 批量）"""
        products = db_query_all()
        with self.redis.pipeline() as pipe:
            for i, (pid, name) in enumerate(products):
                pipe.set(f"product:{pid}:name", name, ex=3600)
                if i % self.batch_size == 0 and i > 0:
                    pipe.execute()
            pipe.execute()
        logger.info(f"预热完成，共 {len(products)} 条")

    def warmup_leaderboard(self, db_query_scores):
        """预热排行榜（ZADD 批量）"""
        scores = db_query_scores()
        mapping = {user: score for user, score in scores}
        self.redis.zadd("leaderboard:game", mapping)
        logger.info(f"排行榜预热 {len(mapping)} 条")
```

### 5.2 缓存降级

```python
import redis
import time
import logging

r = redis.Redis(host="localhost", port=6379, decode_responses=True)
logger = logging.getLogger(__name__)

class CacheDegrade:
    """Redis 异常时的降级策略"""
    def __init__(self, redis_client: redis.Redis, fallback_ttl: int = 300):
        self.redis = redis_client
        self.fallback_ttl = fallback_ttl
        self.circuit_open = False
        self.failure_count = 0
        self.threshold = 5  # 连续失败 5 次熔断

    def _check_circuit(self):
        """简单熔断：连续失败 N 次后短路"""
        return self.circuit_open

    def _record_failure(self):
        self.failure_count += 1
        if self.failure_count >= self.threshold:
            self.circuit_open = True
            logger.error("Redis 熔断开启，进入降级模式")

    def _record_success(self):
        if self.circuit_open:
            self.circuit_open = False
            self.failure_count = 0
            logger.info("Redis 恢复，熔断关闭")

    def get_with_fallback(self, key: str, db_query, fallback_value=None):
        # 熔断中：直接走 DB / 兜底
        if self.circuit_open:
            if fallback_value is not None:
                return fallback_value
            return db_query(key)

        try:
            value = self.redis.get(key)
            if value is not None:
                self._record_success()
                return value
        except redis.RedisError as e:
            logger.warning(f"Redis 异常: {e}")
            self._record_failure()

        # 降级到 DB
        return db_query(key)
```

## 小思考题帮你巩固

1. **为什么缓存更新要"先写 DB 再删缓存"，而不是"先删缓存再写 DB"？**（提示：先删后写会让"读旧值→写回缓存"的窗口亲手把旧值放回去，见 1.3。）
2. **缓存穿透、击穿、雪崩各自的"灾难主体"分别是什么？分别用什么核心手段？**（提示：不存在数据 / 单个热点 key 过期 / 一批 key 同时过期；过滤器+空值 / 互斥锁或永不过期 / 随机 TTL+多级缓存，见二。）
3. **Cache-Aside 中"删缓存失败"会导致什么？怎么保证删一定生效？**（提示：缓存长期是旧值；重试（消息队列异步重删）或延迟双删兜底，见 3.1/3.3。）
4. **延迟双删为什么"第二次删除"要延迟？延迟多久合理？**（提示：要给"读旧值→写回缓存"的并发窗口留出时间；通常 ≥ 一次 DB 读写 + 写回耗时（约 500ms-1s），见 3.3。）
5. **布隆过滤器为什么只能证明"不存在"，不能证明"存在"？误判率由什么决定？**（提示：哈希位都存在可能来自不同 key 的碰撞；`BF.RESERVE` 的容量与误判率决定位数组大小，位数越多误判越低，见 2.1。）

<details>
<summary>参考答案（点击展开）</summary>

1. 先删后写存在经典窗口：线程删缓存 → 线程 B 读 DB（旧值）→ 线程 A 写 DB（新值）→ 线程 B 把旧值写回缓存，缓存长期旧值。先写 DB 再删缓存，窗口只剩"读 DB 比写 DB 慢"的极端并发（概率极低），且写后删的删除动作可重试——这就是 Cache-Aside 的标准姿势。
2. 穿透="查一个库里也不存在的 key"整批打 DB → 空值缓存（短 TTL）+ 布隆过滤器 + 入参校验；击穿="单个热点 key 过期瞬间"的高并发重建 → 互斥锁（SET NX EX，谁拿到锁谁重建，双检）+ 永不过期/逻辑过期；雪崩="大量 key 同一时刻过期"（或 Redis 宕机）→ 随机 TTL 抖动 + 多级缓存 + 限流降级 + 集群高可用。
3. 删缓存失败（如 Redis 瞬时抖）会让缓存长期保留旧值 → 数据库新值读不出来。保证手段：删除动作放入消息队列异步重试；或直接上延迟双删（第二次删再兜一次）；数据强一致场景用 Canal binlog 推动。
4. 第二次删除必须等"所有可能把旧值写回缓存的并发读完成"——即"读旧值→写缓存"的窗口走完。延迟量一般取 ≥ 一次 DB 读写（50-200ms）+ 写回耗时（50ms），工程常用 500ms-1s；太短挡不住慢查询的读、太长放大不一致窗口。
5. 布隆过滤器对每个 key 哈希到若干位；多个 key 的位可能重叠（碰撞），所以"位都为 1"不能证明该 key 一定存在，只能证明"大概率存在"。误判率由容量 size 与哈希次数（依 error_rate 推算）决定：`BF.RESERVE key error_rate capacity` 预分配足够位数组，误判越低位数组越大。

</details>

## 六、生产实战要点

### 6.1 缓存设计原则

| 原则 | 说明 |
|------|------|
| Key 命名规范 | `业务:实体:ID:字段`，如 `order:1001:detail` |
| TTL 分层 | 配置类长 TTL（24h），动态类短 TTL（5-30min） |
| 随机抖动 | 所有 TTL 加 0-300 秒随机，防雪崩 |
| 大 Value 拆分 | 单 value < 10KB，大对象拆 Hash 或分片 |
| 慢查询规避 | 禁用 KEYS，用 SCAN；大 Hash 用 HSCAN |
| 监控指标 | 命中率、内存使用、QPS、慢查询、BigKey |

### 6.2 缓存命中率监控

```python
import redis
import time

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

class CacheMetrics:
    def __init__(self):
        self.hits = 0
        self.misses = 0

    def record(self, hit: bool):
        if hit:
            self.hits += 1
        else:
            self.misses += 1

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total > 0 else 0.0

metrics = CacheMetrics()

def cached_get(key: str, db_query):
    value = r.get(key)
    if value is not None:
        metrics.record(hit=True)
        return value
    metrics.record(hit=False)
    value = db_query(key)
    if value is not None:
        r.set(key, value, ex=3600)
    return value
```
