# 12 安全与运维

> 系统化梳理 Redis 7+ 安全运维体系：从 requirepass 全局密码、ACL 细粒度权限、网络隔离与危险命令禁用，到 TLS 加密通信、RDB/AOF 备份恢复、redis-shake 迁移、滚动升级与运维 SOP，附 20+ 项安全检查清单与 Redis vs MySQL 安全运维对比。

## 零基础前置认知

**这篇在讲什么**：Redis 安全与运维分两层——**开发必须懂的一层**是"怎么连得安全、权限怎么收"（requirepass/ACL/bind+TLS 连接/危险命令禁用），**运维才折腾的一层**是"备份恢复/升级/SOP"（本章 12.5-12.7，开发可跳读，完整见 99 附录）。读完你能给应用配一个"最小权限账号"、用 TLS 安全连接 Redis、在开发机上跑一遍"20 项安全检查清单"。*ACL/TLS 连接是开发高频，本篇重点展开；备份/升级/运维 SOP 归运维向，标注"可跳过"并在 99 附录有完整承接。*

> 辅助类比：把 Redis 安全想成"公司门禁系统"——**requirepass** 是"大门统一密码"（全库一把锁，粗粒度）；**ACL** 是"按岗位发门禁卡"（用户→命令→key 三维授权：张三只能 GET 某些 key、李四能写、管理员全通）；**bind + protected-mode** 是"门禁只装在本楼"（默认只本机可连，别把 0.0.0.0 暴露到公网）；**rename-command** 是"把危险工具（KEYS/FLUSHALL）藏起来加口令"（防误用防入侵者）；**TLS** 是"走加密专线"（防窃听、防中间人）；**备份/升级/演练** 是"灾备与例行维护"（运维的活）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| requirepass | 全局认证密码（`CONFIG SET requirepass`，重启写 conf） | 最粗粒度；与 ACL 并存时以 ACL 用户为准 |
| ACL | 访问控制列表：用户×(命令)×(key) 三维权限 | `ACL SETUSER` 创建最小权限用户；`ACL LOG` 审计 |
| bind / protected-mode | 监听地址 / 保护模式（默认仅本机+无密码拒外连） | 暴露 0.0.0.0 + 无密码 = 引狼入室（扫到即打穿） |
| rename-command | 把危险命令（KEYS/FLUSHALL/DEBUG）改名或禁用 | 老式"藏钥匙"手段；ACL 推出后更推荐规则禁 |
| TLS | 传输加密（`tls-port`/`tls-cert-file`…，6.0+） | 防窃听/中间人；客户端要配 `ssl=True`/cafile |
| 危险命令 | KEYS/FLUSHALL/DEBUG/SHUTDOWN/CONFIG 等 | 误用或入侵者利用；开发自查清单必检项 |
| 备份/升级/SOP | RDB/AOF 备份、滚动升级、故障处置流程（运维向） | 本章 12.5-12.7 浓缩，完整承接于 99 附录 |

> 区分/注意：**requirepass ≠ ACL**——requirepass 是"一个全库密码"，ACL 是"多用户细粒度授权"（用户/密码/命令/key 三维），且二者并存时 ACL 优先；ACL 还能做"只读用户/只允许某 key 前缀"这类最小权限，是生产多业务共用的首选。**bind 与 protected-mode 是两个开关**：`bind 127.0.0.1` 只监听本机；`protected-mode yes` 在"无密码 + 非本机连接"时拒绝——两者配合别只开一个。**TLS 是传输层加密，不替代认证**：TLS 防"被偷听/篡改"，ACL/密码防"被登入"，别混为一谈。

## 12.1 认证与访问控制

### 12.1.1 安全模型演进

```
Redis 安全模型演进：
┌─────────────────────────────────────────────────────────────┐
│ Redis 2.x~5.x：仅 requirepass 全局密码                      │
│   ├── 所有认证通过的客户端拥有全部权限                       │
│   ├── 无法限制特定用户只能执行特定命令                       │
│   └── 无法限制特定用户访问特定 key                           │
├─────────────────────────────────────────────────────────────┤
│ Redis 6.0+：ACL 访问控制列表                                │
│   ├── 多用户，每用户独立配置                                 │
│   ├── 可限制可执行命令（command / @category）                │
│   ├── 可限制可访问 key（pattern）                            │
│   ├── 可限制 Pub/Sub channel                                │
│   └── 默认用户 default（配密码则全权限，向后兼容）           │
├─────────────────────────────────────────────────────────────┤
│ Redis 6.0+：TLS 传输加密                                    │
│   └── 链路层加密，防窃听篡改                                 │
└─────────────────────────────────────────────────────────────┘
```

### 12.1.2 requirepass 全局密码

```bash
# 运行时设置（明文，重启失效）
CONFIG SET requirepass "your_strong_password"

# 客户端认证
AUTH your_strong_password
# 6.0+ 支持用户名：AUTH default your_strong_password

# 查看密码配置
CONFIG GET requirepass

# 持久化到 redis.conf（推荐）
# requirepass your_strong_password
```

注意：requirepass 等同于设置 default 用户的密码，与 ACL 共存。生产环境强烈建议改用 ACL 多用户模型。

### 12.1.3 ACL 规则语法

```
ACL 规则语法：
user <username> on|off >password ~pattern %R~pattern %W~pattern +@category +command -@category -command allkeys allchannels allcommands resetkeys

字段说明：
├── on/off             启用/禁用用户
├── >password          设置密码（明文，会被 SHA256 存储）
├── <password          移除密码
├── ~pattern           允许访问的 key 模式（读写均允许）
├── %R~pattern         仅允许读的 key 模式（7.0+）
├── %W~pattern         仅允许写的 key 模式（7.0+）
├── &pattern           允许的 Pub/Sub channel 模式（6.2+）
├── +@category         允许命令类别
├── -@category         禁止命令类别
├── +command           允许特定命令
├── -command           禁止特定命令
├── allcommands        等同 +@all
├── allkeys            等同 ~*
├── allchannels        等同 &*
├── resetkeys          重置 key 模式
├── resetpass          清空所有密码
└── reset              完全重置用户

命令类别（@category）：
├── @admin      管理命令（CONFIG, SHUTDOWN 等）
├── @write      写命令（SET, DEL 等）
├── @read       读命令（GET, HGET 等）
├── @dangerous  危险命令（FLUSHALL, DEBUG 等）
├── @string     String 类型命令
├── @hash       Hash 类型命令
├── @list       List 类型命令
├── @set        Set 类型命令
├── @sortedset  Sorted Set 类型命令
├── @pubsub     发布订阅命令
├── @keyspace   键空间命令
├── @connection 连接命令（AUTH, SELECT 等）
└── @scripting  脚本命令（EVAL, FUNCTION 等）
```

### 12.1.4 ACL 实战

```bash
# 1. 查看所有用户
ACL LIST

# 2. 查看当前用户
ACL WHOAMI

# 3. 查看指定用户详情
ACL GETUSER readonly_user

# 4. 创建只读用户（仅允许读，禁止写/管理/危险）
ACL SETUSER readonly_user on >readonly_pass ~* +@read -@write -@admin -@dangerous

# 5. 创建只能访问特定 key 前缀的用户
ACL SETUSER app_user on >app_pass ~app:* +@read +@write -@admin -@dangerous

# 6. 创建只读特定前缀的监控用户（7.0+ 精细化读写分离）
ACL SETUSER app_reader on >reader_pass %R~app:* +@read -@admin -@dangerous

# 7. 创建只能执行监控命令的用户
ACL SETUSER monitor on >monitor_pass ~* +INFO +PING +CLIENT +SLOWLOG +LATENCY

# 8. 创建业务写用户（限定 key 前缀，禁用危险命令）
ACL SETUSER biz_writer on >biz_pass ~biz:cache:* ~biz:lock:* +@read +@write +@connection -@admin -@dangerous -@scripting

# 9. 禁用某命令（即使 +@all 也排除）
ACL SETUSER limited on >limited_pass allkeys allcommands -FLUSHALL -FLUSHDB -CONFIG -KEYS -DEBUG

# 10. 删除用户
ACL DELUSER readonly_user

# 11. 持久化 ACL 到文件
CONFIG SET aclfile /etc/redis/users.acl
ACL SAVE

# 12. 从文件重载 ACL
ACL LOAD

# 13. 查看命令所属类别（辅助编写 ACL）
ACL CAT                      # 列出所有类别
ACL CAT @dangerous           # 列出 @dangerous 类别下所有命令
```

### 12.1.6 Python ACL 管理

```python
import redis

admin = redis.Redis(host="localhost", port=6379,
                    username="default", password="your_strong_password",
                    decode_responses=True)


def create_redis_user(admin_client: redis.Redis, username: str,
                      password: str, key_pattern: str = "*",
                      commands: str = "+@read -@write -@admin -@dangerous") -> None:
    """创建 ACL 用户，遵循最小权限原则"""
    acl_rule = f"on >{password} ~{key_pattern} {commands}"
    admin_client.acl_setuser(username, acl_rule)
    print(f"用户 {username} 创建成功")


def verify_user(admin_client: redis.Redis, username: str) -> dict:
    """查看用户权限详情"""
    info = admin_client.acl_getuser(username)
    return {
        "flags": info.get("flags", []),
        "passwords": len(info.get("passwords", [])),
        "commands": info.get("commands", []),
        "keys": info.get("keys", []),
    }


# 创建多个业务方账号
create_redis_user(admin, "app_reader", "reader_pass", "app:*",
                  "+@read -@write -@admin -@dangerous")
create_redis_user(admin, "app_writer", "writer_pass", "app:*",
                  "+@read +@write -@admin -@dangerous")
create_redis_user(admin, "monitor", "monitor_pass", "*",
                  "+INFO +PING +CLIENT +SLOWLOG +LATENCY")

# 验证只读用户尝试写操作会被拒绝
reader = redis.Redis(host="localhost", port=6379,
                     username="app_reader", password="reader_pass",
                     decode_responses=True)
reader.get("app:test")      # 成功
try:
    reader.set("app:test", "x")  # NOPERM 此 user 无执行权限
except redis.exceptions.ResponseError as e:
    print(f"权限拦截符合预期: {e}")
```

## 12.2 网络安全

### 12.2.1 网络隔离最佳实践

```
网络分层隔离：
┌─────────────────────────────────────────────────────────┐
│ 公网（Internet）                                         │
│   │  ❌ 禁止 6379 暴露公网                                │
└───┼─────────────────────────────────────────────────────┘
    │ 防火墙 / 安全组仅放行 80/443
┌───▼─────────────────────────────────────────────────────┐
│ DMZ 区（应用服务器）                                     │
│   ├── Nginx / API Gateway                                │
│   └── 应用进程 → 通过内网访问 Redis                       │
└───┬─────────────────────────────────────────────────────┘
    │ 内网（10.0.0.0/8 或 172.16.0.0/12）
┌───▼─────────────────────────────────────────────────────┐
│ 数据区（Redis 实例）                                     │
│   ├── bind 10.0.0.1（仅内网 IP）                         │
│   ├── protected-mode yes                                 │
│   ├── requirepass / ACL                                  │
│   └── iptables 仅允许应用服务器 IP 访问 6379              │
└─────────────────────────────────────────────────────────┘
```

| 措施 | 配置 | 说明 |
|------|------|------|
| 绑定 IP | `bind 10.0.0.1` | 仅绑定内网，禁 `bind 0.0.0.0` 暴露公网 |
| 保护模式 | `protected-mode yes` | 未设密码且 bind 0.0.0.0 时仅允许本地连接 |
| 修改端口 | `port 6380` | 降低被扫描概率（非安全主要手段） |
| 防火墙 | iptables / 安全组 | 仅允许应用服务器 IP 访问 |
| 集群总线 | `cluster-bus-port 16380` | 客户端端口 + 10000，需同步放行 |
| TLS | `tls-port 6381` | 链路加密（见 12.3） |

### 12.2.2 网络配置实战

```conf
# redis.conf 网络安全配置
bind 10.0.0.1 127.0.0.1
protected-mode yes
port 6380
tcp-backlog 511
tcp-keepalive 60

```

```bash
# iptables 限制仅应用服务器 IP 访问

iptables -A INPUT -p tcp --dport 6380 -j DROP

# 云安全组同理：仅放行应用服务器安全组到 Redis 安全组的 6380 端口
```

### 12.2.3 危险命令禁用（rename-command）

`rename-command` 在 redis.conf 中配置，将危险命令重命名为空字符串（禁用）或随机串（仅已知者可用）。注意：集群模式下 rename-command 会破坏集群协议，**禁止 rename 集群必需命令**。

```conf
# redis.conf 危险命令处置
# 完全禁用
rename-command FLUSHDB ""
rename-command FLUSHALL ""
rename-command KEYS ""
rename-command DEBUG ""

# 重命名为复杂名称（仅运维知晓）
rename-command CONFIG "CONFIG_a8f3b2c1d4e5"
rename-command SHUTDOWN "SHUTDOWN_a8f3b2c1d4e5"

# 注意：以下命令在集群模式下不可 rename，会破坏集群协议
# CLUSTER / REPLICAOF / SLAVEOF / PSYNC / SUBSCRIBE / PUBLISH
```

| 命令 | 风险 | 处置建议 |
|------|------|---------|
| `FLUSHALL` | 清空所有 DB | rename 禁用，改用 `FLUSHALL ASYNC` 或 ACL `-FLUSHALL` |
| `FLUSHDB` | 清空当前 DB | 同上 |
| `KEYS` | O(N) 阻塞主线程 | rename 禁用，改用 SCAN |
| `CONFIG` | 在线修改配置泄露 | rename 重命名或 ACL `-CONFIG`，运维需时再放开 |
| `DEBUG` | 调试命令，影响性能 | rename 禁用 |
| `SHUTDOWN` | 关闭实例 | rename 重命名，避免误触 |
| `MONITOR` | 实时输出所有命令，性能衰减 50%+ | ACL 禁用，仅调试临时开启 |

> ACL 与 rename-command 关系：ACL 是 6.0+ 推荐的细粒度方案（按用户限制），rename-command 是全局禁用（对所有用户生效）。生产建议优先 ACL，rename-command 仅作全局兜底（如彻底禁用 KEYS）。

## 12.3 TLS 加密通信（6.0+）

### 12.3.1 TLS 架构

```
TLS 加密链路：
┌────────────┐  TLS 1.2/1.3   ┌────────────┐
│  Client    │◄──────────────►│  Redis     │
│ (redis-cli)│  双向证书校验   │ (tls-port) │
└────────────┘                └────────────┘
     │                              │
     ├─ ca.crt（校验服务端证书）    ├─ redis.crt（服务端证书）
     ├─ client.crt（客户端证书）    ├─ redis.key（服务端私钥）
     └─ client.key（客户端私钥）    └─ ca.crt（校验客户端证书）

支持模式：
├── 仅 TLS：tls-port 6379，port 0（禁明文）
├── 双栈：tls-port 6381 + port 6379（明文/TLS 并存，过渡期用）
└── 复制/集群 TLS：repl/tls 也走 TLS（推荐生产全链路加密）
```

### 12.3.2 证书生成

```bash
# 创建 CA 私钥与根证书
openssl genrsa -out ca.key 4096
openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -subj "/C=CN/ST=BJ/O=MyOrg/CN=RedisCA" -out ca.crt

# 创建 Redis 服务端私钥与 CSR
openssl genrsa -out redis.key 2048
openssl req -new -key redis.key \
  -subj "/C=CN/ST=BJ/O=MyOrg/CN=redis.example.com" -out redis.csr

# 用 CA 签发服务端证书
openssl x509 -req -in redis.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out redis.crt -days 365 -sha256

# 创建客户端证书（双向认证用）
openssl genrsa -out client.key 2048
openssl req -new -key client.key \
  -subj "/C=CN/ST=BJ/O=MyOrg/CN=redis-client" -out client.csr
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out client.crt -days 365 -sha256

# 权限设置
chmod 600 redis.key client.key
```

### 12.3.3 redis.conf TLS 配置

```conf
# ============ TLS 配置（redis.conf） ============
# 仅启用 TLS（禁明文）
port 0
tls-port 6381

# 服务端证书与私钥
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file /etc/redis/tls/redis.key

# CA 证书（用于校验客户端证书）
tls-ca-cert-file /etc/redis/tls/ca.crt

# 客户端证书校验模式
# none:   不校验客户端证书
# optional: 客户端可选择性提供证书
# yes:    强制客户端提供证书（推荐）
tls-auth-clients yes

# 支持的 TLS 协议版本
tls-protocols "TLSv1.2 TLSv1.3"

# 加密套件
tls-ciphersuites "TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256"
tls-ciphers "ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384"

# 复制链路也走 TLS
tls-replication yes

# 集群总线也走 TLS
tls-cluster yes
```

### 12.3.4 客户端连接

```bash
# redis-cli TLS 连接
redis-cli --tls \
  --cert /etc/redis/tls/client.crt \
  --key /etc/redis/tls/client.key \
```

## 12.4 数据安全

### 12.4.1 应用层加密

Redis 本身不提供静态数据加密（at-rest encryption），敏感数据应在应用层加密后存储。

```python
import redis
from cryptography.fernet import Fernet

r = redis.Redis(host="localhost", port=6379, password="your_strong_password",
                decode_responses=True)


class SecureRedis:
    """应用层字段级加密：敏感字段写入前加密，读出后解密"""

    def __init__(self, client: redis.Redis, key: bytes | None = None):
        self.r = client
        self.key = key or Fernet.generate_key()
        self.cipher = Fernet(self.key)

    def set_encrypted(self, key: str, value: str, ex: int | None = None) -> None:
        encrypted = self.cipher.encrypt(value.encode()).decode()
        self.r.set(key, encrypted, ex=ex)

    def get_decrypted(self, key: str) -> str | None:
        encrypted = self.r.get(key)
        if encrypted is None:
            return None
        return self.cipher.decrypt(encrypted.encode()).decode()


# 密钥应从 KMS / 环境变量加载，勿硬编码
secure = SecureRedis(r, key=b"your-kms-managed-key-base64==")
secure.set_encrypted("ssn:user:1001", "110101199001011234", ex=3600)
print(secure.get_decrypted("ssn:user:1001"))
```

### 12.4.2 数据安全策略

```
1. 数据加密
   ├── 传输加密：TLS（见 12.3）
   ├── 静态加密：应用层加密敏感字段（AES/Fernet）
   └── 磁盘加密：云盘加密 / LUKS 加密 RDB/AOF 文件

2. 数据脱敏
   ├── 日志不输出敏感数据
   ├── MONITOR 命令可能泄露敏感数据，生产禁用
   └── ACL 限制 MONITOR / DEBUG OBJECT

3. 备份安全
   ├── RDB/AOF 文件加密存储
   ├── 传输备份用 SCP/SFTP（加密通道）
   ├── 备份介质访问审计
   └── 定期销毁过期备份

4. 数据销毁
```

### 12.5.2 RDB 定时备份脚本

```bash
#!/bin/bash
# /opt/redis/backup_rdb.sh - RDB 定时备份脚本
set -euo pipefail

REDIS_HOST="127.0.0.1"
REDIS_PORT="6379"
REDIS_PASS="your_strong_password"
REDIS_DIR="/var/lib/redis"
BACKUP_DIR="/backup/redis"
KEEP_DAYS=7
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/dump_${DATE}.rdb"
LOG_FILE="/var/log/redis/backup.log"

log() { echo "[$(date '+%F %T')] $1" | tee -a "$LOG_FILE"; }

mkdir -p "$BACKUP_DIR"

log "触发 BGSAVE"
redis-cli -h "$REDIS_HOST" -p "$REDIS_PORT" -a "$REDIS_PASS" --no-auth-warning BGSAVE

# 等待 BGSAVE 完成
while true; do
    status=$(redis-cli -h "$REDIS_HOST" -p "$REDIS_PORT" -a "$REDIS_PASS" --no-auth-warning \
             INFO persistence | grep rdb_bgsave_in_progress | tr -d '\r')
    if [[ "$status" == "rdb_bgsave_in_progress:0" ]]; then
        break
    fi
    sleep 1
done

log "复制 RDB 文件到备份目录"
cp "${REDIS_DIR}/dump.rdb" "$BACKUP_FILE"
chmod 600 "$BACKUP_FILE"

# 验证备份文件
redis-check-rdb "$BACKUP_FILE" >> "$LOG_FILE" 2>&1 || {
    log "备份文件校验失败"
    exit 1
}

log "清理 ${KEEP_DAYS} 天前的备份"
find "$BACKUP_DIR" -name "dump_*.rdb" -mtime +${KEEP_DAYS} -delete

# 同步到对象存储（示例）
# aws s3 cp "$BACKUP_FILE" "s3://your-bucket/redis-backup/" --sse AES256

log "备份完成: $BACKUP_FILE"
```

### 12.5.5 redis-shake 迁移

[redis-shake](https://github.com/tair-opensource/redis-shake) 是阿里开源的 Redis 数据迁移与同步工具，支持 RDB 解析、增量同步、断点续传。

```yaml

[source]
address = "10.0.0.1:6379"
password = "source_password"
tls = false

[target]
address = "10.0.0.2:6379"
password = "target_password"
tls = false

[advanced]

reply = { size = 1024 }          # 异步回放批量
```

```bash
# 启动迁移
./redis-shake sync.toml

# 监控迁移进度（查看日志）
tail -f logs/redis-shake.log

# 增量同步持续运行，直至业务切换
# 切换步骤：
# 1. 业务方停止写源 Redis（或切换到目标 Redis 双写）
# 2. 等待 redis-shake 增量追平（日志显示 sync done）
# 3. 业务切换到目标 Redis
# 4. 停止 redis-shake
```

| 迁移场景 | 推荐模式 | 说明 |
|---------|---------|------|
| 同版本全量迁移 | sync | 全量 + 增量，业务可在线 |
| 跨版本迁移 | sync + 兼容性测试 | 7.x → 6.x 需注意命令兼容 |
| 集群间迁移 | sync + cluster 模式 | 自动处理哈希槽 |
| 上云迁移 | sync | 阿里云/腾讯云 Redis 一键接入 |
| 数据校验 | redis-full-check | 迁移后比对数据一致性 |

### 12.6.2 滚动升级（哨兵架构）

哨兵架构下，通过故障转移逐个升级从节点，最后升级主节点，实现零停机。

```
滚动升级流程（一主二从三哨兵）：
┌──────────────────────────────────────────────────────────┐
│ 初始状态：M(master) ← S1(replica) ← S2(replica)          │
│                                                          │
│ 步骤 1：升级 S2                                          │
│   ① sentinel failover 强制 S2 不可达（无需真停）         │
│   ② 停 S2 → 升级二进制 → 启动 S2（自动追同步）           │
│   ③ 等待 S2 同步完成（master_repl_offset 追平）          │
│                                                          │
│ 步骤 2：升级 S1（同步骤 1）                              │
│                                                          │
│ 步骤 3：升级 M                                           │
│   ① sentinel failover mymaster 触发主从切换              │
│   ② 原 M 降为从，S2 升为主（或 S1）                      │
│   ③ 停原 M → 升级 → 启动（自动作为从追同步）            │
│                                                          │
│ 步骤 4：（可选）再次 failover 切回原主                    │
│                                                          │
│ 步骤 5：逐个升级 3 个 sentinel                           │
└──────────────────────────────────────────────────────────┘
```

```bash
# 1. 升级前备份
redis-cli -a your_strong_password BGSAVE
# 等待 rdb_bgsave_in_progress:0
cp /var/lib/redis/dump.rdb /backup/redis/dump_pre_upgrade_$(date +%s).rdb

# 2. 查看当前主从拓扑
redis-cli -p 26379 SENTINEL master mymaster
redis-cli -p 26379 SENTINEL replicas mymaster

# 3. 升级从节点 S2（重复对所有从节点）
# 3.1 查 S2 同步偏移量
redis-cli -h 192.168.1.12 -p 6379 -a your_strong_password INFO replication | grep master_repl_offset
# 与 master 的 master_repl_offset 比对，需一致

# 3.2 停 S2
redis-cli -h 192.168.1.12 -p 6379 -a your_strong_password SHUTDOWN NOSAVE

# 3.3 升级二进制
systemctl stop redis@S2
cp /opt/redis-7.2.4/src/redis-server /usr/local/bin/redis-server
# 或 apt/yum 升级
apt-get update && apt-get install --only-upgrade redis-server

# 3.4 启动 S2
systemctl start redis@S2

# 3.5 验证 S2 重新同步
redis-cli -h 192.168.1.12 -p 6379 -a your_strong_password INFO replication
# role:slave + master_link_status:up + master_sync_in_progress:0

# 4. 升级主节点 M
# 4.1 触发故障转移（哨兵将主切换到已升级的从节点）
redis-cli -p 26379 SENTINEL failover mymaster

# 4.2 等待故障转移完成
while true; do
    state=$(redis-cli -p 26379 SENTINEL master mymaster | grep -A1 flags | tail -1)
    echo "$state" | grep -q "master" && break
    sleep 1
done

# 4.3 原 M 已降为从，停掉升级
redis-cli -h 192.168.1.11 -p 6379 -a your_strong_password SHUTDOWN NOSAVE
systemctl stop redis@M
cp /opt/redis-7.2.4/src/redis-server /usr/local/bin/redis-server
systemctl start redis@M

# 4.4 验证原 M 作为从节点追同步
redis-cli -h 192.168.1.11 -p 6379 -a your_strong_password INFO replication

# 5. 升级 sentinel（逐个）
systemctl stop redis-sentinel@1
cp /opt/redis-7.2.4/src/redis-sentinel /usr/local/bin/redis-sentinel
systemctl start redis-sentinel@1
# 重复对 sentinel@2, sentinel@3

# 6. 验证集群健康
redis-cli -p 26379 SENTINEL masters
redis-cli -a your_strong_password INFO server | grep redis_version
```

### 12.6.4 RDB/AOF 跨版本兼容性

| 升级路径 | RDB 兼容 | AOF 兼容 | 注意事项 |
|---------|---------|---------|---------|
| 6.x → 7.x | 兼容（7.0 可读 6.x RDB） | 兼容（7.0 多 AOF 文件可读旧 AOF） | 7.0 默认多 AOF 文件结构 |
| 7.x → 6.x | 不兼容（6.x 无法读 7.0 RDB） | 不兼容（多 AOF 文件 6.x 不识别） | 降级需先在 7.x 重新生成 RDB/AOF |
| 5.x → 7.x | 兼容 | 兼容 | 注意 Stream、Function 命令 |
| 4.x → 7.x | 兼容 | 兼容 | 注意 PSYNC2、混合持久化 |
| 同小版本（7.2.4 → 7.2.5） | 完全兼容 | 完全兼容 | 直接滚动升级 |

> 关键原则：跨大版本降级通常不兼容，升级前必须完整备份，并制定回滚到旧版本的数据方案（用旧版本二进制 + 旧 RDB/AOF 备份恢复）。

### 12.7.2 SOP-1：内存告警（used_memory > 85% maxmemory）

```
现象：Prometheus 告警 RedisMemoryHigh
影响：触发淘汰策略（缓存场景）或写入失败（noeviction 场景）

处置步骤：
① 确认告警：redis-cli INFO memory
   - used_memory_human / maxmemory_human
   - mem_fragmentation_ratio（区分真实增长与碎片）

② 区分原因：
   a) 真实数据增长
      - DBSIZE 看 key 数量
      - redis-cli --bigkeys 找大 Key
      - 处置：清理无用 key / 扩容 maxmemory / 集群扩容
   b) 内存碎片（碎片率 > 1.5）
      - CONFIG SET activedefrag yes 开启自动整理
      - 或 MEMORY PURGE 手动触发
   c) 客户端缓冲区暴涨
      - INFO clients 看 connected_clients / blocked_clients
      - CLIENT LIST 看各客户端 output_buf
      - 处置：KILL 异常客户端 / 调小 client-output-buffer-limit

③ 缓解措施：
   - 临时调大 maxmemory（CONFIG SET maxmemory 8gb）
   - 切换更激进的淘汰策略（如 noeviction → allkeys-lru）
   - 清理已知的临时 key（UNLINK）

④ 长期治理：
   - 容量规划：预留 30% buffer
   - 大 Key 治理：见 11.3
   - 设置 maxmemory-policy 与业务匹配
```

### 12.7.3 SOP-2：主从断开（replication lag / slave down）

```
现象：INFO replication 显示 master_link_status:down 或 master_repl_offset 远大于 slave
影响：从节点数据陈旧，读不一致；故障转移延迟

处置步骤：
① 确认状态：
   - 主节点：redis-cli INFO replication → connected_slaves 减少
   - 从节点：redis-cli INFO replication → master_link_status:down
   - 哨兵：redis-cli -p 26379 SENTINEL masters

② 排查网络：
   - ping/telnet 主从互通性
   - iptables / 安全组是否放行
   - 主节点是否 bind 内网 IP

③ 排查配置：
   - masterauth / requirepass 是否一致（认证失败最常见）
   - ACL 是否授予从节点 PSYNC/REPLICAOF 权限
   - repl-backlog-size 是否过小导致全量重同步

④ 排查主节点负载：
   - 主节点 client-output-buffer-limit replica 是否打满
   - 主节点是否因大 Key / fork 阻塞
   - INFO stats 看 rejected_connections

⑤ 处置：
   - 网络/配置问题：修复后从节点自动重连
   - 全量重同步：在低峰期 REPLICAOF NO ONE + REPLICAOF 重置
   - 从节点数据损坏：删除从节点数据目录，重启触发全量同步

⑥ 验证：
   - master_link_status:up
   - master_repl_offset 与 slave 一致
   - 哨兵状态正常
```

### 12.7.4 SOP-3：集群槽异常（cluster_state:fail）

```
现象：CLUSTER INFO 显示 cluster_state:fail 或 cluster_slots_ok < 16384
影响：部分 key 读写失败（MOVED 错误无法响应）

处置步骤：
① 确认状态：
   - CLUSTER INFO
   - CLUSTER NODES（找 fail/pfail 节点）

② 定位异常节点：
   - CLUSTER COUNT-FAILURE-REPORTS <node-id> 看故障报告
   - 异常节点：redis-cli -h <ip> -p <port> PING
   - 检查异常节点进程、磁盘、网络

③ 单节点宕机：
   - 该节点有从节点：等待故障转移自动完成
   - 该节点无从节点：
     a) 重启该节点（数据目录有 RDB/AOF 可恢复）
     b) 数据丢失：从备份恢复，CLUSTER ADDSLOTS 重新分配槽

④ 槽未分配：
   - CLUSTER ADDSLOTS <slot> 重新分配
   - 或 CLUSTER SETSLOT <slot> NODE <node-id>

⑤ 脑裂恢复：
   - 确认多数派节点
   - 少数派节点：CLUSTER RESET HARD 后重新加入

⑥ 验证：
   - CLUSTER INFO 全 ok
   - CLUSTER SLOTS 槽分布正常
   - 业务读写正常
```

### 12.7.5 SOP-4：慢查询突增

```
现象：SLOWLOG LEN 持续增长 / 客户端延迟告警
影响：QPS 下降、请求超时、级联雪崩

处置步骤：
① 采集慢查询：
   - SLOWLOG GET 50
   - 记录命令、耗时、客户端

② 分类定位：
   a) KEYS / HGETALL / SMEMBERS 等全量命令
      → 业务方误用，立即叫停，改用 SCAN
   b) DEL 大 Key
      → 改用 UNLINK，分批删除
   c) SORT / SUNIONSTORE 等集合运算
      → 限制集合大小 / 业务侧预计算
   d) Lua 脚本过长
      → 拆分脚本 / lua-time-limit 限制
   e) AOF fsync 阻塞
      → 检查磁盘 IO / 调整 appendfsync
   f) fork 阻塞
      → latest_fork_usec 过大，关闭 THP，降低数据量

③ 临时缓解：
   - CLIENT KILL 异常客户端
   - 降级非核心业务
   - 切换从节点读流量

④ 长期治理：
   - 接入 SLOWLOG 采集到 ELK / Grafana
   - 业务侧禁止 KEYS（rename-command KEYS ""）
   - 大 Key 治理（见 11.3）
   - Code Review 把关命令使用
```

### 12.7.6 SOP-5：连接拒绝（rejected_connections > 0）

```
现象：INFO stats 显示 rejected_connections 增长
影响：新客户端连接被拒，业务报错

处置步骤：
① 确认：
   - INFO clients: connected_clients vs maxclients
   - 若 connected_clients ≈ maxclients：连接数耗尽

② 排查连接来源：
   - CLIENT LIST 按 addr 聚合，找 TopN 客户端
   - 排查是否有连接泄漏（应用未关闭连接）

③ 处置：
   - 临时调大 maxclients（CONFIG SET maxclients 20000）
   - 调系统 ulimit（ulimit -n 65535）
   - KILL 异常连接（CLIENT KILL ADDR）
   - 应用侧修复连接池配置（maxTotal / maxIdle 合理）

④ 长期治理：
   - 应用统一连接池
   - 监控客户端连接数分布
   - ACL 限制单用户最大连接（7.0+ maxconnections）
```

## 12.9 Redis vs MySQL 安全运维对比

| 维度 | Redis | MySQL |
|------|-------|-------|
| 认证模型 | requirepass 全局密码 + ACL 多用户（6.0+） | 用户名密码 + host 白名单 + caching_sha2_password |
| 权限粒度 | 命令类别 + key 前缀 + channel（ACL） | 库/表/列级 GRANT，更细 |
| 网络隔离 | bind + protected-mode + iptables | bind-address + 防火墙 |
| 传输加密 | TLS（6.0+），双栈支持 | TLS（MySQL 8.0 原生） |
| 危险命令 | rename-command / ACL 禁用 FLUSHALL/KEYS | DROP DATABASE / TRUNCATE 由 GRANT 控制 |
| 静态加密 | 不支持，应用层加密 | 透明表空间加密（keyring） |
| 审计 | 不原生支持，需 MONITOR 或第三方模块 | 企业审计插件 / MariaDB Audit Plugin |
| 备份方式 | RDB 快照 + AOF 日志 + redis-shake | mysqldump / Percona XtraBackup / binlog |
| 备份频率 | RDB 小时级 + AOF 秒级 | 全量日级 + binlog 实时 |
| 恢复粒度 | RDB 全量 / AOF 命令级 / 时间点回放 | 全量恢复 + binlog 时间点恢复（PITR） |
| 主从复制 | 异步 / 半同步（WAIT） | 异步 / 半同步 / 组复制（MGR） |
| 升级方式 | 滚动升级（哨兵/集群故障转移） | 滚动升级（MHA/Orchestrator 切换） |
| 升级兼容性 | RDB/AOF 跨大版本有限兼容（降级常不兼容） | 跨大版本需 mysql_upgrade，binlog 兼容性较好 |
| 默认端口 | 6379 | 3306 |
| 公网暴露风险 | 极高（默认无密码曾被大规模勒索） | 高（默认 root 空密码曾爆发漏洞） |
| 安全基线 | 必须密码 + ACL + 内网 + TLS | 必须密码 + 删匿名用户 + 限 host + TLS |
| 监控栈 | redis_exporter + Prometheus | mysqld_exporter + Prometheus |
| 常见安全事件 | 无密码公网暴露被勒索、挖矿 | SQL 注入、弱口令爆破 |

## 小思考题帮你巩固

1. **requirepass 与 ACL 是什么关系？为什么多业务方共用一个实例时该用 ACL？**（提示：requirepass 全库一把锁；ACL 用户/命令/key 三维授权，能造"只读且只见某前缀"的最小权限账号，见 12.1。）
2. **`bind 0.0.0.0` + 无密码 + `protected-mode yes` 会发生什么？为什么生产不能用 `bind 0.0.0.0`？**（提示：protected-mode 只在"无密码"时拦外连；一设密码它就不拦了，公网扫描会直接撞库，见 12.2。）
3. **TLS 解决了什么问题，不能解决什么问题？配了 TLS 还要 ACL/密码吗？**（提示：TLS 防窃听/中间人（传输层），不验证"你是谁"（身份/授权）；两者互补，见 12.3。）
4. **`rename-command` 与 ACL 禁命令相比有什么局限？为什么新项目倾向 ACL？**（提示：rename 是"藏名字"，对客户端透明性差、脚本/工具可能依赖原名；ACL 规则式禁命令更清晰可审计，见 12.1/12.2。）
5. **开发自查清单里最容易忽视、却最容易出事的是哪几项？**（提示：bind 暴露公网、无密码/弱密码、危险命令未禁、`KEYS`/`FLUSHALL` 可被任意客户端执行、ACL 未最小化，见 12.8。）

<details>
<summary>参考答案（点击展开）</summary>

1. requirepass 是"一个全库密码"（任何客户端拿到就能执行一切）；ACL 是按用户授权（`ACL SETUSER app on >pass ~app:* +@read`——只能读 app:* 前缀的 key）。并存时 ACL 优先。多业务共用一个实例时 ACL 能做出互不越权的隔离账号，出事也能 `ACL LOG` 审计到"谁用什么命令碰了哪个 key"。
2. `protected-mode yes` 的拦截条件是"无密码 + 非本机来源"；一旦你设置了 requirepass，该保护自动放开——于是 6379 暴露到公网 + 有密码（哪怕弱密码）= 可被暴力扫射。生产必须 `bind` 内网 IP（或直接 `protected-mode no` + 防火墙 + 仅内网），**绝不 bind 0.0.0.0 暴露公网**。
3. TLS 解决"传输被窃听/篡改/中间人"（数据保密+完整性），不验证"访问者身份与权限"（那是认证与授权的事）。所以 TLS 必须与 requirepass/ACL 组合：TLS 保信道、ACL 控身份权限，缺一不可。
4. rename-command 把命令改名后，客户端/运维脚本若还按原名调用会失败且难以排查，本质是"藏"而非"禁"，且不能按用户区分（全局改名）；ACL 直接"禁止某用户执行某命令"规则清晰、能审计。新项目（Redis 6+ 有 ACL）优先 ACL 规则而不是 rename。
5. 最易出事：① bind/暴露面（被公网扫描直接打穿）；② 无密码或弱密码；③ KEYS/FLUSHALL/DEBUG/CONFIG 等危险命令未对普通用户禁止；④ ACL 未最小化（给了 @all）。自查清单 20 项中前几项样例全中就是"裸奔"状态——开发机上至少跑一遍 12.8 清单。
