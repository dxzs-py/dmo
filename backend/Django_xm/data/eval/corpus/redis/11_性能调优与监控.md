# 11 性能调优与监控

> 系统化梳理 Redis 7+ 性能调优方法论：从慢查询诊断、Pipeline 批量、大 Key 治理、内存碎片整理，到 redis-benchmark 压测与 redis_exporter + Prometheus + Grafana 监控栈完整部署，覆盖生产 INFO 指标解读与 redis.conf 调优参数。

## 零基础前置认知

**这篇在讲什么**：Redis 调优不是"玄学调参"，而是**先体检、再对症**——五个自诊断工具各管一类病：**慢查询**（找出哪条命令真慢）、**Pipeline/MGET**（治"网络往返病"）、**大 Key**（治"单线程阻塞病"）、**碎片/内存**（治"RSS 虚高病"）、**redis-benchmark**（量化压测验证吞吐）。读完你能用 `SLOWLOG`+`CLIENT LIST`+`LATENCY` 三步定位"慢在哪"，用 `--bigkeys` 揪出大 Key 并拆分，把 `INFO` 关键指标读成"体检报告"，并搭一条最小监控看板验证（exporter+Prometheus+Grafana）。*全套监控/生产 conf 见 99 附录，本篇以"开发自助诊断"为主线。*

> 辅助类比：把 Redis 性能调优想成"给发动机做体检"——**慢查询**是"检查哪一次点火慢了"（SLOWLOG 记录超阈值命令，像行车记录仪）；**Pipeline** 是"把多脚油一次踩完再答复"（省掉每脚的往返）；**大 Key** 是"一颗超大的超载齿轮"（操作它要转很久，单线程下整台机器都等它）；**碎片率**是"变速箱里没排满的空隙"（used_memory_rss / used_memory 一眼看懂）；**benchmark** 是"台架测马力"（不实跑不知道极限）。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| SLOWLOG | 记录执行耗时超阈值的命令（`slowlog-log-slower-than`，默认 10000µs） | 慢命令=单线程卡顿元凶；`SLOWLOG GET` 查看 |
| Pipeline / MGET | 多命令一次往返 / 一条命令批量读 | 治"网络 RTT 病"；MGET 单命令更省 |
| 大 Key | 单 key 元素多/体积大（数 KB~MB 级） | 遍历类命令 O(N) 阻塞主线程；`--bigkeys` 扫描 |
| 碎片率 | used_memory_rss / used_memory | >1.5 建议整理（activedefrag），<1.0 警惕 SWAP |
| redis-benchmark | 官方压测工具（`-c` 并发、`-n` 总数、`-P` pipeline） | 量化核心命令吞吐与延迟，验证调优效果 |
| INFO | 分节统计（server/clients/memory/persistence/stats/replication/keyspace） | 体检报告入口；`INFO commandstats` 看命令占比 |
| CLIENT LIST / LATENCY | 查活跃连接 / 查事件延迟 | 定位"连接堆积"或"事件延迟抖动" |
| 优化顺序 | 先定位后调参 | 慢查→大 Key→内存→配置，别跳过诊断直接调参 |

> 区分/注意：**慢查询 ≠ 网络延迟**——SLOWLOG 只记"命令在服务端的执行时间"，不含网络排队；客户端感觉慢要先分"是网络 RTT 还是服务端执行慢"（`CLIENT LIST` 看 idle、`SLOWLOG` 看命令耗时）。**大 Key 的"大"是命令级的 O(N)**：`HGETALL`/`LRANGE`/`SMEMBERS` 这类遍历命令在大 key 上开销很大，`KEYS *`/`SMEMBERS` 这类在单线程里会瞬间堵死——所以"慢查询"多半是大 key 造成的。**基准测试要贴近真实负载**：`redis-benchmark` 默认压 SET/GET 纯字符串，与你的业务命令集可能偏差很大，最好压你最重的命令并用 `-P` 验证 pipeline 效果。

## 11.1 慢查询诊断

### 11.1.1 慢查询日志机制

Redis 慢查询日志记录执行耗时超过阈值的命令，仅记录「命令执行耗时」不含网络往返与排队。日志保存在内存中（FIFO 队列），重启即丢失，需配合外部采集落盘。

```
┌──────────────────────────────────────────────────────────┐
│  客户端请求生命周期（slowlog 仅记录阶段 ④）              │
│                                                          │
│  ① 网络接收  ② 协议解析  ③ 命令排队  ④ 命令执行  ⑤ 响应 │
│     ──────────────────────────────────►                  │
│                                  ▲                       │
│                                  └── slowlog-log-slower- │
│                                      than 阈值判定在此    │
└──────────────────────────────────────────────────────────┘
```

| 参数 | 默认值 | 含义 | 生产建议 |
|------|--------|------|----------|
| `slowlog-log-slower-than` | 10000（10ms） | 超过该微秒数的命令记入慢日志，0 记录全部，<0 禁用 | 10000（10ms）或 5000（5ms） |
| `slowlog-max-len` | 128 | 慢日志队列最大长度，超出丢弃最旧 | 1024（保留更长历史） |

### 11.1.2 慢查询命令实战

```bash
# 1. 调整慢查询阈值（微秒，10000 = 10ms）
CONFIG SET slowlog-log-slower-than 10000

# 2. 调整慢日志保留条数
CONFIG SET slowlog-max-len 1024

# 3. 查看最近 10 条慢日志
SLOWLOG GET 10
# 返回字段：1=唯一ID  2=Unix时间戳  3=耗时(微秒)  4=命令及参数  5=客户端IP:port  6=客户端名

# 4. 查看当前慢日志条数
SLOWLOG LEN

# 5. 清空慢日志
SLOWLOG RESET

# 6. 持久化配置到 redis.conf
# slowlog-log-slower-than 10000
# slowlog-max-len 1024
```

慢查询分析流程：

```
┌────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ SLOWLOG    │───►│ 命令类型判定  │───►│ 原因定位     │───►│ 优化方案     │
│ GET 20     │    │              │    │              │    │              │
│            │    │ KEYS *       │    │ O(N) 全量扫描│    │ 改用 SCAN    │
│            │    │ HGETALL 大K  │    │ 大 Key 阻塞  │    │ 拆分/UNLINK  │
│            │    │ SUNIONSTORE  │    │ 集合运算大   │    │ 控制集合大小  │
│            │    │ DEL 大Key    │    │ 同步删除阻塞 │    │ 改用 UNLINK  │
│            │    │ SORT 大集合  │    │ 排序耗时     │    │ 限制元素数    │
└────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

### 11.1.3 危险命令与替代方案

| 命令 | 时间复杂度 | 风险 | 替代方案 |
|------|-----------|------|----------|
| `KEYS *` | O(N) | 阻塞主线程，秒级卡顿 | `SCAN 0 MATCH pattern* COUNT 100` |
| `HGETALL` 大 Hash | O(N) | 大 Key 阻塞 | `HSCAN key 0 COUNT 100` / `HMGET` 指定字段 |
| `SMEMBERS` 大 Set | O(N) | 大 Key 阻塞 | `SSCAN key 0 COUNT 100` |
| `LRANGE 0 -1` 大 List | O(N) | 大 Key 阻塞 | 分页 `LRANGE 0 99` |
| `DEL` 大 Key | O(N) | 同步删除阻塞 | `UNLINK`（异步删除，4.0+） |
| `FLUSHALL` | O(N) | 清空全部数据 | `FLUSHALL ASYNC`（异步）或禁用 |
| `SORT` 大集合 | O(N+M*logM) | 排序 CPU 飙高 | 业务侧预排序或限制元素数 |
| `MONITOR` | 持续 | 实时输出所有命令，性能衰减 50%+ | 仅短时调试，生产禁用 |

```bash
# SCAN 渐进式遍历（推荐）
SCAN 0 MATCH user:* COUNT 100
# 返回：下一游标 + 本次匹配的 key 列表；游标为 0 表示遍历结束

# UNLINK 异步删除大 Key（O(1) 返回，后台线程回收内存）
UNLINK bigkey:hash:1001

# FLUSHALL 异步清空（降低阻塞）
FLUSHALL ASYNC
```

## 11.2 Pipeline 批量与 MGET/MSET

### 11.2.1 RTT 与 Pipeline 原理

Redis 单条命令需一次网络往返（RTT）。N 条独立命令 = N 次 RTT + N 次系统调用。Pipeline 将多条命令打包一次发送、一次接收响应，显著降低 RTT 与系统调用开销。

```
非 Pipeline（N 条命令）：
  Client ──cmd1──► Redis   Client ◄──resp1── Redis
  Client ──cmd2──► Redis   Client ◄──resp2── Redis
  ...
  共 N 次 RTT，N 次读写系统调用

Pipeline（N 条命令）：
  Client ──cmd1,cmd2,...,cmdN──► Redis
  Client ◄──resp1,resp2,...,respN── Redis
  共 1 次 RTT，2 次读写系统调用
```

| 方式 | RTT 次数 | 原子性 | 适用场景 |
|------|---------|--------|----------|
| 单条命令循环 | N | 每条独立 | 少量命令 |
| MGET / MSET | 1 | 单命令原子 | 同类型 String 批量 |
| Pipeline | 1 | 非原子（命令间可插入其他客户端命令） | 跨类型批量、减少 RTT |
| MULTI/EXEC 事务 | 1 | 原子（顺序执行不打断） | 需要原子性的多命令 |
| Lua EVALSHA | 1 | 原子 + 服务端执行 | 复杂逻辑、条件判断 |

### 11.2.2 批量命令实战

```bash
# MGET / MSET：单命令原子，服务端一次执行
MSET user:1:name "张三" user:2:name "李四" user:3:name "王五"
MGET user:1:name user:2:name user:3:name

# Hash 批量：HSET / HMGET（旧命令 HMSET 已废弃，合并进 HSET）
HSET user:1 name "张三" age 25 email "zhangsan@example.com"
HMGET user:1 name age email

# Pipeline 命令文件批量导入
# 准备 commands.txt，每行一条 RESP 协议命令
redis-cli --pipe < commands.txt
# 适用于大批量数据初始化，吞吐量可达 10万+/秒

# redis-cli 交互式 Pipeline
redis-cli -h 127.0.0.1 -p 6379 -a your_strong_password --pipe-timeout 30 --pipe < data.txt
```

### 11.2.3 Python Pipeline 示例

```python
import redis
import time

r = redis.Redis(host="localhost", port=6379, password="your_strong_password",
                decode_responses=True)


def batch_set_naive(data: dict[str, str]) -> float:
    """逐条 SET：N 次 RTT"""
    start = time.perf_counter()
    for key, value in data.items():
        r.set(key, value)
    return time.perf_counter() - start


def batch_set_pipeline(data: dict[str, str]) -> float:
    """Pipeline 批量 SET：1 次 RTT"""
    start = time.perf_counter()
    with r.pipeline() as pipe:
        for key, value in data.items():
            pipe.set(key, value)
        pipe.execute()
    return time.perf_counter() - start


def batch_get_mget(keys: list[str]) -> list[str | None]:
    """MGET 单命令批量读"""
    return r.mget(keys)


def batch_get_pipeline(keys: list[str]) -> list[str | None]:
    """Pipeline 批量读"""
    with r.pipeline() as pipe:
        for key in keys:
            pipe.get(key)
        return pipe.execute()


if __name__ == "__main__":
    data = {f"user:{i}:name": f"用户{i}" for i in range(2000)}
    t1 = batch_set_naive(data)
    t2 = batch_set_pipeline(data)
    print(f"逐条 SET 2000 条: {t1:.3f}s")
    print(f"Pipeline SET 2000 条: {t2:.3f}s")
    print(f"Pipeline 加速比: {t1 / t2:.1f}x")
    # 典型输出：逐条 1.8s vs Pipeline 0.06s，加速 30x+
```

Pipeline 注意事项：
- 单个 Pipeline 命令数建议控制在 500~1000，过大易阻塞客户端与占用 output buffer
- Pipeline 非原子，命令间可能插入其他客户端命令，强一致性场景用 MULTI/Lua
- Pipeline 内命令顺序与响应顺序严格一一对应

## 11.3 大 Key 诊断与治理

### 11.3.1 大 Key 定义与危害

```
BigKey 定义（生产经验阈值）：
├── String：value > 10KB
├── Hash：field 数量 > 5000 或 单 value > 10KB
├── List：元素数量 > 5000 或 总大小 > 10KB
├── Set：member 数量 > 5000
└── Sorted Set：member 数量 > 5000

危害：
1. 内存不均：集群某节点内存远高于其他节点（数据倾斜）
2. 主线程阻塞：DEL/HGETALL/SMEMBERS 等 O(N) 操作阻塞主线程
3. 网络拥塞：单次传输大 Key 占用大量带宽，QPS 下降
4. 超时雪崩：客户端操作大 Key 超时，重试放大流量
5. 持久化阻塞：fork 时大 Key 复制耗时长，AOF 重写阻塞
```

### 11.3.2 大 Key 诊断命令

```bash
# 1. redis-cli --bigkeys：扫描发现各类型最大的 key（基于采样）
redis-cli --bigkeys -i 0.1
# -i 0.1 表示每 100 条命令休眠 0.1 秒，降低对生产影响

# 2. redis-cli --memkeys：扫描内存占用最大的 key（Redis 7+ 默认编译支持）
redis-cli --memkeys -i 0.1

# 3. MEMORY USAGE：查看单个 key 占用内存字节数
MEMORY USAGE user:1001
# 返回示例：(integer) 1048576（约 1MB）
MEMORY USAGE user:1001 SAMPLES 0
# SAMPLES 0 表示精确计算（默认采样 5 个元素估算）

# 4. DEBUG OBJECT：查看 key 编码与序列化大小（生产慎用，DEBUG 类命令建议 ACL 禁用）
DEBUG OBJECT user:1001
# 返回：Value at:0x... refcount:1 encoding:listpack serializedlength:86 lru:...

# 5. STRLEN / LLEN / SCARD / ZCARD / HLEN：快速评估元素规模
STRLEN bigkey:string:1
HLEN bigkey:hash:1
LLEN bigkey:list:1
SCARD bigkey:set:1
ZCARD bigkey:zset:1

# 6. SCAN 遍历 + MEMORY USAGE 自定义扫描脚本
redis-cli --eval scan_bigkeys.lua , 10000
```

`scan_bigkeys.lua` 参考实现：

```lua
-- 遍历所有 key，输出内存占用 > 阈值的 key
local cursor = '0'
local threshold = tonumber(ARGV[1])
local result = {}
repeat
    local reply = redis.call('SCAN', cursor, 'COUNT', 200)
    cursor = reply[1]
    for _, key in ipairs(reply[2]) do
        local mem = redis.call('MEMORY', 'USAGE', key, 'SAMPLES', '0')
        if mem and mem > threshold then
            table.insert(result, key .. '=' .. mem)
        end
    end
until cursor == '0'
return result
```

### 11.3.3 大 Key 删除与拆分

```bash
# 1. UNLINK 异步删除（4.0+）：O(1) 返回，后台线程回收内存
UNLINK bigkey:hash:1001
UNLINK bigkey:list:1001 bigkey:set:1001   # 支持多 key

# 2. 大 Hash 分批删除（HSCAN + HDEL）
# 先扫描 field
HSCAN bighash:1001 0 COUNT 200
# 对返回的 field 批量执行 HDEL
HDEL bighash:1001 field1 field2 field3 ...
# 重复直到 HLEN 为 0，最后 UNLINK key

# 3. 大 List 分批删除（LTRIM）
LTRIM biglist:1001 0 -201    # 删除末尾 200 个
LTRIM biglist:1001 0 -201    # 持续推进
# 直至 LLEN 为 0

# 4. 大 Set 分批删除（SSCAN + SREM）
SSCAN bigset:1001 0 COUNT 200
SREM bigset:1001 member1 member2 ...

# 5. 大 ZSet 分批删除（ZREMRANGEBYRANK）
ZREMRANGEBYRANK bigzset:1001 0 199    # 删除排名 0~199
```

大 Hash 拆分示例：

```bash
# 原始：单 Hash 存储 10万用户
HSET user:all 1001 "{...}" 1002 "{...}" ... 100000 "{...}"

# 拆分方案 1：按 ID 范围分片（1000 个/桶）
HSET user:range:1 1001 "{...}" ... 2000 "{...}"
HSET user:range:2 2001 "{...}" ... 3000 "{...}"

# 拆分方案 2：按 hash(id) % N 分片（负载更均衡）
# HSET user:shard:0 <hash为0的id> "{...}"
# HSET user:shard:1 <hash为1的id> "{...}"
```

```python
import hashlib
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)


class BigHashSharding:
    """大 Hash 拆分：按 hash(key) % shard_count 分片"""

    def __init__(self, client: redis.Redis, prefix: str, shard_count: int = 16):
        self.r = client
        self.prefix = prefix
        self.shard_count = shard_count

    def _shard_key(self, field: str) -> str:
        shard = int(hashlib.md5(field.encode()).hexdigest(), 16) % self.shard_count
        return f"{self.prefix}:shard:{shard}"

    def hset(self, field: str, value: str) -> None:
        self.r.hset(self._shard_key(field), field, value)

    def hget(self, field: str) -> str | None:
        return self.r.hget(self._shard_key(field), field)

    def hgetall_shard(self, shard_idx: int) -> dict:
        """仅遍历单个分片，避免 HGETALL 大 Hash"""
        return self.r.hgetall(f"{self.prefix}:shard:{shard_idx}")


sharding = BigHashSharding(r, "user", shard_count=16)
for uid in range(100000):
    sharding.hset(str(uid), f"userinfo_{uid}")
print(sharding.hget("1001"))
```

## 11.4 内存碎片与 JEMALLOC

### 11.4.1 内存结构

```
Redis 内存使用 = 自身内存 + 对象内存 + 缓冲内存 + 内存碎片

1. 自身内存：Redis 进程本身（约几 MB，可忽略）
2. 对象内存：所有键值对
   ├── RedisObject 头部（16 字节）
   ├── key 的 SDS
   └── value 的数据
3. 缓冲内存：
   ├── 客户端输出缓冲区（client-output-buffer）
   ├── 复制积压缓冲区（repl-backlog）
   └── AOF 缓冲区
4. 内存碎片：
   ├── 操作系统分配的内存 > Redis 实际使用
   ├── 碎片率 = used_memory_rss / used_memory
   └── 由 allocator（默认 jemalloc）分配回收产生
```

### 11.4.2 碎片率诊断与处置

| mem_fragmentation_ratio | 含义 | 处置 |
|------------------------|------|------|
| < 1.0 | Redis 使用了 Swap，性能严重下降 | 立即排查内存压力，关闭 swap，扩容 |
| 1.0 ~ 1.5 | 正常范围 | 无需处理 |
| 1.5 ~ 2.0 | 碎片偏多 | 关注，可手动触发整理 |
| > 2.0 | 碎片严重 | 开启 activedefrag 或重启实例 |

### 11.4.3 JEMALLOC 与内存分配

Redis 默认使用 jemalloc 内存分配器，相比 glibc malloc 能显著降低碎片。jemalloc 按固定 size class 分配（8、16、32、48、64、80、96、112、128...字节），存储小对象时实际占用会向上取整。

```
 jemalloc size class（部分）：
 ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┐
 │  8B  │ 16B  │ 32B  │ 48B  │ 64B  │ 80B  │ 96B  │ ...
 └──────┴──────┴──────┴──────┴──────┴──────┴──────┘

 存一个 20B 的 String value：实际占 32B（向上取整到 32B size class）
 存一个 50B 的 String value：实际占 64B
 碎片来源：频繁增删导致 free 的 chunk 难以复用
```

编译期切换分配器：

```bash
# 源码编译时指定分配器
make MALLOC=libc     # 使用 glibc malloc（碎片较高，不推荐）
make MALLOC=jemalloc # 默认，碎片最低
make MALLOC=tcmalloc # Google tcmalloc，性能与 jemalloc 接近

# 验证当前分配器
redis-cli INFO memory | grep allocator
# allocator:jemalloc-5.2.1
```

内存优化技巧：

```
1. 编码优化
   ├── Hash：field 少时用 listpack（7.0 替代 ziplist），省内存
   ├── List：元素少时用 listpack
   ├── Set：全整数且数量少时用 intset
   └── Sorted Set：元素少时用 listpack

2. 数据结构选型
   ├── 小对象用 Hash 代替多个 String（省 RedisObject 头部）
   ├── 布尔集合用 Bitmap 代替 Set
   └── 去重计数用 HyperLogLog 代替 Set（12KB 存 2^64）

3. key 设计
   ├── 缩短 key 名（但保持可读性）
   ├── 设置合理过期时间
   └── 避免大 key（>10KB）

4. 共享对象池
   ├── Redis 预创建 0~9999 的整数对象
   ├── 引用这些整数不分配新内存
   └── 超出范围才创建新对象
```

### 11.6.3 Python 监控采集

```python
import redis
import json

r = redis.Redis(host="localhost", port=6379, password="your_strong_password",
                decode_responses=True)


class RedisMonitor:
    def __init__(self, client: redis.Redis):
        self.r = client

    def get_metrics(self) -> dict:
        info = self.r.info()
        hits = info.get("keyspace_hits", 0)
        misses = info.get("keyspace_misses", 0)
        total = hits + misses
        return {
            "ops_per_sec": info.get("instantaneous_ops_per_sec", 0),
            "connected_clients": info.get("connected_clients", 0),
            "blocked_clients": info.get("blocked_clients", 0),
            "rejected_connections": info.get("rejected_connections", 0),
            "used_memory_mb": round(info.get("used_memory", 0) / 1024 / 1024, 2),
            "used_memory_peak_mb": round(info.get("used_memory_peak", 0) / 1024 / 1024, 2),
            "fragmentation_ratio": info.get("mem_fragmentation_ratio", 1.0),
            "evicted_keys": info.get("evicted_keys", 0),
            "expired_keys": info.get("expired_keys", 0),
            "hit_rate": f"{hits / total * 100:.1f}%" if total else "N/A",
            "latest_fork_usec": info.get("latest_fork_usec", 0),
            "rdb_last_status": info.get("rdb_last_bgsave_status", "unknown"),
            "aof_last_status": info.get("aof_last_bgrewrite_status", "unknown"),
            "role": info.get("role", "unknown"),
            "connected_slaves": info.get("connected_slaves", 0),
        }

    def check_health(self) -> dict:
        m = self.get_metrics()
        alerts = []
        if m["fragmentation_ratio"] > 1.5:
            alerts.append(f"内存碎片率过高: {m['fragmentation_ratio']}")
        if m["fragmentation_ratio"] < 1.0:
            alerts.append("正在使用 Swap，性能严重下降")
        if m["evicted_keys"] > 0:
            alerts.append(f"有 key 被淘汰: {m['evicted_keys']}")
        if m["rejected_connections"] > 0:
            alerts.append(f"连接被拒绝: {m['rejected_connections']}")
        if m["rdb_last_status"] != "ok":
            alerts.append(f"RDB 保存异常: {m['rdb_last_status']}")
        if m["latest_fork_usec"] > 50000:
            alerts.append(f"fork 耗时过高: {m['latest_fork_usec']}us")
        return {"metrics": m, "alerts": alerts}


if __name__ == "__main__":
    monitor = RedisMonitor(r)
    print(json.dumps(monitor.check_health(), indent=2, ensure_ascii=False))
```

| 调优核心 | 避免阻塞单线程（大 Key、O(N) 命令、fork） | 优化查询执行计划与索引 |
| 内存管理 | maxmemory + 淘汰策略，jemalloc 碎片 | innodb_buffer_pool_size，page 管理 |
| 慢查询定位 | `SLOWLOG GET`（微秒级阈值） | `slow_query_log` + `pt-query-digest`（秒级阈值） |
| 批量优化 | Pipeline / MGET / MSET 减少 RTT | 批量 INSERT / `LOAD DATA INFILE` |
| 索引机制 | 无索引，依赖数据结构（Hash/ZSet 跳表） | B+Tree 索引，覆盖索引优化 |
| 连接管理 | maxclients + 短连接复用 | max_connections + 连接池（HikariCP） |
| 持久化开销 | RDB fork / AOF fsync 阻塞 | redo log fsync、binlog 刷盘 |
| 监控栈 | redis_exporter + Prometheus | mysqld_exporter + Prometheus |
| 关键指标 | QPS、命中率、碎片率、延迟百分位 | QPS、TPS、慢查询数、Buffer Pool 命中率 |
| 压测工具 | `redis-benchmark` | `sysbench` / `mysqlslap` |
| 参数热更新 | `CONFIG SET` 在线生效 | `SET GLOBAL` 部分可热更，多数需重启 |
| 扩容方式 | 集群分片（哈希槽迁移） | 分库分表 / 读写分离 |
| 常见瓶颈 | 单线程 CPU、内存上限、网络 IO | 磁盘 IO、锁竞争、连接数 |
| 故障特征 | 延迟突增、连接拒绝、主从断开 | 慢查询堆积、锁等待、死锁 |

## 小思考题帮你巩固

1. **客户端"感觉慢"时，如何区分是网络 RTT 慢还是服务端执行慢？**（提示：SLOWLOG 只记服务端执行耗时；`CLIENT LIST` 看 idle、`PING` 测网络，见 11.1。）
2. **为什么说"慢查询多半是大 Key 造成的"？大 Key 与大 Value 分别怎么定位？**（提示：HGETALL/SMEMBERS 等 O(N) 遍历在单线程里阻塞；`--bigkeys` 按类型扫、`MEMORY USAGE` 测价值，见 11.3。）
3. **Pipeline 和 MGET 都能减少往返，它们有何区别？什么时候用哪个？**（提示：MGET 是单命令批量读同类型；Pipeline 可混合任意命令（写+读），但无单命令原子性，见 11.2。）
4. **碎片率 >1.5 和 <1.0 分别说明什么？各举一个处置思路。**（提示：>1.5 内存布局散（activedefrag）；<1.0 可能 SWAP（查 maxmemory 过高/换页），见 11.4。）
5. **redis-benchmark 压出来的吞吐为什么不能直接当"我的业务极限"？怎么压才可信？**（提示：默认只压 SET/GET 纯字符串、无 pipeline 无真实命令集；用你最重的命令+真实并发+`-P` 多跑几轮取中位数，见 11.5。）

<summary>参考答案（点击展开）</summary>

1. 看 `SLOWLOG`：若命令执行耗时不突出（都 <1ms），说明慢在网络/RTT（长连接复用、Pipeline 或就近部署）；若 SLOWLOG 出现大耗时，才是服务端执行慢（查大 Key/阻塞命令）。辅助：`CLIENT LIST` 看客户端 idle 时间与连接数，`LATENCY LATEST/HISTORY` 看事件延迟抖动。
2. 大 Key 上的遍历命令（HGETALL/LRANGE/SMEMBERS/ZRANGEALL）是 O(N)，单线程下一条执行几秒、整机卡顿——这类慢查询的元凶几乎都是大 Key。定位：`redis-cli --bigkeys`（按类型扫出最大 key）；精确测量用 `MEMORY USAGE <key>` 与 `OBJECT ENCODING`；治理=业务分片（大 Hash 按范围拆、大 List 拆短）或换更优结构。
3. MGET 是**一条命令**批量取同类型值（服务端执行一次、结果按序返回）；Pipeline 是**多条命令打包一次发送**（可混合任意类型命令、各自有返回）。MGET 更省服务端开销但只能"批量读"；Pipeline 灵活但有"批量发送、逐条执行"语义。业务"只是取一批值"用 MGET/MSET，混合写+读用 Pipeline。
4. >1.5：used_memory_rss 明显大于 used_memory（jemalloc 碎片/大 key 频繁增删）→ 开 `activedefrag yes`、整治大 key 增删模式；<1.0：RSS < used_memory 说明部分内存被换出（SWAP，磁盘 IO 拖垮延迟）→ 检查 maxmemory 是否设过高、物理内存是否吃紧，降 maxmemory 或扩内存。
5. benchmark 默认用 SET/GET 纯字符串、固定并发、无 pipeline、无真实命令分布，与生产负载相差大。要可信：挑业务最重的前几类命令（如 HGETALL/ZRANGEBYSCORE）、用贴近生产的并发 `-c`、`-P` 模拟管道、多轮取中位数；同时结合 SLOWLOG/INFO 验证压测结果与线上是否一致。

## 本章小结

| 主题 | 关键要点 |
|------|---------|
| 慢查询 | slowlog 仅记录命令执行耗时；阈值建议 10ms，队列 1024；优先排查 KEYS/大 Key/DEL |
| Pipeline | 单 Pipeline 建议 ≤1000 命令；非原子，强一致用 MULTI/Lua；可降低 RTT 30x+ |
| 大 Key | String >10KB / 集合 >5000；诊断用 --bigkeys/MEMORY USAGE；删除用 UNLINK/分批 |
| 内存碎片 | 碎片率 1.0~1.5 正常；>1.5 开 activedefrag；<1.0 排查 swap；默认 jemalloc |
| 压测 | redis-benchmark 必备；关注 QPS、p99、stddev；对比 Pipeline/大 value/持久化影响 |
| 监控栈 | redis_exporter + Prometheus + Grafana 一键部署；导入 Dashboard 11835 |
| INFO 指标 | 重点 connected_clients/rejected_connections/used_memory/碎片率/命中率/fork 耗时 |
| redis.conf | 网络/内存/持久化/安全/慢查询/IO 线程六大块；系统层禁 THP、overcommit=1、关 swap |
