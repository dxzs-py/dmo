# 05 复制与高可用

> Redis 通过主从复制实现读写分离与数据冗余，通过 Sentinel 哨兵集群实现自动故障检测与转移，是中小规模生产环境的高可用标准方案。

## 零基础前置认知

**这篇在讲什么**：单机 Redis 挂了就全挂、读压力大也扛不住——**复制（主从）**让数据有冗余、读可扩展，**哨兵（Sentinel）**让主节点挂了能自动"换班"（故障转移），是"从单机到高可用"的第二步。本篇讲清：**数据怎么从主节点复制到从节点**（全量 RDB + 增量 backlog）、**哨兵怎么判断"主挂了"并选新主**（主观/客观下线 + Raft 选主）以及**开发最该掌握的"客户端怎么连哨兵"**（故障转移对客户端透明）。读完你能搭出主从+哨兵、写对客户端连接代码，并说出故障转移的完整时序。*搭建类配置（生产 conf 片段、一键部署脚本）浓缩在篇末速查并引用 [codes/](./codes/) 的 4 个现成配置文件。*

> 辅助类比：把这段想成"门店打烊后的数据交接"——**主从复制**是"总店每天把账本复印送给分店"（全量=整本复印一次，增量=只送新记的几笔，积压缓冲区=总店留的"最近账目缓存"）；**哨兵**是"巡店老师傅团"（3 个老师傅互相盯着总店：一个说总店出事=主观下线，**过半老师傅都确认=客观下线**，然后老师傅们内部投票选出"带队人"（Raft Leader）重新指定分店顶班）；**客户端连哨兵**是"店员不知道谁是总店就打电话问老师傅团"，老师傅换班时主动广播"新总店在哪"——对店员完全无感。

**基础名词集**：

| 名词 | 一句话定义 | 与相邻概念的关系 |
|------|-----------|----------------|
| 主从复制 | master 把写命令同步到 replica（从库只读） | 读写分离 + 冗余；故障时 replica 可升级 |
| 全量同步 | 首次/断开超时：传输 RDB 快照 + 期间增量 | 由 `PSYNC ? -1` 触发，主节点 BGSAVE |
| 增量同步 | 断开超时较短：只补 offset 之后命令 | 依赖复制积压缓冲区（repl-backlog，默认 1MB） |
| 复制积压缓冲区 | 主节点保存最近写命令的环形缓冲 | offset 在缓冲区内→增量；超出→全量 |
| 主观下线 SDOWN | 单个哨兵觉得主节点挂了 | 由 down-after-milliseconds 超时判定 |
| 客观下线 ODOWN | 超过 quorum 个哨兵确认主节点挂了 | 触发故障转移的前提 |
| Raft 选举 | 哨兵们投票选出 Leader 执行转移 | Leader 需要过半票（max(quorum, n/2+1)） |
| replica-priority | 从节点升主优先级（越小越优先，0=永不） | 相同优先级比复制偏移量（数据最新优先） |
| min-replicas | 主节点要求至少 N 个从在线且延迟小，否则拒写 | 强一致场景的保护阀 |

> 区分/注意：**"主观下线" 与 "客观下线" 是针对谁说的**——SDOWN 是"一个哨兵认为某实例挂了"（对从节点也适用，但不触发转移）；ODOWN 只针对主节点且需要 quorum 确认，才触发故障转移。**故障转移 ≠ 强一致**：复制默认异步，主挂瞬间可能丢最后未同步的写；要更稳用 `min-replicas` 保护或 WAIT。**客户端要连哨兵而非直连主节点**：否则故障转移后你的客户端还握着旧主地址（这也是 8.x 客户端重点）。

## 一、主从复制

### 1.1 复制原理概述

将主服务器（Master）的数据复制到从服务器（Slave/Replica），实现：

- **读写分离**：主节点写，从节点读，分担读压力
- **数据冗余**：主节点故障时从节点可提升为主
- **灾备**：从节点可异地部署

### 1.2 复制架构图

```
一主一从：                一主多从：                级联复制：
┌──────┐                ┌──────┐                ┌──────┐
│Master│                │Master│                │Master│
└──┬───┘                └─┬──┬─┘                └──┬───┘
   │                      │  │                      │
   ▼                   ┌──┘  └──┐                ┌──┘
┌──────┐               ▼       ▼                ▼
│Slave│           ┌──────┐ ┌──────┐        ┌──────┐
└──────┘           │Slave1│ │Slave2│        │Slave1│
                   └──────┘ └──────┘        └──┬───┘
                                              │
                                           ┌──┘
                                           ▼
                                       ┌──────┐
                                       │Slave2│
                                       └──────┘
```

| 拓扑 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 一主一从 | 简单 | 从故障无备份 | 开发测试 |
| 一主多从 | 读扩展性好 | 主节点同步压力大 | 读多写少 |
| 级联复制 | 减轻主节点同步压力 | 延迟增大 | 大规模部署 |

## 二、复制流程：全量同步与增量同步

### 2.1 全量同步流程

```
全量同步流程：
┌──────────┐                          ┌──────────┐
│  从服务器  │                          │  主服务器  │
└─────┬────┘                          └─────┬────┘
      │  1. PSYNC ? -1 (首次连接)            │
      │ ──────────────────────────────────► │
      │                                     │
      │  2. FULLRESYNC <runid> <offset>     │
      │ ◄────────────────────────────────── │
      │                                     │
      │  3. 主服务器执行 BGSAVE              │
      │     生成 RDB 文件                    │
      │                                     │
      │  4. 发送 RDB 文件                    │
      │ ◄────────────────────────────────── │
      │                                     │
      │  5. 发送缓冲区增量命令               │
      │ ◄────────────────────────────────── │
      │                                     │
      │  6. 加载 RDB + 执行增量命令          │
      │     数据同步完成                     │
      └─────────────────────────────────────┘
```

触发全量同步的场景：

- 从节点首次连接主节点
- 从节点断开时间过长，offset 超出复制积压缓冲区
- 主从 runid 不匹配（主节点重启过）

### 2.2 增量同步流程

```
增量同步流程（Redis 2.8+）：
┌──────────┐                          ┌──────────┐
│  从服务器  │                          │  主服务器  │
└─────┬────┘                          └─────┬────┘
      │  1. PSYNC <runid> <offset>          │
      │ ──────────────────────────────────► │
      │                                     │
      │  2. CONTINUE (offset 在缓冲区内)     │
      │ ◄────────────────────────────────── │
      │                                     │
      │  3. 发送 offset 之后的增量数据        │
      │ ◄────────────────────────────────── │
      └─────────────────────────────────────┘
```

### 2.3 全量 vs 增量同步对比

| 对比项 | 全量同步 | 增量同步 |
|--------|---------|---------|
| 触发条件 | 首次连接 / offset 超出缓冲区 | runid 匹配且 offset 在缓冲区内 |
| 数据传输 | RDB 全量 + 缓冲区增量 | 仅 offset 之后的增量 |
| 网络开销 | 大 | 小 |
| 主节点负载 | 高（BGSAVE） | 低 |
| 持续时间 | 长（取决于数据量） | 短 |

## 三、复制积压缓冲区

### 3.1 原理

主服务器维护一个固定长度的 FIFO 队列（默认 1MB），用于增量复制。从服务器断开时间过长，offset 超出缓冲区范围，则需要全量同步。

```
复制积压缓冲区（环形缓冲区）：
┌───────────────────────────────────────────┐
│  offset=100   offset=200   offset=300     │
│  ┌──────┐    ┌──────┐    ┌──────┐         │
│  │ cmd1 │    │ cmd2 │    │ cmd3 │ ...     │
│  └──────┘    └──────┘    └──────┘         │
│  ▲                                       │
│  │                                       │
│  从节点 offset=150 → 在缓冲区内 → 增量同步  │
│  从节点 offset=50  → 超出缓冲区 → 全量同步  │
└───────────────────────────────────────────┘
```

### 3.2 配置命令

```bash
# 调整复制积压缓冲区大小
CONFIG SET repl-backlog-size 64mb

# 缓冲区存活时间（主从断开后保留多久，默认 3600 秒，0 表示永不释放）
CONFIG SET repl-backlog-ttl 3600

# 查看当前配置
CONFIG GET repl-backlog-size
CONFIG GET repl-backlog-ttl
```

### 3.3 缓冲区大小估算

```
repl-backlog-size 估算公式：
缓冲区大小 = 平均每秒写入量 × 预计最大断开时间 × 2

示例：
- 平均写入 1MB/s
- 预计最大断开 60 秒
- 缓冲区 = 1MB × 60 × 2 = 120MB（建议向上取整 128MB）
```

## 四、主从复制配置

### 4.1 命令行配置

```bash
# 在从服务器上执行（Redis 5.0+ 使用 REPLICAOF）
REPLICAOF 127.0.0.1 6379

# 查看复制状态
INFO replication

# 取消复制（从服务器变为主服务器）
REPLICAOF NO ONE

# 从服务器默认只读
CONFIG SET replica-read-only yes
```

### 4.2 配置文件方式（速查，完整配置见 codes/）

主从配置只需三个关键指令（`replicaof`/`replica-read-only`/`replica-priority`），完整可运行配置见 [codes/redis_master.conf](./codes/redis_master.conf) 与 [codes/redis_replica.conf](./codes/redis_replica.conf)：

```conf
# 从服务器配置（关键三行）
replicaof 127.0.0.1 6379      # 指定主节点
replica-read-only yes          # 从库只读（默认）
replica-priority 100           # 哨兵选主优先级（0=永不升主）

# 主从认证与调优（按需）
masterauth your_password       # 主节点开启了 requirepass 时，从库连主用
repl-timeout 60                # 复制超时（秒）
repl-backlog-size 64mb         # 复制积压缓冲区大小（按"每秒写入×断开秒数×2"估）
repl-backlog-ttl 3600          # 主从断开后 buffer 保留秒数（0=永不放）
replica-serve-stale-data yes   # 同步期间是否响应旧数据
repl-diskless-sync no          # 否=落盘 RDB 再传；是=直接 socket 传（省磁盘、占网络）
```

> 主从复制是"开发部署自研服务"的必要运维基础，配置保持最小集即可；完整生产化（密码/TLS/多从）见 [codes/](./codes/) 与 99 附录「运维速查」。

### 4.3 INFO replication 关键字段

| 字段 | 说明 |
|------|------|
| `role` | 角色（master/replica） |
| `connected_slaves` | 已连接从节点数 |
| `master_replid` | 主节点复制 ID |
| `master_repl_offset` | 主节点复制偏移量 |
| `repl_backlog_size` | 复制积压缓冲区大小 |

## 五、min-replicas 配置

主节点可强制要求至少 N 个从节点在线，否则拒绝写入：

```bash
# 至少 1 个从节点在线且延迟 ≤10 秒
CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10

# 查看配置
CONFIG GET min-replicas-to-write
CONFIG GET min-replicas-max-lag
```

适用场景：强一致性要求场景，避免主节点故障后丢失未同步数据。

## 六、哨兵 Sentinel

### 6.1 哨兵三大任务

| 任务 | 说明 |
|------|------|
| 监控（Monitoring） | 定期向主从服务器发送 PING 命令检测存活 |
| 通知（Notification） | 被监控的 Redis 实例出问题时通知管理员或应用 |
| 自动故障转移（Failover） | 主服务器故障时自动将从服务器升级为主服务器 |
| 配置中心（Configuration Provider） | 客户端连接哨兵获取主节点地址 |

### 6.2 哨兵架构图

```
┌─────────────────────────────────────────────────────┐
│                Sentinel 集群（3 节点）                │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐       │
│  │Sentinel1 │◄──►│Sentinel2 │◄──►│Sentinel3 │       │
│  │  :26379  │    │  :26380  │    │  :26381  │       │
│  └────┬─────┘    └────┬─────┘    └────┬─────┘       │
│       │               │               │              │
│       │    监控         │    监控        │    监控     │
│       ▼               ▼               ▼              │
│  ┌─────────────────────────────────────────────┐    │
│  │              Redis 主从集群                  │    │
│  │  ┌──────┐                                   │    │
│  │  │Master│ (:6379)                           │    │
│  │  └──┬───┘                                   │    │
│  │     │                                       │    │
│  │  ┌──┴─────┐    ┌──────┐                    │    │
│  │  │Replica1│    │Replica2│                  │    │
│  │  │(:6380) │    │(:6381) │                  │    │
│  │  └────────┘    └───────┘                    │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘

Sentinel 之间通过 pub/sub 互相发现（__sentinel__:hello 频道）
Sentinel 与 Redis 节点通过命令通信（PING/INFO/SENTINEL 命令）
```

### 6.3 故障检测机制

```
主观下线（SDOWN）：
单个哨兵认为实例下线（PING 超时）

客观下线（ODOWN）：
超过 quorum 数量的哨兵认为主服务器下线
→ 触发故障转移

┌────────┐  ┌────────┐  ┌────────┐
│Sentinel1│  │Sentinel2│  │Sentinel3│
│ SDOWN   │  │ SDOWN   │  │ SDOWN   │
└────┬───┘  └────┬───┘  └────┬───┘
     │           │           │
     └───────────┼───────────┘
                 ▼
           ODOWN（2/3 同意）
                 │
                 ▼
           故障转移开始
```

### 6.4 sentinel.conf 配置

```conf
# sentinel.conf（Sentinel1 配置）
port 26379
daemonize yes
pidfile /var/run/redis-sentinel.pid
logfile /var/log/redis/sentinel.log
dir /var/lib/redis

# 监控主服务器（名称 IP 端口 quorum）
sentinel monitor mymaster 127.0.0.1 6379 2

# 主服务器无响应超时时间（毫秒，默认 30 秒）
sentinel down-after-milliseconds mymaster 30000

# 故障转移超时时间（毫秒，默认 180 秒）
sentinel failover-timeout mymaster 180000

# 故障转移后同时向新主服务器发起复制的从服务器数量
sentinel parallel-syncs mymaster 1

# 主节点认证密码
sentinel auth-pass mymaster your_password

# 通知脚本（可选）
sentinel notification-script mymaster /var/redis/notify.sh

# 故障转移后执行脚本（可选）
sentinel client-reconfig-script mymaster /var/redis/reconfig.sh
```

### 6.5 关键参数说明

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `quorum` | — | 判定客观下线所需哨兵数量（建议 n/2+1） |
| `down-after-milliseconds` | 30000 | 主观下线超时（过短易误判，过长影响可用性） |
| `failover-timeout` | 180000 | 故障转移超时 |
| `parallel-syncs` | 1 | 故障转移后同时复制的从节点数（1 安全，多则快） |

### 6.6 启动哨兵

```bash
# 启动哨兵
redis-sentinel sentinel.conf

# 后台启动哨兵
redis-sentinel sentinel.conf --daemonize yes

# 使用 redis-server 启动哨兵模式
redis-server sentinel.conf --sentinel
```

### 6.7 哨兵状态查询

```bash
# 连接哨兵
redis-cli -p 26379

# 查看哨兵状态
INFO sentinel

# 查看主服务器信息
SENTINEL get-master-addr-by-name mymaster

# 查看主服务器下从服务器列表
SENTINEL slaves mymaster

# 查看其他哨兵信息
SENTINEL sentinels mymaster

# 查看所有被监控的主节点
SENTINEL masters

# 重置主服务器（清除故障转移状态）
SENTINEL reset mymaster

# 强制故障转移（手动切换）
SENTINEL failover mymaster

# 查看哨兵集群信息
SENTINEL ckquorum mymaster
```

## 七、故障转移流程

### 7.1 完整流程

```
故障转移步骤：
1. 哨兵检测到主服务器客观下线（ODOWN）
2. 哨兵集群选举 Leader 哨兵执行故障转移
   ├── 基于 Raft 协议
   ├── 任一 Sentinel 都可发起选举请求
   └── 获得过半票数（>= max(quorum, n/2+1)）成为 Leader
3. Leader 哨兵选择一个从服务器升级为主服务器
   选择规则：
   a. 排除已下线或断线的从服务器
   b. 按 replica-priority 升序选择（0 永不升主）
   c. 优先级相同选择复制偏移量最大的（数据最新）
   d. 偏移量相同选择 runid 最小的
4. 其他从服务器改为复制新主服务器
5. 更新哨兵监控配置
6. 旧主服务器恢复后变为新主服务器的从服务器
```

### 7.2 Leader 选举（Raft）

```
Sentinel Leader 选举流程（Raft 变体）：
1. Sentinel A 发现 ODOWN，发起选举（term+1）
2. 向其他 Sentinel 发送 SENTINEL is-master-down-by-addr 请求投票
3. 其他 Sentinel 在同一 term 内只投一票（先到先得）
4. 获得过半票数的 Sentinel 成为 Leader
5. Leader 执行故障转移

注意：
- quorum 是判定 ODOWN 的票数
- Leader 选举需要 max(quorum, n/2+1) 票
- 3 个 Sentinel 的集群，quorum=2，Leader 需要 2 票
```

### 7.3 故障转移时间估算

```
故障转移总耗时：
= down-after-milliseconds（检测下线）
+ Leader 选举（通常 <1 秒）
+ 选主 + 提升（<1 秒）
+ 从节点重新复制（取决于数据量）

默认配置下：30 秒 + 1-2 秒 ≈ 32 秒
可调小 down-after-milliseconds 缩短检测时间，但易误判
```

## 八、客户端连接哨兵

### 8.1 客户端流程

```
客户端连接哨兵流程：
1. 客户端连接 Sentinel，订阅 +switch-master 频道
2. 客户端通过 SENTINEL get-master-addr-by-name 获取主节点地址
3. 客户端连接主节点进行读写
4. 故障转移时 Sentinel 推送 +switch-master 通知
5. 客户端更新主节点地址并重连
```

### 8.2 Python 客户端示例

```python
from redis.sentinel import Sentinel

# 配置哨兵节点
sentinel = Sentinel([
    ("127.0.0.1", 26379),
    ("127.0.0.1", 26380),
    ("127.0.0.1", 26381),
], socket_timeout=0.5)

# 获取主节点连接
master = sentinel.master_for("mymaster", socket_timeout=0.5)
master.set("key", "value")

# 获取从节点连接
slave = sentinel.slave_for("mymaster", socket_timeout=0.5)
print(slave.get("key"))
```

### 8.3 Node.js (ioredis) 客户端示例

```typescript
import Redis from "ioredis";

const sentinel = new Redis({
  sentinels: [
    { host: "127.0.0.1", port: 26379 },

    { host: "127.0.0.1", port: 26381 },
  ],
  name: "mymaster",
  role: "master",
});

await sentinel.set("key", "value");
```

## 十、Redis vs MySQL 主从复制对比

| 对比项 | Redis 主从复制 | MySQL 主从复制 |

| 复制方式 | 异步（默认）/ 半同步 | 异步 / 半同步 / 组复制 |

| 复制延迟 | 单线程重放，大命令易延迟 | 多线程重放，延迟较低 |
| 配置复杂度 | 低 | 高 |

## 小思考题帮你巩固

1. **从节点断线 3 小时重连，为什么大概率走全量同步？**（提示：复制积压缓冲区默认 1MB 且 TTL 3600s，offset 早已超出，见三 3.1。）
2. **主观下线（SDOWN）和客观下线（ODOWN）分别是谁下的判断、决定什么？**（提示：单个哨兵 vs 超过 quorum 个哨兵；后者才触发故障转移，见六 6.3。）
3. **为什么 3 个哨兵的集群，`quorum=2` 才安全；quorum=1 或 2 个哨兵会怎样？**（提示：Leader 需要过半票 max(quorum, n/2+1)；哨兵过少或 quorum 太小，网络分区会脑裂出两个主，见六 6.5/七 7.2。）
4. **故障转移后，客户端是怎么"知道新主是谁"的？直连旧主的代码会怎样？**（提示：客户端连哨兵、订阅 `+switch-master` 并 `get-master-addr-by-name` 重新获取，见八 8.1。）
5. **异步复制下"主挂瞬间丢最后几笔写"能否避免？`min-replicas` 保护的是哪一类？**（提示：等 WAIT/半同步或 `min-replicas-to-write=1` 强制至少一个从跟上才接受写，见五。）

<details>
<summary>参考答案（点击展开）</summary>

1. 复制积压缓冲区是主节点保存的"最近的写命令"环形队列，**默认仅 1MB 且主从断开超过 `repl-backlog-ttl`（3600s）会释放**。断线 3 小时要么 buffer 已覆盖（offset 被冲掉）要么已被释放，从节点报出的 offset 在主节点已找不到 → 只能 `PSYNC ? -1` 全量（BGSAVE 传 RDB）。
2. SDOWN 是**单个哨兵**因 `down-after-milliseconds` 超时未收到 PING 回复而下线的判断（任何实例都可能）；ODOWN 只针对**主节点**，需要超过 `quorum` 个哨兵都确认其不可达才成立；ODOWN 才启动故障转移流程。
3. `quorum` 是"判定客观下线"的确认数；执行故障转移还要选 Leader，需要 **max(quorum, n/2+1)** 过半票。3 哨兵 quorum=2 → Leader 要 2 票（过半）。若只有 2 个哨兵或 quorum=1，在网络分区时可能"两个哨兵各判各的"，出现**脑裂**（两个主）——所以生产至少 3 哨兵、quorum≥2。
4. 客户端启动时向哨兵们 `SENTINEL get-master-addr-by-name mymaster` 拿主节点并连接，同时订阅 `+switch-master` 频道；故障转移完成后哨兵广播新主地址，客户端收到后重连。直连旧主地址的代码在故障后必然连不上（旧主已降从/失联）——这就是"必须走哨兵"的原因。
5. 异步复制下主挂瞬间的未同步写会丢；`min-replicas-to-write=1` + `min-replicas-max-lag=10` 让主节点"至少 1 个从在线且延迟≤10s 才接受写"，把"未同步即确认"的窗口压到接近零（牺牲可用性换一致性）；也可用 `WAIT numreplicas timeout` 让单次写等待同步确认。

</details>

## 最佳实践与常见陷阱

> 本节的每条都来自 Redis 高可用实践，按"现象 → 原因 → 处置"组织。

| # | 陷阱 | 现象 | 原因 | 处置 |
|---|------|------|------|------|
| 1 | 2 个哨兵配 quorum=1 | 故障后出现两个主 | 哨兵不够、票数不满足过半，网络分区脑裂 | 生产至少 3 哨兵，quorum=n/2+1（如 2） |
| 2 | 只配了 masterauth 忘了从库复制也鉴权 | 从库连接被拒、同步失败 | 主库 requirepass 后从库也要 masterauth | 从库配 `masterauth`（与 requirepass 同密码），见四 4.2 |
| 3 | repl-backlog 太小频繁全量 | 断线重连后总是全量（浪费带宽/阻塞） | buffer 太小覆盖了 offset | 按"每秒写入×断开秒数×2"调大（见 3.3） |
| 4 | 客户端直连主节点 IP | 故障转移后客户端全断 | 没走哨兵 | 客户端用 Sentinel 方式（redis-py `Sentinel`/ioredis `sentinels`），见八 |
| 5 | 主从配好后没验证 offset | 数据没同步却没发现 | 忽略 `master_link_status`/offset | `INFO replication` 定期核对 `master_link_status:up`、主从 offset 齐平 |
| 6 | 从库写入了数据 | 主从数据分叉 | 默认 `replica-read-only yes` 被改/旧版本行为 | 保持从库只读；确需临时写用 `no` 并知风险 |
| 7 | down-after-milliseconds 设太小 | 网络抖动就误判、频繁转移 | 判定阈值过短 | 与网络 RTT 匹配（默认 30s，跨机房可调大）；警惕频繁 failover 本身是风险信号 |

> **一句话总结**：Redis 高可用的杠杆在"**复制兜数据、哨兵兜主节点、客户端兜地址**"——复制要盯 backlog 大小与 offset、哨兵要至少 3 个且 quorum 过半、客户端必须连哨兵而不是死记主 IP；理解了 SDOWN/ODOWN 与 Raft 选主，"主挂了自动换班"就不再是黑盒。
